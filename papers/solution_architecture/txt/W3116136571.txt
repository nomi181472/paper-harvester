FOCUS: GUEST EDITORS’ INTRODUCTION

SERVERLESS SYSTEMS ARE becoming more popular and being
adopted by a large number of companies. Serverless computing is a new
paradigm that provides a platform to
efficiently develop and deploy applications to the market without having
to manage any underlying infrastructure.1,2 However, serverless solutions
introduce several new issues that companies need to tackle. In this article,
we introduce serverless technology
and its evolution, discuss its benefits
and issues, and describe future challenges that researchers should address.

Serverless Technologies

In the last few years, 3 developers
started thinking about operating their
systems instead of operating their servers, considering applications as work-

as overhead scaling, provisioning,
and infrastructure. In this case, the
program technically runs on external
servers with the support of cloud service providers.4
In serverless technologies, the
cloud provider dynamically allocates
the servers. That is, the code is executed in event-triggered stateless containers, which may last for more than
one invocation. In addition, serverless
solutions include different technologies, which can be classified as back
end as a service (BaaS) and functions
as a service (FaaS).
Baas allows the replacement of serverside components with off-the-shelf
services. It enables developers to outsource the aspects behind a scene of
an application so that developers can

Such examples include remote authentication systems, database management,

Google Firebase, which is a fully
managed database that can be used
directly from an application, is an
example of BaaS. In this case, Firebase (the BaaS services) manages data
components on our behalf.
FaaS is an environment used for
running software. Serverless applications are event-driven, cloud-based

systems where application development relies solely on a combination of
third-party services, client-side logic,
and cloud-hosted remote procedure
calls.4 FaaS allows developers to deploy code that, upon being triggered,
is executed in an isolated environment.
Each function typically describes a
small part of an entire application.
The execution time of functions is
typically limited (e.g., 15 min for AWS
Lambda). Functions are not constantly
active. Instead, the FaaS platforms
listens for events that instantiate the
functions. Therefore, functions must
be triggered by events, such as client
requests, events produced by any external systems, data streams, or others.
The FaaS provider is then responsible
for horizontally scaling function executions in response to the number of
incoming events.
Serverless applications can be
developed in several contexts; however, they may be limited in other
areas. For example, long-running
functions, such as machine learning
training or long-running algorithms,
might have timeout problems. Such
constant workloads might result in
higher costs compared to indefinitely
running on-demand computing services like virtual machines or container runtimes.

Serverless Computing
and Microservices
Serverless computing has several
characteristics in common with microservices, but it also has several
differences. In some cases, a serverless system is more suited for the job
than microservices. To understand
which to use, developers should understand how these two technologies
compare and contrast.
Microservices originated from the
evolution of software architectures1 to
reduce the complexity of monolithic

systems and service-oriented architectures. They are small and autonomous services with a single and
clearly defined purpose5 aimed at reducing the complexity of monolithic
applications.6 Microservices enable
the vertically decomposition of applications into a subset of businessdriven independent services connected
with lightweight communication protocols—usually HTTP application
programming interfaces (APIs). Each
service can be developed, deployed,
and tested independently by different
development teams and using different technology stacks. Microservices
have a variety of different advantages.
They can be developed in different
programming languages, can scale independently from other services, and
can be deployed on the hardware that
best suits their needs.
Microservices are commonly responsive to their interface, the primary
mechanism of interaction with the logic.
Serverless technologies, instead, are supported to be responsive to events, and
the APIs are mainly the mechanisms
adopted for generating the events. As an

example, it is possible to trigger a function from different event sources (e.g.,
a database or a message bus) without
using an API gateway. The key difference between microservices and serverless systems is the smaller granularity
of serverless functions and the adoption
of the event-driven paradigm. While it
is possible to develop event-driven microservices, it is highly recommended to
develop event-driven serverless applications. It is possible to compose different
serverless functions to create a microservice using different patterns, such as the
Saga7 pattern, the gatekeeper, and others. More details on serverless patterns
for microservices can be found in a paper by Taibi et al.8
When the first serverless platforms
came on the market, practitioners
started to build microservices using
serverless functions. As an example,
it is possible to build a microservice
with an API gateway as the service
interface, a serverless function behind it, and a switch statement to act
as a router. This very simple approach
enables applications to scale independently, but it is still not properly

leveraging the benefits of serverless
computing.
Microservices are best suited for
long-running, complex applications
that have significant resource and management requirements. Serverless functions are event driven and, therefore,
executed only when needed. When the
execution is over, the computing instance that runs the function is decommissioned. Serverless technologies are
more suited for event processing and
nonresource-intensive tasks. However,
serverless systems scale automatically,
without needing a specific infrastructure and, therefore, are more suitable
when developers need automatic scaling and lower runtime costs, while
microservices can be adopted when
flexibility is required.

2. Fast and independent deployment: Developers can deploy

single serverless function without needing to deploy the whole
system. While this is also possible for microservices, serverless
models allow a smaller function
to be uploaded, offering more independence than microservices.
3. No infrastructural costs:
When using traditional cloud
services, companies usually pay for generously large

machines to avoid running
out of resources. Costs are
paid independently from the
actual usage of the system.
With serverless models, there is
no need to buy servers or pay
fixed fees. Code is executed
only when triggered by an
event, and the infrastructure
is billed only for the effective
time that the code is executed.
In the case of short-running
tasks, this might dramatically
reduce the infrastructural

costs. However, in the case of
a continuously running task, it
might incur extra costs.
4. Autoscaling: Serverless functions
scale automatically, independently
from the load. Serverless applications can handle a very high number of requests as well as a single
request from a single client.
Serverless-based systems are distributed systems and introduce several complexities, including different
development paradigms (e.g., the
event-driven paradigm); the problem
of communication between services;
and the complexity of monitoring,
testing, and security.
1. Testing and debugging: The
replication of serverless environments is not always feasible, and
developers need to test serverless
functions in production. Debugging is even more complex because of the distributed nature of
serverless projects and because
the back-end processes are hidden to the developers. 2,9
2. Long-running processes: Longrunning processes might cost
more on serverless compared
to a traditional server-full
infrastructure.
3. Performance: Serverless functions are not always active,
and they need to be activated.
As a result, such a “cold start”
requires some time and might
introduce delays in the execution of applications. Some
workarounds have been proposed to “keep the functions
warm” and avoid the cold
start. However, some cloud
providers already provide
solutions to reduce the cold
start (e.g., https:// www
.cloudflare.com).

4. Vendor lock-in: Adopting a
serverless-based solution with
one vendor makes it very difficult to switch to another provider if needed. In particular,
the adoption of vendor-specific
databases, message buses, API
gateways, or other native
technologies increases even
more the vendor lock-in. Some
solutions for cross-provider
deployment have been proposed.

Architectural Perspective
Due to the novelty of serverless applications, there are few empirical data
30

I E E E S O F T WA R E

on how complex applications are
composed on the architectural level,
beyond what could be learned so far
from interviews and mixed-methods
studies.12 Typical architectures encompass cloud functions as the glue
code to automate processes based
on events; cloud functions as shortlived services exposed to the Internet bound to BaaS, avoiding the need

to restart servers and apply security
patches to web servers; and functions
deployed at various stages in dataprocessing pipelines, for instance, to
handle sensor data streams.
Now, you might be curious about
whether this is changing over time,
perhaps driven by new technologies.
Understanding the evolution requires
long-term observation studies on publicly available data. The AWS Serverless Application Repository is a prime
source of knowledge on how cloud
functions are composed with each
other and with back-end services, and,
luckily, the evolution of its content has
been recorded for the past two years.
From that observation, we know that
JavaScript and Python are, by far, the
most popular programming languages
(on AWS Lambda). We know further
that the execution models differ among
simple request–reply functions, iterators working over multiple inputs (e.g.,
bag-of-tasks functions), dispatchers,
and other forms. Finally, we understand that half of all applications are
single-function implementations and
that fewer than 15% bind the stateless
function to a stateful back end, effectively yielding a stateful application.
Taking the idea of event-driven
microservices further, not only can
we deploy declaratively specified
compositions of cloud functions and
back-end services in a GitOps-style
workflow, but we can also describe
with workflow models how they interact in causal order. It is in this space
where further innovation in serverless
applications engineering will happen.

Future Challenges
Trends emerge from the convergence
of serverless architectures with others to further free application engineers from infrastructural concerns.
One challenge is capturing rich portable deployment information so that

| W W W. C O M P U T E R . O R G / S O F T W A R E | @ I E E E S O F T W A R E

flexible data processing across the
edge–cloud continuum becomes easy
through optimized deployments. This
means departing from the instruction-centric serverless framework toward more goal- or intent-centric ones
where runtime behavior knowledge is
taken into account. Better tracing and
profiling are additional issues, freeing
the engineer from the need to specify
the runtime version or memory configuration—surely, in the age of artificial intelligence, it should be possible
to detect that automatically and avoid
effort and inconsistencies.
Another problem is the identification of optimal architectural patterns.
Developers often apply workarounds
to overcome serverless system limitations.2 As an example, developers might
try to find workarounds to avoid the
situation of double billing when having
a synchronous call waiting for the output of another call. From this point of
view, the major challenge is to change
the developers’ mindset, enabling them
to reason using an event-driven paradigm. The long-term evolution of the
systems is another important issue. The
lack of clear patterns but, also, vendor
lock-in increases the maintenance complexity due to the need to use only the
technologies provided by one provider
and the complexity of the migration to
other providers.
