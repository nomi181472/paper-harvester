Abstract
Digital twin simulation models evolve and are redeployed like software. Engines
based on the Discrete Event System Specification (DEVS) have a sound formal
basis but offer little support for versioning, automated validation, or continuous delivery in cloud-native environments. This paper proposes a model-centric
DevOps architecture that deploys DEVS-based digital twin simulations as managed services. Models are first-class DevOps artefacts written in a declarative
language based on YAML (YAML Ain’t Markup Language) with a tuple-level
mapping to the multiPDEVS formalism. Repository continuous integration (CI)
validates publishing manifests, the engine loader performs syntactic, structural,
and static semantic checks before every simulation, and published model artefacts are versioned and immutable, so that an earlier validated version can be
selected by pinning its identifier. The platform runs as containerised microservices
on Kubernetes with engine adaptations that externalise inputs and results and
expose lifecycle control. An initial case study on bus route 22 in Riga exercises
the lifecycle on an offline model with roughly 115,000 DEVS atomic components and reports single-container throughput and concurrent job execution on
one Kubernetes node. Behavioural validation and multi-node evaluation remain
future work.
Keywords: digital twin, DEVS, model-driven engineering, domain-specific modelling
language, cloud-native architecture, DevOps, CI/CD, simulation model lifecycle

1 Introduction
Digital twins are now used across engineering domains for continuous monitoring, prediction, and optimisation of physical systems through their virtual counterparts [1, 2].
Most implementations rely on dynamic simulation to let the virtual model reproduce
and predict system behaviour under varying conditions. Among formal frameworks,
the Discrete Event System Specification (DEVS) [3] offers a systems-theoretic basis
for modelling such systems.
DevOps practices have reshaped software delivery through continuous integration and deployment (CI/CD) pipelines [4], yet these practices remain insufficiently
integrated into the lifecycle of DEVS simulation models. Simulation models evolve iteratively like software, but lack the standardised mechanisms for automated validation,
versioned deployment, and rollback that DevOps pipelines provide elsewhere.
Many digital twin implementations are still built ad hoc [5], and most DEVS
engines were built for desktop or cluster execution with persistent processes, direct file
system access, and manual configuration. These assumptions clash with cloud-native
deployment, where containers are ephemeral, scaling is horizontal, and infrastructure
is declared as code.
The research problem addressed in this paper is therefore the absence of an engineering lifecycle in which a DEVS model is specified, validated, versioned, deployed,
and reverted through the automated mechanisms that software artefacts already have,
while keeping the formal semantics that motivate DEVS. Three research questions
follow from this problem and structure the paper:
1. Can DEVS models be specified declaratively in a form that allows well-formedness
with respect to the formalism to be checked before a simulation is executed, enabling
validation as a continuous integration (CI) stage?
2. What adaptations enable a classical DEVS engine based on persistent processes to
execute as an ephemeral, horizontally scaled cloud workload while ensuring that
each run is reproducible from versioned artefacts?
3. Does the resulting lifecycle let a digital-twin model of realistic scale be varied
through configuration changes alone, without modifying the engine code, while
achieving sufficient throughput for iterative use?
This paper presents a model-centric DevOps architecture for deploying DEVSbased digital twin simulations as managed services. The contributions are the
following:
1. A declarative Simulation Model Definition Language (SMDL) based on YAML
(YAML Ain’t Markup Language) for DEVS simulation models with a tuplelevel mapping to the multiPDEVS formalism [6], and a companion Simulation
Scenario Definition Language (SSDL) that binds model versions to scenario
parameterisations, enabling version control, automated validation, and CI/CD
integration.
2. A microservices-based cloud-native architecture with engine adaptations that externalise inputs and results and expose lifecycle control, letting a classical DEVS

2

simulator operate as a cloud-native workload while keeping model management,
execution, and data integration independently deployable.
3. A publishing and execution pipeline for simulation models in which repository CI
validates the publishing manifest, the engine loader applies syntactic, structural,
and static semantic (well-formedness) validation before every run, and publishing produces immutable versioned artefacts from which an earlier validated model
version is selected by pinning its identifier.
4. An initial case study on the Riga bus route 22 corridor that exercises the lifecycle
on an offline simulation model, quantifies single-container engine throughput and
concurrent job execution on one Kubernetes node, and varies a multi-modal scenario
through manifest and data changes without engine-code changes.
The four contributions together answer the three questions. Each ingredient has a
precedent: DEVSML 3.0 [7] already grounds a declarative model language in formal
DEVS semantics, CI pipelines for simulation software validate declarative metadata [8,
9], and immutable versioned artefacts with pinning-based reversion are standard in
DevOps and MLOps tooling [10, 11]. The novelty of this paper is their integration
within a single model lifecycle; the surveyed platforms each address a subset of them.
In the evaluated system the loader’s checks run at job start. The Discussion answers
each question and states what the evidence supports and what remains untested.
The work extends our prior research on DEVS-based simulation engines for digital
twins [12] to their operational lifecycle in the cloud.

2.1 Digital Twins and DEVS Simulation
The digital twin concept, introduced by Grieves [1], describes a virtual representation
of a physical system with bidirectional data flow between the physical and digital
spaces. Tao et al. [2] formalise a five-dimensional model of physical entity, virtual
entity, services, data, and connections, and the survey by Fuller et al. [21] maps the
enabling technologies.
DEVS [3] defines atomic models with states, input/output ports, and transition
functions, together with coupled models that compose atomic models via port couplings. multiPDEVS [6] extends Parallel DEVS to multicomponent systems with
nonmodular decomposition and efficient handling of simultaneous events. Mature
engines surveyed by Wainer and Govind [22] include ADEVS [23], CD++ [24],
VLE [25], PyPDEVS [26], and xDEVS [18], complemented by graphical authoring
(DEVS-Suite [27]) and DEVS-based co-simulation wrappers (MECSYCO [28]). The
suitability of DEVS for digital twins has been recognised in the context of digital
quadruplets [5], and Vanommeslaeghe et al. [29] demonstrate co-simulation with Functional Mock-up Interface (FMI). Our work builds on a multiPDEVS engine [12] that
supports hierarchical composition with Parallel DEVS semantics.

2.2 Cloud-Native Simulation and DevOps for Models
Simulation engines have shifted from monolithic designs toward modular [30], containerised, and orchestrated services [16]. Simulation services are increasingly exposed
as microservices [13, 14] and deployed through orchestrators such as Kubernetes [15,
20], which improves scalability and manageability for digital twin and cyber-physical
workloads. Current digital twin platforms adopt stateless, cloud-native, service-based
architectures [17]. Such frameworks support scalable data integration and distributed
execution, but they concentrate on deployment logistics and leave model management
aside (Table 1).
Closing the gap between deployment and model management requires automated
model lifecycles. In software development, process automation is now routine practice [10], yet model management still lags behind [31]. CI/CD practices in software
and AI development provide versioning, staged validation, delivery, monitoring, and
4

rollback, and DevOps and Machine Learning Operations (MLOps) tooling is gradually extending these capabilities to models [10, 11]. For simulation software, prior work
on GitLab-based CI/CD for large-scale simulation software [8] and DevOps models
for metadata-driven tools [32] shows that simulation code and metadata can be integrated into automated pipelines [9, 33]. Simulation models themselves, however, are
not yet consistently treated as first-class DevOps artefacts and still lack widely adopted
approaches for declarative specification, structural and static semantic validation, and
CI/CD across their cloud lifecycles. Recent work on DevOps, model-driven engineering
(MDE), and MLOps documents the same shortfall [9, 33, 34]. Complementary work
on digital twin programming with semantically lifted states [35] ties runtime data to
ontologies and formal specifications, reinforcing the case for treating twin models as
structured, queryable artefacts. The adoption of SysML v2 [36] provides a standard
systems-modelling language for such artefacts; its relation to the declarative language
proposed here is discussed in Section 3.1.

3 Model-Centric Representation and Lifecycle
A central design principle of our architecture is treating simulation models as versioncontrolled artefacts with a well-defined lifecycle. Two declarative languages carry
this lifecycle. The Simulation Model Definition Language (SMDL) defines what a
model is and how it behaves. The Simulation Scenario Definition Language (SSDL)
defines under which configurations a model is studied: it binds registered model versions to parameterisations, datasets, replications, and random seeds. This section
covers SMDL, its mapping to the DEVS formalism, and the validation and versioning
strategy; SSDL is described together with scenario assembly in Section 5.2.

3.1 YAML-Based Model Definition Language
SMDL specifies DEVS simulation models in YAML, a human-readable, versioncontrollable format. The language draws on the declarative style of Microsoft’s
Digital Twins Definition Language (DTDL) [37] and shares the MDE stance of
DEVSML 3.0 [7]; YAML files yield line-oriented Git diffs and can be checked in CI
with the tooling already used for container manifests. Figure 1 shows the abstract
syntax: atomic models with control state, memory, and the DEVS characteristic functions, recursively composed coupled models, typed ports, couplings, and parameters.
The diagram mirrors the engine’s model classes; the concrete schema described next
realises a subset of it, and the structural validation layer checks conformance to that
schema. The coupling type determines its endpoints: an output port of a component
to an input port of a sibling (IC), an input port of the coupled model to an input port
of a component (EIC), or an output port of a component to an output port of the coupled model (EOC). The language covers fully declarative models (behaviour configured
through parameters of pre-built classes) and hybrid models (behaviour implemented
in code and referenced by name).
A model document lists tagged model definitions under models:; the tag selects the
modelling style: !<discrete event> for process-oriented models, !<agent based> for
agent populations, and !<hybrid> for agents that flow through a network of blocks.

3.1.1 Relation to SysML
With the adoption of SysML v2 and its kernel language KerML by the Object Management Group [36], a standardised language exists whose constructs can express the
structural content of an SMDL document: coupled models correspond to part definitions with nested part usages, ports to port definitions, couplings to connections,
and atomic models with few control states to state definitions with transitions. A
multiPDEVS domain library in SysML v2 is therefore feasible, as DEVSys showed
for SysML v1 [38], and we regard it as an alternative concrete syntax for the same
semantic domain. Three considerations led us to keep YAML as the artefact that the

7

pipeline validates and stores. First, SysML v2 does not define time advance, confluent transitions, or multiPDEVS influencer sets; a domain library would encode them
as metadata, and the transformation to Eqs. (1)–(2) with its well-formedness checks
would still be required. Second, the checks described below need only a YAML parser
and the engine’s loader, which a CI runner can invoke; evaluating SysML v2 constraints there requires a SysML v2 implementation and the DEVS domain mapping.
Third, the model authors in our setting are transport analysts, for whom we expect a
compact YAML syntax to present a lower entry barrier; this expectation has not been
evaluated. The natural integration is a SysML v2 front end or KerML domain library
whose instances are exported to SMDL through the standard API, so that models
authored in the standard reuse the same pipeline; Reiterer et al. [9] extend SysML v2
with DevOps metadata in this spirit.

3.2 Mapping to DEVS
The semantic domain of SMDL is the multiPDEVS formalism of Eqs. (1)–(2), and
the SMDL Processor realises a model-to-model transformation from the abstract syntax (Figure 1) into it. Structural validation (Section 3.3) checks conformance to the
implemented SMDL schema described above; static semantic validation then checks
the well-formedness conditions listed at the end of this subsection on the transformed
instance. These conditions do not establish that the code of a referenced component class conforms behaviourally to DEVS execution semantics, which belongs to the
behavioural layer of the validation strategy.
The SMDL Processor translates a YAML model definition into the internal multiPDEVS [6] representation used by the simulation engine, following the Modelling
and Simulation as a Service (MSaaS) paradigm [12]. Figure 2 shows the engine architecture: the SMDL Processor parses the model specification and instantiates DEVS
elements, the Simulation Manager coordinates execution following the multiPDEVS
abstract simulator of [6] as implemented in [12], and an FMI adapter supports cosimulation with external Functional Mock-up Units [29, 39]. A Hierarchical Engine for
Large-scale Infrastructure Co-Simulation (HELICS) broker [40] further connects the
engine to multi-domain federates for scalable cyber-physical co-simulation scenarios.
We formalise the mapping target using the multiPDEVS formalism of [6], with XMachines [41] providing the component memory structure as adopted in the engine
design of [12]. A multiPDEVS model is a tuple

The engine executes two kinds of models. The components of a multiPDEVS model
interact through the influence relations Id and Ed : a transition of component d reads
the states of its influencers and proposes state changes to its influencees, without
ports. Classic Parallel DEVS atomic and coupled models with explicit ports [3] interact
through events on port couplings and run on the engine’s port-based simulator; in
terms of Eq. (1), such an atomic model corresponds to a multiPDEVS model with a
single self-influencing component, D = {d} and Id = Ed = {d}, whose event sets X
and Y are its port events. This correspondence places the port-based models in the
formal picture, and the engine performs no such translation. The transport model of
the case study consists of port-based models generated by a domain builder; it is not
written in SMDL, so the mapping below does not apply to it.

The SMDL Processor maps a !<discrete event> document to one flat multiPDEVS model of the form of Eq. (1), without wrapping the block network into
port-coupled models: D is the set of block names, the entities declared under
entities: are the items that components hand to each other, and X and Y are
empty, because a model document has no external ports. Each block becomes a component tuple of the form of Eq. (2). For fully declarative components, the block tag
selects a pre-built class that supplies the control states Sd and the transition, output,
and time-advance functions, and the fields of the block parameterise them; for hybrid
components, a script reference supplies the memory Md and the code of the functions
that operate on it. The sets Id and Ed are derived from the wiring and never written
by the modeller: in this mapping every block influences itself, d ∈ Id ∩ Ed , because its
internal transition changes its own state, and a reference to: b in block a adds b to
Ea and a to Ib . The handover of an entity from a to b is the proposal of Eq. (2): during
its transition, a offers the entity to b, which accepts or refuses it according to its own
state. For the first two blocks of Listing 1, Iar1 = {ar1}, Ear1 = {ar1, r1 approach},
Ir1 approach = {ar1, r1 approach}, and Er1 approach = {r1 approach, qr1}; the time
advance of ar1 is the next sample of its inter-arrival distribution, and its internal transition creates a car entity and offers it to r1 approach, whose time advance while it
holds an entity is the value of its delay expression, after which it offers the entity to
qr1.
Three well-formedness checks read directly from the tuple components and form
the core of the static semantic layer: (i) reference integrity: every to: reference, and
every route target of a routing block, must name a block declared in the same model,
so that Ed ⊆ D for every component; (ii) closure of the wiring: every block other than
a sink must name at least one receiver, and a sink names none; (iii) block names must
be unique, so that D is a set. Checks (i) and (iii) hold for every multiPDEVS instance.
Check (ii) is an SMDL wiring constraint: the formalism admits Ed = {d}, and the
constraint exists because a document has no external interface, so an entity leaving a
block without a receiver would be lost silently. The checks are necessary conditions and
establish no further property of the formalism; the loader does not check, for instance,
for cycles of blocks with zero time advance. In Listing 1, renaming the target of ar1
to an undeclared block violates check (i) and produces the third diagnostic of Table 2.

3.3 Validation and Versioning
Each model definition is versioned using semantic versioning (major.minor.patch):
patch for parameter adjustments that do not alter model structure, minor for
backward-compatible additions of new components or ports, and major for interfacebreaking structural changes. The convention is applied by model authors; the pipeline
does not yet check a version increment against the structural change it accompanies (Table 3). The Model Management Layer maintains a full history of deployed
model versions, so that an execution request names the exact model version it uses.
A pinned model version fixes one input of a run; the identity of a run also comprises
the SSDL document, the input datasets, the random seeds, and the engine build. The
SSDL document records the model and dataset references, the replication settings,
and the seed. Datasets are referenced by version-scoped object-store paths, immutable
10

by convention, and the engine image by a tag in the job manifest; a tag can move to
another image, so a reproducible record needs the image digest, which the platform
does not store yet. The artefact bundle of the case study (Data availability statement)
records the engine commit, the image digest, the SHA-256 checksum of every input
file, and the seeds of every reported run. Such a record reconstructs the inputs of a run
exactly; equality of results across Java Virtual Machine (JVM) versions, hardware,
and concurrent scheduling was not tested.
Validation is organised in layers whose names we fix here, because the terms are
used differently across the MDE and digital-twin communities. Syntactic validation
checks that the document is well-formed YAML. Structural validation checks conformance to the SMDL schema derived from the metamodel of Figure 1 (required fields,
field types, and admissible tags). Static semantic validation checks the well-formedness
conditions of the previous subsection on the mapped instance, the availability of referenced entities, resources, and functions, and parameter range constraints, which
depend on the model class. All three layers are static: they are decided on the artefact
when it is loaded, before any simulation is executed, so they can run as CI stages. In
the evaluated implementation the engine’s loader performs them in this order, through
its YAML parser, the typed deserialisation of the document into the schema classes,
and a normalisation pass that checks wiring and parameters; the loader is part of the
engine executable, and a separate validation-only tool is not provided. Behavioural
validation, which checks that simulated behaviour matches the intended semantics of
the physical system, satisfies domain invariants, or agrees with observed execution
traces, is a distinct runtime concern. The pipeline reported here does not implement
behavioural validation. Throughout this paper, “semantic validation” refers to the
static layer. Extensions towards behavioural validation are discussed below.
Table 2 walks model revisions through the three static layers by injecting four
faults: three into the bus route 22 manifest and the coupling fault into the SMDL
model of Listing 1. Each revision was loaded with --scenario=file on an SSDL project
that references the faulty model. Each fault is rejected by the earliest layer able to
detect it, and the process exits with a non-zero status before simulation starts, so a
CI stage that runs this command fails for such a revision. In the evaluated system the
three layers run inside the loader at the start of every job, so every executed case-study
scenario passed them. The repository pipeline of Section 5 checks the manifest against
the platform schema; a loader stage that blocks registration of a rejected revision is
the intended integration and has not been wired in yet.

Table 3 lists the richer forms of validation expected in digital-twin engineering, the
hook the present architecture provides for each, and the extension required. Two of

5 DevOps Pipeline for Simulation Models
Four services realise the DevOps pipeline. A Simulation Model Registry and a Simulation Model Publishing worker implement the Model Management layer by cataloguing
models and ingesting model repositories. A Simulation API, which manages projects,
13

scenarios, experiments, and jobs, and a Simulation Orchestrator, which materialises
each job as a Kubernetes workload, implement the Simulation Execution layer. RabbitMQ delivers each work item (publish, delete, dispatch) to a single consumer, Kafka
fans progress and lifecycle events out to multiple listeners, and an S3-compatible object
store holds all artefacts.

5.1 Model Publishing and Registration
Each simulation model is authored in a dedicated Git repository with a
manifest.yaml that describes metadata, component sources, inputs, outputs, parameters, and runtime requirements. A repository-level CI pipeline validates the manifest
against the platform schema and registers the model with the registry, which creates a
catalogue entry keyed by (code, version ) and queues a publish message. The publishing
worker clones the repository at the requested revision and uploads the processed manifest, model payload, and documentation under a version-scoped object-store prefix.
The registry record is then marked published with its artefact URLs, or failed, in
which case the author corrects the source and publishes a new version. Earlier releases
remain immutable in catalogue and object storage, which underpins the reproducibility of downstream experiments. Figure 4 summarises this stage. Loader-based model
validation is not yet a step of this pipeline; in the evaluated system it runs when a job
starts.

5.2 Scenario Assembly and Job Dispatch
A published model is consumed through three entities that the Simulation API persists: a SimulationProject groups related work, a Scenario binds a registered model
version to a concrete parameterisation and an optional dataset, and an Experiment
defines a parameter sweep over its parent scenario. Figure 5 shows this structure. When
execution is triggered for a project, a subset of its scenarios, or individual experiments,
the API performs three steps for each selected scenario.
First, it generates an SSDL document that inlines the project metadata, the model
locator resolved by the registry, and the scenario configuration with its experiments
expanded in place. Second, it uploads the document to a version-scoped object-store
path, so that the engine receives a self-contained, versioned input. Third, it creates a
SimulationJob record and queues a dispatch message with the job identifier and the
scenario, model, and optional dataset URLs for a single orchestrator worker.
The API thus decides what to run, and the orchestrator decides where and how
to run it. The dispatch message carries only identifiers and immutable object-store
references, so a redelivered message describes the same inputs. Delivery to a single
consumer does not guarantee exactly-once execution, and the handling of redelivered
messages was not exercised in the evaluation.

5.3 Engine Adaptations for Cloud Deployment
The Simulation Orchestrator renders a base engine manifest from object storage into
a job-specific Kubernetes specification: resource names carry the job identifier, so concurrent runs do not collide, and the job metadata is injected as environment variables.

6 Case Study and Evaluation
The Riga bus route 22 corridor is the first instantiation of our planned city-wide multimodal transport digital twin; it exercises the architecture end-to-end while remaining
tractable to analyse in depth. The case study extends our earlier DEVS-based geosimulation framework for public transport analysis and planning [42] to the cloud-native
DevOps setting presented here. The study is offline: its inputs are the published
network and schedule, one day of historical e-ticket validations, and a synthetic car
demand, with no live connection to the physical system. Table 4 maps each claim
examined in this section to its evidence and to the boundary of that evidence. The
intersection model of Listing 1 exercises the SMDL transformation and wiring checks;
the transport case study evaluates the shared lifecycle and execution infrastructure
with a domain-generated Parallel DEVS model.

Bus route 22 links the centre of Riga (Abrenes street) with Riga International Airport

intended to support transport planners with demand–supply equilibration, transit

6.3 Multi-Modal Routing and Iterative Equilibration
Car routes are computed by time-dependent Dijkstra on the road graph using the
current iteration’s edge travel time estimates. Transit routes enumerate candidate
(line, boarding stop, alighting stop) triples over the published schedule, scoring each
by walking access and egress, in-vehicle travel time, and accumulated dwell times
against the same time-dependent edge weights, so that router and simulator remain
18

consistent. Each transit ride is materialised as a synthetic wait -edge identifier that
routes the traveller to the appropriate TransitStopModel.
Demand–supply equilibration follows a MATSim-style [47] co-evolutionary loop
reimplemented inside the DEVS engine so that network simulation, scoring, and
replanning all share the same DEVS event semantics, event stream, and versioned
manifest. Each iteration runs the full DEVS simulation, scores plans with a Charypar–
Nagel utility [48] (non-arrival penalty −1000), stochastically replans a fraction of
travellers (30% route, 10% mode, 20% ±15 min departure shift), and updates edge
travel times via the Method of Successive Averages. Convergence is tested on periteration score statistics: after each iteration k the mean ūk and the sample standard
deviation σk of the scores of all traveller plans are recorded, with a plan that produced no arrival assigned the configured penalty, and the loop stops after at least
five iterations when, over the last five iterations, maxk ūk − mink ūk ≤ 0.02 and
maxk σk − mink σk ≤ 0.02. Both tolerances are absolute, in the utility units of the
scoring function (the manifest sets the first, and the second keeps its default), and the
second condition requires the dispersion of scores across travellers to have stabilised;
a large but steady dispersion satisfies it. Utility coefficients are listed in the manifest
of Listing 2. The measurements reported below use a single simulation pass without
replanning, so the convergence behaviour of the loop is not evaluated in this paper.

6.4 Simulation Results
The published bus route 22 model is executed through the publishing and execution
pipeline, which materialises one Kubernetes job per scenario (Figure 7) and so isolates
scenarios at the container level. The registration, publishing, dispatch, and callback
stages were exercised on the project’s Kubernetes deployment, and the measurements
that follow were made on a dedicated single-node cluster specified in Section 6.5.
Table 5 summarises the scenario parameters and single-run results for the Riga bus
route 22 simulation with a 24-hour horizon, matching the full day of the validation log.
Of the 17,697 travellers in the demand file, 17,676 arrive within the 24-hour horizon:
11,986 of 12,000 car trips and 5,690 of 5,697 transit trips (99.9% of each). The engine’s
post-run invariant report accounts for the remaining 21, all still under way when the
horizon ends (19 on links, one waiting at a stop, one alighting); no traveller is skipped
at the source, discarded at an intersection, or rejected on a link, and all twelve checks of
the report pass. Of the arriving transit travellers, 4,821 ride the bus and 869 complete
the trip on foot, because the schedule-aware router returns a walking plan when it
reaches the destination earlier than the next departure. Thirteen vehicles find the first
link of their path full and wait at its entry until a slot becomes available. The report
prompted this correction: on an earlier engine build the scenario failed the travellerconservation check because five buses leaving a stop into an occupied single-vehicle
link were dropped with their 22 passengers; the link model now holds such a vehicle
at the entry, and all measurements use the corrected build. The report is an engine
diagnostic (Table 3): the engine writes it with the results and exits with status zero
regardless of the report, and no pipeline stage reads it yet, so a completed job does
not demonstrate that the domain invariants hold.

7 Discussion
The first research question, declarative specification with well-formedness checking
before execution, is supported for the implemented SMDL subset by the tuple-level
mapping and the loader’s rejection of the four injected faults, one in an SMDL

23

document and three in the transport manifest. The checks establish selected wellformedness conditions; they do not establish complete formalism conformance or
behavioural conformance to DEVS execution semantics, and no mechanised proof is
claimed.
The second research question names three properties, for which the evidence differs. Ephemeral execution rests on the four engine adaptations, under which the engine
runs as a Kubernetes job that fetches its inputs, posts its results, and keeps no execution state beyond the run; this path was exercised functionally on the project’s
deployment. Scenario-level concurrency was measured with up to six jobs on one node;
scale-out across nodes is untested, and no matched non-Kubernetes baseline exists for
an isolation overhead. Reproducibility has three parts: reconstruction of the reported
experiments is supported by the artefact bundle (Section 3.3), automatic provenance
in the platform is incomplete because the image digest is not retained, and numerical repeatability was shown as identical arrival counts across repetitions on one image
and node, untested across environments.
Variation of a realistic model through configuration alone at a throughput sufficient
for iterative use, the third research question, is supported by the bus route 22 case
study, which, within the caveats below, varied a multi-modal scenario through manifest
and data changes on one model version at no less than 450× real time. A structural
revision through validation, publishing, execution, and reversion was not exercised,
so the evidence for model evolution is the lifecycle design and the immutable registry
history.
Among the systems compared in Table 1, the closest neighbour is DEVSML 3.0 [7],
which shares cloud-native DEVS deployment, declarative model specification, and formal DEVS semantics; the cited work reports no CI/CD lifecycle, immutable versioned
artefacts, or loader-based static semantic validation before every run, which this paper
adds. xDEVS [18, 19] offers formal DEVS semantics and a cloud-enabled distributed
architecture without a declarative model lifecycle, and the Modelica-based platform
of Kumar et al. [17] and KTWIN [20] provide declarative twin definitions on cloudnative platforms without model CI/CD or versioning. The equilibration loop is close
in spirit to MATSim [47]; it runs inside the DEVS engine, so simulation, scoring, and
replanning share one event semantics and one versioned artefact.
Engine portability. The registry, publishing worker, version pinning, SSDL scenario assembly, job dispatch, and the result-callback and lifecycle-event contracts are
engine-agnostic: they treat the model as an opaque versioned artefact plus a manifest. The SMDL-to-multiPDEVS mapping and the adaptations that externalise inputs
and results are engine-specific. A different DEVS engine, such as xDEVS [18] or
PyPDEVS [26], would have to implement the same four adaptations, and DEVS/DESS
would need additional abstraction in the SMDL mapping; none has been hosted yet.
Deployment portability. The Kubernetes dependency is confined to the Simulation
Orchestrator, whose job renderer, service addressing, and reconciliation worker use
the Kubernetes API; the Simulation API, registry, and publishing worker do not. A
different container runtime therefore replaces one service; this boundary follows from
the architecture, and no second runtime has been exercised.

24

Evaluation limits. The evaluation covers transport only; a manufacturing or energy
model would exercise continuous dynamics and the co-simulation paths (FMI and
HELICS adapters of Section 3.2) that the bus route 22 study does not. Engine performance was measured with a fixed 4 GB JVM heap; just-in-time (JIT) compiler
warm-up and heap-size sensitivity were not studied. The transit demand is derived
from the e-ticket validation counts and times of a single weekday, with line directions
and stops assigned at random. The car demand is synthetic and inherits the temporal
profile of the transit demand. Travel-time and behavioural parameters were not calibrated against observations. The point-queue link model does not capture signalised
intersection dynamics, so the sub-capacity baseline does not demonstrate that the
engine handles saturated traffic correctly.

8 Conclusion and Future Work
The architecture presented in this paper makes DEVS simulation models first-class
DevOps artefacts: SMDL gives them a declarative, versioned form with a tuple-level
mapping to multiPDEVS. Repository CI validates their publishing manifests and publishes them as immutable versioned artefacts, the engine loader applies the static
validation layers before every run, and four engine adaptations let a classical multiPDEVS engine run as a Kubernetes job that keeps no execution state beyond the run.
The offline bus route 22 case study exercised this lifecycle on a model with roughly
115,000 atomic components; scenarios were configured through the transport manifest
without changes to engine code, and each configuration passed the static validation
layers before execution.
The next steps concern the pipeline itself: the loader as a registration-blocking
stage of the repository pipeline, fault-detection rates over a curated corpus of model
revisions, the version-evolution and regression stages of the validation strategy, a stage
that gates jobs on the engine’s invariant report, and measurements of the convergence
of the equilibration loop and of orchestrated multi-scenario execution across several
nodes. The principal application direction is to scale the case study into a public transport digital twin for Riga, composed corridor by corridor from independently versioned
SMDL models, with live bus-location feeds from the operator closing the loop between
the physical system and the model. Longer-term directions include behavioural validation against declared invariants and temporal properties over lifecycle events and
simulation-event traces, hybrid DEVS / DESS models, automated parameter calibration in the pipeline, application studies in manufacturing and energy systems, and a
SysML v2 front end exporting to SMDL through the standard API.
