Abstract—Energy-aware orchestration across geographically
distributed infrastructures is increasingly important as data
centers absorb growing Artificial Intelligence (AI) workloads.
However, existing approaches often exclude the energy cost
of automated decision-making from system-level sustainability
assessments. This paper presents an energy-aware agentic orchestration framework that treats Large Language Model (LLM)
reasoning as a measurable component of the control loop. We
compare single-shot tool calling, ReAct, and plan-and-execute
strategies on a multi-site Kubernetes testbed spanning two
European data centers and instrumented at layers ranging from
power distribution units to per-pod energy attribution. Using
ten natural-language orchestration intents with varying decision
complexity, we show that reasoning strategy and intent complexity strongly influence graphics processing unit (GPU) energy
consumption during orchestration decisions. ReAct and plan-andexecute generated executable tool calls across all evaluated intents
but required multiple LLM inferences, whereas the single-shot
configuration was less costly but non-actionable. Prefix caching
reduced mean ReAct GPU energy consumption by 29.4%. For
the evaluated lightweight workload, the infrastructure-energy
changes observed within the one-second measurement window
were insufficient to offset the measured GPU decision energy.
These findings demonstrate the importance of accounting for
reasoning overhead when assessing the sustainability of AI-native
orchestration and motivate energy-budgeted selection of agent
strategies.
Keywords—Green networking, Energy-aware orchestration,
Agentic AI, Large language models, Kubernetes, GPU energy

substantial: operators could request the most energy-efficient
site for a new workload in plain language, get causal explanations for sudden power spikes, or trigger graceful migrations

users with greener, more reliable services.
However, existing studies evaluate these agents primarily
by task accuracy and operational effectiveness, while generally
treating the energy consumed by the decision-making process
as negligible relative to the managed infrastructure. This
assumption may not hold when iterative reasoning executes
repeatedly on accelerator-based platforms. In energy-aware
orchestration, excluding this control-plane overhead can overestimate the sustainability benefits attributed to an automated
decision. Determining whether, and under which conditions,
the operational value of LLM-driven orchestration justifies its
additional energy cost therefore remains an important open
question [8], [9].

The method comprises four coupled components. The first
is an intent interpretation layer that receives the operator’s
natural-language request and routes it to a reasoning agent.
The second is a telemetry access layer, which exposes finegrained energy measurements of the infrastructure as callable
tools. The third is an actuation layer that exposes lifecycle
operations on target deployments as callable tools. The fourth
is the reasoning agent itself, whose strategy determines how
it orchestrates these tools to reach a decision. We describe
each component and then explain how they combine into the
end-to-end workflow shown in Figure 1.
Each intent is a free-form request that refers to one or
more sites and expresses a goal related to energy, performance,
or placement. Requests range from simple observations, such
as querying a site’s current power consumption, to complex
optimization goals involving multiple sites and constraints. We
categorize intents by complexity level based on the number
and nature of operations required to satisfy them. Level 1
intents are satisfiable by a single query or a single actuation.
Level 2 intents require a sequence of reads and writes with
an explicit dependency between them. Level 3 intents require
causal reasoning, hypothetical projection, or multi-constraint
optimization across sites. This taxonomy is not a property
of the natural language itself but of the decision process that
the intent demands. It lets us analyze how different reasoning
strategies behave as decision complexity grows.
The agent interacts with the infrastructure exclusively
through a typed tool interface. Two families of tools are
exposed. The first family grants read access to the infrastructure’s energy state. It includes tools to retrieve aggregate
site power, per-pod energy-consumption ranked by magnitude,
host-level power measured at the power distribution unit,
energy time series for trend analysis, and a cross-site comparison that enables evidence-based placement decisions. The
second family grants the orchestrator write access. It includes
tools to query deployment status, scale deployments, migrate
workloads between sites, and operate a deployment in both
sites simultaneously.
Each tool is described to the agent using a natural-language
signature that specifies its purpose and parameters. The agent
chooses which tools to call, in what order, and with what
arguments. This separation is important for the analysis that
follows. The telemetry tools are side-effect-free and can be
called repeatedly at low infrastructural cost. Actuation tools
modify the cluster’s live state and can only be evaluated by
executing them. The energy cost of the agent’s reasoning, as

The first is a single-shot tool-use baseline, in which the
model receives the intent together with the tool catalog and is
expected to emit the required tool calls in a single generation.
The second is an iterative strategy based on the ReAct
paradigm, in which the agent alternates between reasoning
steps and tool invocations. After each tool call, the agent
observes the result and decides whether to continue reasoning,
call another tool, or terminate with a final answer. This strategy
generates multiple inference requests per intent, and the number of requests increases with decision complexity. It offers
explicit self-correction at the cost of additional inferences.
The third is a plan-and-execute strategy, in which the agent
first emits a complete sequence of tool calls based solely
on the intent and the tool catalog, and then executes the
sequence without further reasoning. This strategy separates
planning from execution. In our implementation, it may require
additional model calls for plan normalization or final response
synthesis, but it does not perform the observation-reasoning
loop used by ReAct.
These strategies occupy distinct positions on the space defined by reasoning overhead and adaptivity. The experimental
evaluation in Section V measures where each strategy lands in
practice.
Figure 2 details the internal loop that the agent executes
when processing an intent. The agent first combines the intent
with a system prompt that describes the available tools and
the orchestration context. The resulting prompt is submitted to
the language model, which produces either a textual response,
one or more tool calls, or both. When the model emits tool
calls, it dispatches each call to the corresponding telemetry or
actuation tool. The tool result is appended to the conversation
and, if the strategy permits, fed back to the model for the next
reasoning step. The loop terminates when the model emits a
final textual answer, when a strategy-specific step budget is
exhausted, or when a tool returns a terminal condition.
A key observation is that the single-shot strategy performs
only the first inference and terminates after the initial response,
regardless of whether it emits valid tool calls.

Because the method treats reasoning cost as a measurable
quantity, we introduce an explicit attribution scheme that
separates three contributions to the total energy associated
with an intent. We quantify energy consumption across three
layers. We measure inference energy at the compute accelerator hosting the language model. Managed workload energy
is measured at the power distribution unit and attributed at
each site’s software layer. We estimate the energy impact of
each agent action from the change in infrastructure energy
consumption observed before and after the intervention over a
fixed measurement window.
For action intents, the observed short-horizon
infrastructure-energy
difference
is
computed
as
Esaved = (Pbefore − Pafter )∆t, where Pbefore and Pafter are
the mean cluster powers measured over one-second windows
immediately before and after the action, respectively, and
∆t = 1 second. We then define the net energy benefit as
N EB = Esaved − EGPU , where EGPU is the accelerator
energy consumed during the complete decision window. A
positive NEB indicates that the observed infrastructure-energy
reduction exceeded the decision energy within the evaluated
observation window. A negative value indicates that the
decision energy was not recovered within that window; it
does not establish whether the action could be energetically
amortized over a longer operational period.

IV.

E XPERIMENTAL T ESTBED

We evaluate the proposed method on a two-site Kubernetes
deployment spanning two European data centers, with the
reasoning agent hosted at a third geographic location. Figure 3
depicts the overall topology and the flow of telemetry and
orchestration traffic across the three sites. Table II summarizes
the benchmark intents used in the evaluation.
The agent and language model run on a workstation in
Brazil equipped with an Intel Xeon w3-2435 CPU (8 cores,
30 GiB RAM) and an NVIDIA RTX 4000 Ada GPU (20 GiB
VRAM, 130 W TDP). The GPU serves Qwen2.5-7B-Instruct
via vLLM 0.12.0, with the agent built on LangChain 1.2.0 and
LangGraph 1.0.5.

Fig. 3: Three-tier experimental topology.

The infrastructure consists of a single Kubernetes 1.28.15
cluster split across two sites connected by a Virtual Private
Network (VPN) tunnel: the primary site at ITAV (Aveiro,
Portugal) hosting 3 control plane and 3 worker nodes, and
a secondary compute site at UPV (Valencia, Spain) with 3
worker nodes. Control plane responsibilities reside at Aveiro,
while Valencia acts as a compute pool.
ITAV nodes run Ubuntu 24.04 on kernel 6.8 with containerd as the container runtime. UPV nodes run Ubuntu 22.04 on
kernel 5.15 with the same runtime. The cluster uses Flannel for
pod networking over VXLAN. The sites are reachable via private addresses: 10.255.40.0/24 for Aveiro and 172.21.32.0/24
for Valencia, and traffic between them traverses the VPN
tunnel that connects the two networks.
The workload under orchestration is a lightweight distributed web application deployed as a Kubernetes Deployment
with no explicit resource requests or limits. The agent scales,
migrates, and duplicates replicas of this deployment across
the two sites. Because the sites host no competing workloads
during the experiments, the application’s contribution to each
worker’s power envelope is small relative to the host’s baseline
consumption. This property is relevant to the interpretation of
the NEB reported in Section V.
Each worker node is instrumented to measure energy at
three levels, which together provide a layered view of consumption from the physical outlet down to the process. At the
physical layer, a PDU measures the bare-metal power drawn by
each host. At the operating system layer, Intel RAPL exposes
per-socket energy counters for the CPU package and its
memory controller. At the container orchestration layer, Kepler
runs as a per-node DaemonSet in a dedicated namespace and
attributes energy to individual pods and containers by combining RAPL counters with cgroup-level resource accounting. All
three data sources are published to a single InfluxDB instance
at one-second granularity, and the agent consumes them via
the Holosense platform, which exposes the underlying store
as a query API. The instrumentation covers both Aveiro and

Valencia workers symmetrically, enabling the agent to compare
the two sites on an equivalent basis.

The evaluation comprises two phases that differ only in
their prefix-cache configuration. Phase 1 uses the FP16 model
with vLLM’s prefix cache enabled, whereas Phase 2 uses
the same model and precision with the prefix cache disabled.
In each phase, all 10 benchmark intents are evaluated under
each of the three reasoning strategies, with five repetitions
per intent–strategy combination executed in randomized order.
Before every action intent, the cluster is automatically restored
to a canonical baseline in which Aveiro hosts one replica
and Valencia hosts none, thereby providing a comparable
initial placement state across runs. A 5-second cooldown is
inserted between consecutive runs to reduce short-term thermal
carryover on the GPU.
Every run produces a record that combines four sources
of evidence. The GPU energy trace is produced locally on
the agent host. The inference-level telemetry, which includes
prompt and generation token counts, as well as the prefix cache
hit rate, is obtained from vLLM’s Prometheus endpoint and
differenced over the run window. The cluster energy state,
sampled at both the PDU and Kepler layers, is retrieved from
Holosense immediately before and after any action intent. The
agent’s orchestration loop records the reasoning trace, which
captures the sequence of model inferences and tool invocations. The four sources are aligned on a common timeline
and persisted in a single CSV file per phase for subsequent
statistical analysis.

Statistical Validation. The assumptions of the standard
two-way ANOVA were not uniformly satisfied: homogeneity
of variance was violated for both ReAct and Tool Calling, and
residual normality was additionally violated for Tool Calling.
We therefore complemented the ANOVA with Welch’s t-test
and the non-parametric Kruskal-Wallis and Mann-Whitney U
tests, as reported in Table IV. For the ReAct and Tool Calling
configurations included in this analysis, intent complexity
exhibited the largest reported effect on GPU energy. Table V
further shows that complex intents consumed 4.5–8.3 times
more energy than simple intents across the evaluated cache
conditions.
Strategy-Dependent Effect of Prefix Caching. Figure 7
shows that enabling prefix caching reduced mean ReAct GPU

energy by 29.4%, with reductions of 59.5%, 32.8%, and 25.2%
for levels L1, L2, and L3, respectively. The pooled ANOVA
identified a significant cache effect, whereas Welch’s test was
marginal under heterogeneous variance; level-specific comparisons remained significant for L1 and L3. For Tool Calling, the
observed mean reduction was 9.3% and was not statistically
significant. This contrast is consistent with ReAct’s repeated
inference calls reusing a growing shared prefix, whereas the
single-shot configuration provides no accumulated prefix reuse
across inference steps.

C ONCLUDING R EMARKS

Energy-aware orchestration across geographically distributed infrastructures requires accounting for both the energy consumed by managed workloads and the GPU energy
cost of automated decision-making. This paper presented an
agentic framework that measures these components jointly,
introduced the NEB to compare short-horizon infrastructureenergy changes with GPU decision energy, and evaluated
three reasoning configurations on a real multi-site Kubernetes testbed. For the evaluated lightweight workload and
one-second attribution horizon, the observed infrastructureenergy differences were generally insufficient to offset the
energy consumed by LLM reasoning. ReAct and Plan & Execute produced actionable tool calls, whereas the single-shot
Tool Calling configuration did not; prefix caching reduced
mean ReAct GPU energy by 29.4%. These findings show
that the sustainability of agentic orchestration depends jointly
on actionability, reasoning strategy, workload magnitude, and
the period over which operational savings are evaluated. Future work will investigate larger and more energy-intensive
workloads, additional model families, adaptive strategies that
match reasoning depth to intent complexity, longer post-action
observation periods, and carbon-aware placement based on
renewable-energy availability.
