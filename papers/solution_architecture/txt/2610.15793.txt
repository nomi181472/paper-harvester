ABSTRACT

Write transactions

Multi-version concurrency control (MVCC) has been the dominant
concurrency protocol in modern database management systems
(DBMSs). However, cloud-native HTAP architectures shift many
of MVCC’s traditional advantages from the primary transaction
engine to the deployment architecture. Now, transactional and analytical processing are decoupled into loosely synchronized engines,
while cloud deployment primitives provide the workload isolation
required for this design. In this paper, we challenge the status quo,
arguing that single-version concurrency control (SVCC) is better
suited to cloud transaction processing than MVCC. Through a systematic analysis of MVCC’s limitations, we show that SVCC avoids
these shortcomings through a more lightweight and efficient design.
Beyond arguing for a lighter transaction processing, we use this
SVCC effort as a blueprint to advocate for a broader rethinking of
cloud-native architectures and to outline a research roadmap to
shape next-generation DBMSs.

The cloud already provides workload isolation at the deployment

MVCC has been the standard. As of 2026, the five top-ranked
database management systems (DBMSs) in the DB-Engines ranking – Oracle, MySQL, SQL Server, PostgreSQL, and MongoDB –
all implement multi-version concurrency control (MVCC). The appeal of MVCC over single-version concurrency control (SVCC) is
that readers never block writers, so one engine can serve hybrid
transactional and analytical processing (HTAP) workloads without
a separate analytical system. To gain that capability, DBMSs accept the substantial complexity and space overhead of maintaining
multiple versions.

fundamentally changes the design objectives of database systems.

The rise of multi-version storage. In the mid-1980s, the price of
magnetic disks declined to a point where data replication became
economically feasible. This shift in storage economics fundamentally changed the design space of database systems. With storage
capacity becoming less restrictive, DBMSs could now afford to
maintain multiple physical versions of the same logical record [12].
Multi-version concurrency control preserves older versions of tuples instead of overwriting them in place [15, 16, 56]. Consequently,
long-running read queries can access older tuple versions and are
not blocked by concurrent write transactions, significantly improving read-write concurrency and overall system performance. Moreover, empirical studies show that many applications tolerate isolation levels weaker than full serializability [23, 53]. MVCC naturally
supports such relaxed isolation models (e.g., snapshot isolation)
while reducing contention between readers and writers. These practical advantages, combined with improved storage affordability, led
to increased attention from database practitioners, which explains
why MVCC was adopted by most modern DBMSs.
Primary advantage: Non-blocking reads. The main benefit of
MVCC lies in its ability to decouple readers from writers. By preserving multiple physical versions of a tuple and associating them with
visibility metadata (e.g., version timestamps), long-running queries
can access a consistent snapshot of the database without conflicting
with concurrent update transactions. Another commonly cited advantage of MVCC is time-travel queries, which allow users to access
historical database states; however, this feature introduces substantial performance and storage overhead, leading PostgreSQL to
deprecate and eventually remove its time-travel support in v6.2 [5].
Such snapshot-based reads offer fresher views of the database than
offloading reads to replicas in cloud-native DBMS architectures,
which typically incur millisecond-scale replication lag [8, 25, 63].
In workloads where reads dominate, this leads to substantial improvements in throughput and tail latency stability.

MVCC: THE GOOD AND THE UGLY
2.2

The importance of managing concurrent access in DBMSs was
recognized early [24]. The key to that is the transaction abstraction, proposed by Jim Gray et. al. [34]. Jim Gray published many
more papers on transaction processing [11, 32, 33, 35, 36], which
emphasize the importance and benefits of transactions, and their
atomicity, isolation (i.e., serializability) and durability (ACID) properties [13, 14, 31].

2.1

The Ugly

With the prevalence of MVCC, why do we argue for SVCC in cloud
transaction processing? To answer, let us now discuss the trade-offs
database designers must accept in exchange for MVCC’s benefits.
Main trade-off: Complicated version management. The fundamental cost of MVCC is that maintaining multiple versions per tuple
requires additional machinery beyond the concurrency control algorithm (e.g., two-phase locking). Unlike SVCC, MVCC treats every
update as a version-creation event. This fundamentally changes
the responsibilities of the storage engine: Instead of managing a
single mutable state per key, the system must continuously create,
track, validate, and eventually reclaim multiple coexisting versions.
As a result, concurrency control is no longer isolated within the
primary protocol. It becomes tightly integrated with storage layout,
indexing data structures, and memory management. The complexity introduced by multi-versioning is therefore structural rather
than incidental, as we illustrate in Figure 2 and examine in the
following paragraphs.

The Good

The early prevalence of single-version design. Many DBMSs
soon followed and started integrating the transaction abstraction
into their system. In many early implementations, a transaction
overwrote the tuple value directly [40, 60], i.e., the system maintained only a single physical version of each record at any point
in time. This single-version design was both natural and practical.
Maintaining exactly one up-to-date copy of each tuple simplified
storage management, recovery, and buffer management, making
the approach straightforward to implement. Moreover, it aligned

systematic trade-offs. First, determining global visibility information requires coordination, introducing additional synchronization

Consequently, it is difficult to predict when garbage collection will
occur and how much overhead it will incur, making it a persistent
source of performance instability [19]. More importantly, garbage
collection is not merely an optimization but a correctness requirement in MVCC. Without it, version chains grow unbounded, index
entries accumulate, and storage consumption increases significantly
over time. Thus, multi-versioning introduces a permanent maintenance responsibility that does not exist in SVCC.
Overhead 3 : Tuple metadata and secondary index. Beyond
version storage and garbage collection, MVCC imposes persistent
space and runtime overheads due to tuple metadata and secondary
indexes. Each tuple must store visibility metadata (e.g., timestamps
and/or transaction IDs), leading to a typical header overhead of
16-32 bytes or more per record [7, 66]. For narrow schemas, this
metadata can constitute a substantial fraction of the tuple size, reducing effective storage capacity and cache efficiency. Secondary
index management is also more involved under MVCC, since both
index keys and tuple pointers may change across versions. Different design choices exhibit different performance trade-offs across
workloads, and index-only scans are generally infeasible unless

Overhead 1 : Version storage. Once updates produce new physical versions rather than overwriting in place, the system must
decide where and how to store these versions for subsequent access. Common approaches include undo-log-based version chains,
append-only delta stores, or separate version indexes [7, 43, 49, 66].
While these designs differ in locality and write amplification, none
avoids the fundamental cost of retaining multiple versions.
Overhead 1 a: Version storage complexity. Specifically, version storage introduces unavoidable indirection. A lookup no longer
focuses on only one record; instead, the engine must traverse the associated version chain to find a visible version. Under write-heavy
workloads, these chains can grow, degrading cache locality and
increasing pointer chasing costs. Alhomssi and Leis [7] shows that
preventing unbounded version accumulation in MVCC requires
a combination of carefully engineered mechanisms, including (1)
post-commit visibility validation to detect isolation conflicts, (2)
auxiliary data structures for managing old versions to enable efficient sweeping and also shorten version chains, and (3) in-row
storage of recent versions to improve performance; all of these
are non-trivial, significantly increasing system complexity. Studies
in [43, 66] further demonstrate that preventing excessive MVCC
version-chain growth is challenging and requires substantial modifications to the core execution engine.
Overhead 1 b: Version storage for large objects. Handling
non-inline attributes (e.g., large VARCHAR, TEXT, JSON, or BLOB
columns) further complicates version storage: The value of such
attributes is typically not stored inline with the tuple; instead, the
tuple contains only a pointer to separately allocated storage, introducing an additional level of indirection to access the actual
object [52, 66]. Under MVCC, the DBMS may allow multiple versions to share the same external object; hence, reference counters
are necessary to prevent excessive space consumption and ensure
that values are reclaimed only when no version references them.
This significantly complicates garbage collection, an already challenging component of MVCC as we will discuss next.

remain visible to active transactions, they cannot be reclaimed
immediately. MVCC, therefore, requires a garbage collection mechanism to determine when a version becomes globally unreachable

SVCC: THE BETTER FIT FOR THE CLOUD

Modern cloud data platforms comprise separate transactional and
analytical engines connected through a disaggregated storage layer.
In this section, we first identify the design principles that underpin
these platforms and reshape concurrency-control requirements.
We then show that these requirements render MVCC’s primary
overheads (c.f., Section 2.2) difficult to justify for the primary OLTP
engine, making SVCC the more natural choice for cloud OLTP.

3.1

New Design Principles in Cloud DBMSs

Modern cloud data platforms follow three design principles that
shape their high-level architecture and, in turn, their concurrencycontrol requirements.
Cost and resource efficiency as a necessity. In traditional onpremises deployments, databases ran on dedicated physical hardware, with the main goal being to maximize performance within
fixed resource constraints. In contrast, cloud computing follows
a pay-as-you-go model, where CPU, memory, storage, and network resources are billed based on usage. As a result, cost efficiency becomes a primary objective [27, 59, 61? ]; any mechanism
that consumes CPU time, memory, or storage must justify its cost.
Consequently, designs that eliminate unnecessary overhead while
maintaining high performance become increasingly attractive.

Deployment-level workload isolation. The elasticity of the
cloud also enables new architectural patterns. On-demand instance
provisioning [59, 64] and low-latency log-based replication [37,
39, 47] make it easy to run multiple instances of the same system.
Instead of serving all workloads within a single engine, operators
can deploy a dedicated instance for transaction processing and
offload long-running analytical queries to replica instances or a separate engine. Workload isolation is thus provided at the deployment
level rather than by the concurrency-control mechanism within an
engine.
The single-writer architecture. In line with the principle of workload isolation, several major cloud DBMS vendors have adopted a
single-writer architecture in their cloud OLTP systems, with examples including Amazon Aurora [63], Microsoft Socrates [8], Huawei
Taurus [25], and Alibaba PolarDB [65]. In this architecture, one
primary instance handles all writes while multiple replicas act as
failover [2, 71]. The primary writer can therefore be optimized
for short OLTP transactions, while read-intensive and analytical
workloads execute elsewhere. The single-writer architecture thus
reinforces the broader shift from engine-level to deployment-level
workload isolation.
Implications for concurrency control. As discussed in Section 2,
MVCC was designed to isolate different workloads within a single
engine. These MVCC features were necessary when one database
instance had to handle heterogeneous workloads. In cloud-native
DBMSs, however, workload isolation can be achieved through replicas and elastic instances, with replica freshness typically within
milliseconds [8, 25, 63]. Consequently, the primary OLTP engine
no longer needs to execute long-running queries or provide crossworkload isolation. Its concurrency-control requirements are therefore substantially narrower. The relevant question is no longer
how to support heterogeneous workloads within one engine, but
which concurrency-control scheme best serves a dedicated OLTP
writer. Given these architectural changes, is MVCC still the right
concurrency control mechanism for the primary OLTP engine?

Complexity Evaluation

Setup. In this section, we use our own implementation experience
as a concrete proxy to represent complexity. We use LeanStore [45],
a modern storage engine that supports high throughput with 𝜇sscale commit latency [50], and implement both protocols:
• SVCC: We implement traditional two-phase locking (2PL) with
Wait-Die deadlock prevention. We use an open-sourced wait-die
lock implementation combined with Intel TBB concurrent hash
tables as an in-memory wait-die lock manager.
• MVCC: We implement Hyper-style MVCC [49]. In this protocol,
a transaction modifies tuples in place, buffers their before-images
in an undo log, and, at commit time, validates the writes of concurrently committed transactions against its read predicates.

Why SVCC Fits Cloud OLTP

The cloud deployment model removes a principal motivation for
MVCC in the primary OLTP engine: supporting heterogeneous
workloads and long-running snapshots within a single engine. Once
these workloads are isolated in dedicated analytical engines, the
primary writer can focus on transactions. Under these narrower
requirements, SVCC is not only viable but also a more natural
foundation for cloud OLTP.
SVCC is cheaper at every level. As discussed in Section 2.2,
MVCC introduces substantial engine-level complexity, resulting in
runtime overheads that are not present in single-version designs. In
particular, MVCC requires intricate mechanisms to manage multiple
versions of both standard data types (e.g., numeric fields) and large
objects. In contrast, SVCC avoids this additional machinery and
relies only on the underlying concurrency control scheme, such as
2PL. Moreover, SVCC preserves a simple and intuitive model that
remains consistent across all layers of the system.

primary instance now adopts SVCC as its concurrency control protocol (c.f., Figure 3). The lightweight design of SVCC intentionally
scopes the primary engine to short transactions, which is the typical assumption for OLTP workloads. A transaction may, however,

BEYOND SVCC: RETHINKING CLOUD HTAP

Our experience with SVCC suggests that many of the complexities in modern cloud-native DBMSs arise from legacy design assumptions rooted in traditional DBMS architectures. We therefore
believe this is the time to step back and consider the broader system. Through this looking glass, we believe that the community
has the opportunity to identify a leaner and more efficient architectural blueprint for cloud-native DBMSs. Many existing proposals [21, 26, 37, 55, 65, 67, 70] preserve these legacy assumptions,
resulting in unnecessary complexity and overhead across the stack.
Below, we outline several research directions that we believe are
key to building the next generation of cloud-native DBMSs.

Direction #1 : HTAP synchronization. In traditional on-premise
DBMSs, analytical queries rely on MVCC snapshots to achieve nearreal-time visibility, as discussed in Section 2. In cloud-native HTAP
architectures, however, analytical snapshots are maintained outside
the transactional engine, i.e., in storage layer – Figure 3 (middle),
making snapshot synchronization latency a primary optimization
objective. Recent approaches reduce this lag by exposing recent
updates through row-oriented page services [3] or log-caching
layers [47]. Both approaches face the same issue: when the transactional engine produces a large volume of updates between the last
synchronization point and the analytical snapshot timestamp, the
analytical engine must merge all accumulated logs before answering queries, potentially negating the benefits of engines such as
DuckDB or Raydon if the log gap is large (e.g., GBs). We therefore believe that efficient HTAP synchronization remains an open research
problem. One direction is partitioning the log (and page) service by
analytical predicates, allowing analytical engines to retrieve only
relevant partitions and reducing unnecessary data movement.
Direction #2 : SSD-based object stores. Complementing softwarelevel log partitioning, redesigning the underlying cloud object stores
(e.g., Amazon S3) offers a hardware-aware path to reducing HTAP
synchronization latency. Contemporary cloud object stores are inadequate not only for cloud-native HTAP systems but also for database
workloads more broadly. This limitation stems from the fact that
today’s object stores largely inherit architectures designed nearly
two decades ago and have not been fundamentally rearchitected to
take advantage of modern hardware. Recent developments, such
as S3 Express, reflect the growing demand for high-performance
object storage; however, these remain incremental enhancements
to the existing object-store abstraction and still incur access latencies that are too high for database workloads. We envision new
SSD-based object-store primitives designed from the ground up
for cloud-native DBMSs, preserving the scalability and durability
properties while providing substantially lower access latency.
Direction #3 : Stateless page service. Another direction for optimizing cloud-native HTAP architectures is to make page materialization truly elastic. As analytical workloads become more
intensive, the page service must scale elastically to sustain high
request throughput. This, in turn, requires page service instances
to join and leave as fast as possible. However, existing cloud page
services (e.g., Databricks/Neon LTAP [3]) maintain dirty pages and
asynchronously flush them to object storage, requiring coordination across page service instances. We propose a truly stateless page
service based on the log-is-the-data paradigm. Durability, replication, and persistence are handled entirely by the log service, while
buffer evictions and checkpointing append pages directly to the
log service. As a result, page service instances become transient
execution units that can be created, assigned to table predicates, and
removed independently; this also enables page service deployment
on serverless infrastructure. Thus, page materialization becomes a
fully elastic compute layer rather than a stateful storage.

an important open challenge. A promising starting point is to adapt
the per-page mapping table introduced by Umbra [30].
Summary. Our work is a first step toward the broader vision of
how rethinking system components can reduce complexity while
improving overall robustness. With this paper, we hope to inspire
further research on re-architecting the cloud database stack and
encourages a broader community effort to build a leaner, more
robust foundation for the next generation of cloud databases.
