Abstract
Large language model (LLM) agents are moving from chat interfaces into infrastructure operations, where
they read telemetry, call tools, generate and execute code, and change the state of production Kubernetes
clusters. This collapses a boundary that conventional cloud-native security assumes: the boundary
between data and control. Content that an agent merely reads—a log line, a ticket, a tool description—can
redirect what it does. This paper argues that the model must not be treated as a security boundary and
that agent safety on Kubernetes is therefore an infrastructure problem: every guarantee must continue to
hold under the assumption that the agent is fully compromised by prompt injection. We contribute (i) a
threat model and ten-class threat taxonomy for agents operating on and within Kubernetes, aligned with
emerging OWASP guidance for agentic applications; (ii) nine design principles, centered on complete
mediation at the tool boundary and on breaking the combination of untrusted input, sensitive access, and
external egress; (iii) a seven-layer defense-in-depth framework that maps each principle to native or widely
adopted Kubernetes mechanisms—workload identity, RBAC and ValidatingAdmissionPolicy, gVisor/Kata
sandboxing via the SIG Apps Agent Sandbox project, FQDN-aware egress policy, an agent/MCP gateway
with policy-as-code over tool arguments, and eBPF runtime enforcement; (iv) a reference architecture with
concrete policy artifacts and per-layer bindings for Amazon EKS, Azure Kubernetes Service, and Google
Kubernetes Engine; and (v) a qualitative evaluation comprising a threat–control coverage matrix and four
attack walkthroughs, with a proposed empirical methodology. We report no measured attack-success
or overhead figures; instead we identify residual risks and the measurements needed to validate the
framework.
Keywords: AI agents, agentic AI, Kubernetes, cloud-native security, prompt injection, Model Context
Protocol, sandboxing, policy as code, eBPF, zero trust, least privilege, Amazon EKS, Azure AKS, Google
GKE

Introduction

Operations teams are beginning to delegate real work to LLM-based agents: triaging alerts, reading logs
and metrics, proposing and applying remediations, opening pull requests against GitOps repositories, and

generating ad hoc scripts to diagnose problems. Kubernetes is a natural home for these agents. It is where
the workloads they manage already run, its declarative API is well suited to automated reasoning, and
an ecosystem of agent frameworks, protocols, and gateways has grown around it, including the Model
Context Protocol (MCP) [1], the Agent2Agent (A2A) protocol, the CNCF kagent project [2], and the Linux
Foundation agentgateway project [3].
An agent that can act on a cluster is, from a security standpoint, a new kind of principal. Unlike a controller,
its behavior is not fixed by code that can be reviewed: it is a function of a model, a prompt, and every
piece of content that enters its context window during a task. Unlike a human operator, it does not reliably
distinguish instructions from data. Indirect prompt injection—adversarial instructions embedded in content
the agent retrieves rather than in the user’s request—has been demonstrated against deployed LLM-integrated
applications [4], and benchmark studies show that tool-using agents remain susceptible even with model-level
defenses [5]. In the MCP ecosystem specifically, tool poisoning—hidden instructions in tool descriptions,
schemas, or return values—has been demonstrated against widely used clients [6, 7].
For a Kubernetes operator this has a sharp consequence. Content that an agent merely reads—a container log
line written by an attacker-controlled workload, an annotation on a resource, a field in an incident ticket, a
tool description served by a third-party MCP server—can become a command that the agent then executes
with its own credentials. The classical separation between the data plane and the control plane, on which
much of cloud-native security rests, does not survive contact with an agent unless the platform reconstructs it.
This paper takes the position that the model is not a security boundary. Model alignment, system prompts,
and input classifiers reduce the probability of misbehavior, but they offer no guarantee, and their failure modes
are adversarially discoverable. Agent security on Kubernetes must therefore be built the way multi-tenant
platform security is built: by assuming the workload is hostile and constraining what it can reach, do, and
exfiltrate, regardless of what it “intends.” This framing aligns with the classical principles of least privilege
and complete mediation [8] and with the confused-deputy problem [9], both of which return with new force
when the deputy is an LLM.

Scope and Non-Goals

We focus on agents used for infrastructure and platform operations—the setting in which agent actions have
the largest blast radius. We do not address model training-time attacks (data or weight poisoning), the safety
of model outputs presented to humans, or hardening of the inference service itself. We treat the model
provider as reachable over the network and outside the trust boundary of the cluster. The policy artifacts in
this paper are illustrative; API versions of fast-moving projects should be checked against current releases.

2

Background

2.1

LLM Agents

An LLM agent iterates a loop: it receives a goal, reasons over its context, selects a tool and arguments,
observes the result, and repeats until it decides the goal is met [12]. Three properties matter for security. First,
tool results re-enter the context, so data returned by any tool can influence subsequent tool choices. Second,
tool selection is open-ended: the agent chooses which capability to invoke and with what arguments at run
time. Third, agents increasingly carry memory across sessions—vector stores, scratchpads, or summaries—so
a single injection can persist.

2.2

Agent Protocols

MCP standardizes how an agent (client) discovers and invokes tools, resources, and prompts exposed by
servers [1]. Tool descriptions and schemas are natural-language metadata that the model reads to decide
when and how to call a tool. Because this metadata is consumed by the model rather than by deterministic
code, it is an injection surface in its own right [6, 13, 14]. A2A standardizes agent-to-agent messaging and
capability discovery. Both protocols are now commonly fronted by gateways that terminate transport security,
authenticate callers, and apply per-tool authorization [3].

2.3

Kubernetes Security Primitives

Kubernetes provides a rich but fragmented set of controls: ServiceAccounts and projected, audience-bound
tokens for workload identity; RBAC for coarse authorization by verb and resource; admission control,
including the in-process, CEL-based ValidatingAdmissionPolicy (VAP) [15], for fine-grained validation
of object content; Pod Security Standards; RuntimeClass for selecting alternative container runtimes
such as gVisor [16] or Kata Containers [17]; NetworkPolicy and CNI-specific extensions such as Cilium’s
FQDN-aware policies [18]; and API-server audit logging [19]. eBPF-based tools such as Tetragon [20]
and Falco [21] add kernel-level observation and enforcement. Managed Kubernetes services add workloadidentity federation that maps ServiceAccounts to short-lived cloud credentials: EKS Pod Identity and IAM
Roles for Service Accounts (IRSA) on AWS [22], Microsoft Entra Workload ID on AKS [23], and Workload
Identity Federation for GKE [24]. They also increasingly offer managed sandbox runtimes and FQDN-aware
egress policy, which we compare in Section 6.
None of these mechanisms was designed with agents in mind, and none, alone, addresses the data/control
collapse described above. The contribution of this paper is to compose them, together with agent-specific
components, into a coherent posture.

Threat Model

3.1

System Model

Securing AI Agents on Kubernetes

We consider an operations agent deployed as a workload in a Kubernetes cluster (or in a management cluster
that administers workload clusters). The agent receives tasks from humans (chat, tickets) or from automation
(alerts). It reasons using a hosted or self-hosted model, calls tools exposed over MCP (Kubernetes API reads,
log and metrics queries, GitOps operations, cloud-provider APIs), and may request code-execution sandboxes
in which it runs generated scripts. It may store memory in a vector database, and it may delegate sub-tasks to
other agents over A2A.

3.2

Assets

The assets at risk are: (a) the integrity and availability of cluster workloads and configuration; (b) credentials
reachable from the agent or its tools (ServiceAccount tokens, cloud credentials, API keys); (c) confidential
data visible through tools (logs, configuration, customer data in telemetry); (d) the integrity of the agent’s
memory; and (e) the audit trail that attributes actions to principals.

3.3

Adversary Capabilities

We consider five adversary capabilities, which may combine:
A1 Content injection. The adversary controls some content the agent will read: a log line emitted by
a workload they control, an annotation or label, a ticket body, a web page, a document in a retrieval
corpus.
A2 Malicious or compromised tool server. The adversary operates an MCP server the agent connects to,
or compromises an existing one, and can change its tool metadata or responses at any time.
A3 Malicious generated code. As a consequence of A1 or A2, code the agent writes and executes is
attacker-influenced.
A4 Low-privilege insider. A user permitted to make requests of the agent attempts to use it to exceed
their own authority.
A5 Benign failure. No adversary is present, but model error, hallucination, or a feedback loop produces
harmful actions.
We assume the adversary can fully control the agent’s subsequent tool choices and arguments once injection
succeeds. This is the central modeling choice: we grant the attacker the agent.

3.4

Trust Assumptions

We trust the Kubernetes control plane, the node kernel and container runtime (subject to the isolation strength
of the selected RuntimeClass), the policy engines, the gateway, and the identity provider. We do not trust
the model, the agent process, its context, retrieved content, tool metadata from servers outside an approved
registry, or generated code.

3.6

The Lethal Combination

A useful lens is the observation, popularized by Willison [30] and formalized as the “Agents Rule of Two” by
Meta [31], that serious harm typically requires an agent session to combine three properties at once: exposure
to untrusted input, access to sensitive data or privileged actions, and the ability to communicate externally or
change state. Removing any one of the three for a given session sharply bounds the damage of a successful
injection. Kubernetes is unusually well suited to enforcing this structurally, because each property maps
onto a controllable resource: content sources onto tool authorization, sensitive access onto RBAC and secret
placement, and external communication onto egress policy.

4

Design Principles

P1 – The model is not a security boundary. Every control must hold if the agent is fully adversary-controlled.
Prompt-level defenses are hygiene, not guarantees.
P2 – Complete mediation at the tool boundary. Every action the agent takes leaves the agent process
through a mediated channel—the gateway or the Kubernetes API server—where it is authenticated, authorized
against its arguments, and logged. There is no unmediated path.
P3 – Least agency. Grant the minimum set of tools, verbs, resources, and namespaces needed for the task
class, and prefer read-only capabilities. Agency should be scoped per task, not per agent product.

P4 – Delegated, attributable identity. Each agent has its own workload identity; actions on behalf of a user

P8 – Observable and attributable by construction. Correlate each request, model call, tool call, API-server
action, and approval in a single trace.
P9 – Bounded autonomy. Rate-limit actions, cap budgets, and trip circuit breakers; autonomy is graduated
by environment and by action risk.

A Seven-Layer Defense-in-Depth Framework

Fig. 1 summarizes the framework. Layers L1–L7 are technical controls; a cross-cutting governance layer (G)
covers approval, autonomy tiers, and budgets.

5.1

L1: Identity

Per-agent workload identity. Every agent, and every class of tool server, runs under its own ServiceAccount.
The default ServiceAccount is never used, and automountServiceAccountToken is disabled on any
pod that does not call the Kubernetes API, notably on code-execution sandboxes. Where tokens are needed,
projected tokens should be audience-bound and short-lived. Cloud access uses workload identity—EKS Pod
Identity or IRSA [22], Microsoft Entra Workload ID [23], or Workload Identity Federation for GKE [24]—
rather than static keys, so credentials are scoped, rotated, and attributable in the provider’s audit trail (AWS
CloudTrail, Azure Monitor and Entra sign-in logs, or Cloud Audit Logs). For mesh-wide identity across
clusters and non-Kubernetes services, SPIFFE/SPIRE [32] provides attestable workload identities usable for
mutual TLS.
Delegated user authority. To address the confused-deputy threat (T3), an agent acting on behalf of a user

should present the user’s delegated authority, not only its own. OAuth 2.0 Token Exchange [33] allows the

that restricts which users or groups may be impersonated, so that RBAC is evaluated against the human’s
permissions and the audit log records both identities.

5.2

L2: Authorization and Admission

RBAC. RBAC answers which verbs on which resources in which namespaces. Agents receive namespaced Roles, never ClusterRoles with write verbs. Read-only roles (get, list, watch) are the default;
pods/exec, secrets, serviceaccounts/token, and RBAC objects are excluded, since each allows a direct path to privilege escalation.
Admission as an agent guardrail. RBAC cannot express constraints on object content: it cannot forbid
scaling to zero while permitting scaling, or forbid an agent from editing objects in control-plane namespaces
while permitting edits elsewhere. ValidatingAdmissionPolicy [15] fills this gap with in-process CEL expressions that can be scoped to requests from agent identities via matchConditions. Listing 1 shows a policy
that applies only to ServiceAccounts in the agents namespace. Because it is enforced by the API server, it
holds even if the agent bypasses the gateway and calls the API directly with a stolen token—a property that
tool-layer controls alone cannot provide. Kyverno or OPA Gatekeeper can express equivalent rules where
richer policy libraries are needed.
Pod Security. Namespaces that host agents and sandboxes enforce the restricted Pod Security Standard,
which prevents privileged pods, host namespaces, and hostPath mounts—the most direct paths from a
compromised pod to the node.

5.3

L3: Execution Isolation

Agents that execute generated code (T5) need stronger isolation than a standard container, because containers
share the host kernel and a single kernel vulnerability is sufficient for escape. Two mature options are available
through RuntimeClass: gVisor [16], which interposes a user-space kernel that services system calls on
behalf of the container and thereby shrinks the host-kernel surface, at a cost in syscall-heavy workloads [34];
and Kata Containers [17], which runs each pod in a lightweight virtual machine with its own guest kernel.
The Kubernetes SIG Apps Agent Sandbox project [35] provides a Sandbox custom resource and controller
for exactly this use case: isolated, stateful, singleton workloads with a stable identity, intended among other
things for running untrusted, LLM-generated code. Its extensions add templates, claims, and pre-warmed
pools to reduce start-up latency, which matters because per-session sandboxes are only practical if they
are fast to obtain. Listing 2 shows a hardened sandbox: kernel-isolated runtime, no ServiceAccount token,
non-root, read-only root filesystem, all capabilities dropped, a digest-pinned image, and resource limits.
Sandboxes should be ephemeral and per session; a sandbox that persists across users becomes a channel for
cross-session contamination (T7). They are placed in a dedicated namespace with no RBAC bindings, and
their network access is governed by L4.

5.4

L4: Network

Network policy is the most direct way to break the exfiltration leg of the lethal combination (T6). Agent and
sandbox namespaces start from default-deny for both ingress and egress. Egress is then allowed only to cluster
DNS, to the agent gateway, and to an explicit allowlist of external hostnames—typically the model endpoint.
Because external services are addressed by name and their IP addresses change, IP-based NetworkPolicy is
insufficient; FQDN-aware policies, as provided by Cilium [18], are required. Listing 3 permits an agent to
reach only DNS, the gateway, and a single model endpoint. Sandboxes typically receive no external egress at
all; when a task genuinely needs internet access, egress should be through an inspecting proxy and should
trigger the approval path (Section 5.8).
The same intent is expressed with provider-native resources on AKS and GKE (Section 6.2, Listing 6). Note
that the agent pod has no route to the Kubernetes API server in this policy. All cluster actions go through tool
servers behind the gateway, which hold the necessary credentials. This realizes P2: the agent’s only path to
state change is mediated. East–west traffic between gateway, tool servers, and agents should use mutual TLS,
either from a service mesh or from SPIFFE-issued certificates.

5.5

L5: Tool Mediation

The tool boundary is where agent intent becomes action, and it is the most important point of control. We
place an agent gateway between agents and all tool servers (MCP), peer agents (A2A), and, optionally, model
endpoints. agentgateway [3], now a Linux Foundation project, is one open-source realization; it supports
MCP and A2A, includes MCP- and A2A-aware authorization, and integrates with Kubernetes through the
Gateway API via kgateway. The gateway performs five functions.
(1) Authentication. It authenticates the calling agent by workload identity and the originating user by token,
and performs the token exchange described in Section 5.1.
(2) Authorization over tool and arguments. Per-tool allow lists are necessary but insufficient (T2): the
harm in scale(deployment, 0) lies in the argument, not the tool name. The gateway therefore sends
a structured decision request—agent, user, tool, arguments, session attributes—to a policy engine such as
OPA [36] or Cedar. Listing 4 shows a Rego policy that permits read tools within an agent’s namespaces,
permits GitOps pull requests only to approved repositories, requires human approval for disruptive actions in
production, and denies scale-to-zero outright. Admission policy (L2) enforces overlapping constraints at the
API server; the duplication is intentional, since L5 can block earlier with richer context while L2 cannot be
bypassed.
(3) Supply-chain control for tools (T4). Tool servers are admitted only from an internal registry, with images
signed and verified at admission (e.g., Sigstore/cosign [37] with a Kyverno or policy-controller rule). Tool
descriptions and schemas are pinned: the gateway records a hash of each tool’s metadata at approval time and

5.6

L6: Data and Secrets

Secrets never enter the context. Credentials are held by tool servers, fetched server-side from a secret
manager (e.g., via the External Secrets Operator or Vault), and never returned in tool output. An agent that
never sees a secret cannot be induced to leak it, which removes an entire class of exfiltration regardless of
egress policy.
Redaction at the source. Log and event tools redact tokens, keys, and personal data before returning results,
both to protect confidentiality and to avoid feeding sensitive material to an external model.

5.7

L7: Runtime Detection and Response

Preventive layers will be misconfigured or bypassed; detection bounds the dwell time.
Kernel-level enforcement. eBPF tools observe agent and sandbox pods at the system-call level. Tetragon [20]
can both detect and enforce, for example terminating a process that attempts to open a ServiceAccount token
path inside a sandbox that should have none (Listing 5). Falco [21] offers a broad rule set for unexpected
shells, network connections, and file writes.
Control-plane analytics. API-server audit logs [19], filtered to agent identities, are baselined: new verbs,
new namespaces, or abnormal call rates raise alerts. Gateway decision logs supply denied-call spikes, which
are a strong signal of an injection attempt in progress.
Kill switch. A single, rehearsed action must disable an agent: revoke or rotate its ServiceAccount and
workload-identity bindings, scale it to zero, apply a quarantine network policy, and invalidate its gateway
sessions. Because the agent’s only paths are mediated (P2), revoking identity at L1 and L5 is sufficient to
stop it even if its pod persists.

5.8

G: Governance—Approval, Autonomy, and Budgets

Human approval. Approval-gated calls are suspended at the gateway and surfaced to a human with the full
context: requester, rationale, exact arguments, and a dry-run diff. Approval is bound to the specific call (by
hash of tool and arguments) and expires, so it cannot be replayed for a different action.
Autonomy tiers. Autonomy is graduated by environment (Table 2). An agent may be fully autonomous for
reads in production and for most actions in development, while production mutations require approval or
GitOps review.

Budgets and circuit breakers. Each agent and session has budgets for tool calls, mutations per time window,

Reference Architecture on Managed Kubernetes: EKS, AKS, and GKE

Fig. 2 shows a reference deployment. Its core—namespaces, RBAC, admission policy, the agent gateway
and its policy engine, GitOps, and eBPF runtime enforcement—is provider-neutral and runs unchanged on

bind to the provider: cloud workload identity, the kernel-isolated sandbox runtime, FQDN-aware egress

Provider Bindings

Table 3 maps each framework layer onto the native services of EKS, AKS, and GKE. Three differences

Sandboxing is the largest gap. GKE offers the most complete managed path: GKE Agent Sandbox
is a managed add-on built on the open-source Agent Sandbox controller, uses gVisor for kernel-level
isolation, and adds pre-warmed pools for sub-second provisioning, a claim-based request model, and
default-deny networking for sandboxes [25]. AKS provides managed Kata-based Pod Sandboxing, in
which each pod runs in a lightweight VM with its own guest kernel, selected with runtimeClassName:

project documents its use on AKS [27]. On EKS there is no managed sandbox runtime at the time of writing,
so operators install gVisor or Kata themselves on dedicated node groups and run the open-source controller.
That is feasible but places the isolation runtime, and its patching, inside the operator’s responsibility.
FQDN egress is native on AKS and GKE, not on EKS. On AKS, FQDN filtering is part of Advanced
Container Networking Services (ACNS) and requires Azure CNI powered by Cilium; it is a paid add-on,
and Microsoft notes possible degradation above roughly 1,000 requests per second per pod [28]. On GKE,
the FQDNNetworkPolicy resource requires GKE Dataplane V2 and caps each FQDN at 50 resolved
addresses [29]; Listing 6 expresses the intent of Listing 3. On EKS, the VPC CNI’s network-policy support is
not FQDN-aware, so the egress allowlist of Section 5.4 requires Cilium (in chaining or replacement mode) or
a forced egress proxy. On all three, private connectivity to the model endpoint (PrivateLink, Private Endpoint,
or Private Service Connect) lets the allowlist name a private address rather than a public one, and on GKE,
VPC Service Controls adds a perimeter around Vertex AI and other Google APIs that limits where data can
flow even with valid credentials.
Identity semantics differ in detail. All three federate a Kubernetes ServiceAccount to a cloud principal
without static keys, which satisfies L1. They differ in where the binding is declared—an EKS Pod Identity
association or IRSA role trust policy, an Entra federated identity credential, or a Google IAM policy binding
on the Kubernetes principal—and therefore in which team controls it. In every case the binding should
be owned by the platform team and managed declaratively (for example with Crossplane or Terraform),
so that an agent with write access to its own namespace cannot widen its cloud permissions by editing
ServiceAccount annotations.

Evaluation

We evaluate the framework qualitatively, through threat coverage and adversarial walkthroughs, and we
propose a methodology for empirical validation. We do not report attack-success rates, latency, or cost
overheads; those require the experiments described in Section 7.4.

7.1

Threat–Control Coverage

Table 4 maps each threat to the layers that provide primary (•) or supporting (◦) mitigation. Two properties
are worth noting. First, every threat has at least two mitigating layers, and for every threat at least one primary
control is enforced outside the agent process; no threat relies solely on model behavior (P1). Second, the
injection-driven threats (T1, T2, T6) are each covered by a preventive control at the tool boundary (L5) and
an independent control at a different enforcement point (L2 at the API server, L4 in the CNI), so a single
misconfiguration does not lead to harm.

Attack Walkthroughs

S1: Injection through a log line (T1, T2). An attacker who controls a workload in prod-payments
writes a log line instructing any reading agent to “free capacity by scaling checkout to zero.” In a naive
deployment with a broadly privileged agent, this succeeds if the model follows the instruction. In the reference
architecture, the log is read by the quarantined reader, whose output reaches the planner as quoted data (L6);
if the planner nonetheless proposes k8s_scale with replicas: 0, the gateway policy denies it (L5,
Listing 4); were the gateway misconfigured, the VAP rejects the request at the API server (L2, Listing 1); and
the cluster of denials raises an alert (L7). The attack must defeat three independent enforcement points to
cause harm.
S2: Tool poisoning with exfiltration (T4, T6). A third-party MCP server, approved months earlier, updates
its tool description to instruct the agent to read a configuration secret and include it in a parameter of the
server’s own tool. The gateway detects that the server’s tool-metadata hash has changed and quarantines
it pending review (L5). Independently, the agent cannot read secrets—no tool returns them and no RBAC
grants them (L2, L6)—and the server’s pod, under default-deny egress, cannot reach an arbitrary external
host (L4). The combination of untrusted input and external communication exists in the compromised server,
but the sensitive-access leg is absent.
S3: Malicious generated code (T5). Injected content causes the agent to generate a script that attempts to
read a ServiceAccount token and then exploit a kernel vulnerability. The sandbox has no token mounted
(L1); Tetragon terminates the process on access to the token path (L7, Listing 5); the gVisor or Kata runtime
interposes a separate kernel boundary, so a host-kernel exploit must also defeat the user-space or guest kernel
(L3); and with no egress, the sandbox cannot fetch a second-stage payload or exfiltrate results (L4). The
residual risk is a vulnerability in the isolation runtime itself.
S4: Runaway remediation (T8). With no adversary, the agent repeatedly restarts a deployment whose
failures are caused by a downstream database, worsening the incident. Per-object mutation budgets and the
circuit breaker (G) stop the loop after a bounded number of attempts and escalate to a human; gateway rate
limits (L5) cap the rate in the meantime; and audit-log baselines flag the burst (L7).

7.3

Residual Risk

Several risks are reduced but not eliminated.
• Harmful but policy-compliant actions. Policy can forbid known-bad arguments; it cannot judge
whether a permitted action is wise. A restart that is allowed may still be wrong. Approval gates and
GitOps review move this judgment to humans, at the cost of latency and of approval fatigue.
• Integrity attacks within scope. An injected agent can still produce misleading summaries or propose
subtly harmful pull requests. Review quality, not infrastructure, is the control.
• Exfiltration through the model channel. The model endpoint is, by necessity, an allowed egress
destination. Sensitive data in the context is sent to the model provider by design; contractual and
data-residency controls apply, and L6 minimizes what enters the context.
• Isolation-runtime and policy-engine vulnerabilities. These components join the trusted computing
base.
• Policy drift. The layered design produces many policies across tools; their consistency must itself be
tested.

7.4

Proposed Methodology for Empirical Validation

To move from qualitative to quantitative claims, we propose the following experiments, which we leave to
future work.
1. Kubernetes-native injection benchmark. Adapt the structure of AgentDojo [5]—paired user tasks
and injection tasks in a realistic environment—to a cluster environment, with injections placed in logs,
events, annotations, ConfigMaps, tickets, and MCP tool metadata. Measure benign task utility and
targeted attack success rate (ASR) under ablations: no controls; prompt-level defenses only; each layer
added in isolation; and the full stack.
2. Bypass testing. For each enforcement point, disable the layers above it and confirm the lower layer
alone prevents the harmful outcome, verifying the independence claimed in Table 4.
3. Overhead. Measure added latency per tool call at the gateway and policy engine, sandbox acquisition
time with and without warm pools, and syscall-heavy workload slowdown under gVisor and Kata,
building on prior characterizations [34].
4. Operator burden. Measure approval volume and approval latency per incident under each autonomy
tier, as a proxy for approval fatigue.

8

Discussion

Why not rely on better models? Model-level robustness to injection is improving, and design-level defenses
such as CaMeL [38] show that strong guarantees are possible when control and data flow are separated.
Infrastructure controls are complementary: they bound the damage of the residual failures, they apply
uniformly across models and frameworks, and they are already familiar to platform teams. A platform that
assumes compromise remains safe when the model is swapped.
Utility trade-offs. Every layer constrains the agent. Default-deny egress breaks tools that fetch documentation; approval gates slow remediation; quarantined readers lose nuance. We view the autonomy tiers as the
primary dial: organizations can begin with observe-and-propose in production and expand autonomy per
action class as evidence accumulates.
Agents as tenants. The framework is, in effect, multi-tenant platform engineering with the agent as the
untrusted tenant. Much existing practice—namespace isolation, admission control, network segmentation,
runtime detection—transfers directly. What is new is the tool boundary, where authorization must consider
arguments and provenance, and the need to treat natural-language metadata as code.
Standardization gaps. Several needed primitives lack standards today: a common schema for tool-call
authorization requests, signed and versioned tool metadata in MCP, a standard for propagating delegated user
identity through multi-agent chains, and conventions for tracing agent reasoning across OpenTelemetry spans.
Progress on these would make the controls here portable across gateways and frameworks.
Limitations. This work is a framework and design study. Its evaluation is analytical rather than empirical; the
coverage matrix reflects our assessment rather than measurement; and the artifacts, while concrete, have not
been subjected to a red-team exercise reported here. The ecosystem is moving quickly, and specific projects
or API versions cited may change.

Related Work

Prompt injection. Greshake et al. introduced indirect prompt injection against LLM-integrated applications [4]. AgentDojo provides a dynamic benchmark of attacks and defenses for tool-using agents [5]. CaMeL
defends by design, separating control and data flow with capability tracking [38]. Our L6 information-flow
separation adopts this idea at the level of pods and identities.
Agent and MCP security. OWASP has published threats and mitigations for agentic AI [10], a Top 10 for
agentic applications [11], and an MCP security cheat sheet [7], alongside its LLM Top 10 [39]. The Cloud
Security Alliance’s MAESTRO framework offers a layered threat-modeling method for agentic systems [40].
Tool poisoning was disclosed by Invariant Labs [6], and surveys systematize MCP threats [13, 14]. These
works characterize threats and general mitigations; we contribute a concrete mapping onto Kubernetes
enforcement points and a reference architecture.
Risk management. The NIST AI Risk Management Framework [41] provides organizational structure for
AI risk; our governance layer is one operational instantiation for infrastructure agents.
Cloud-native isolation and policy. Sandboxed runtimes [16, 17, 34], admission control [15], policy as
code [36], eBPF runtime security [20, 21], workload identity [32], and software signing [37] are established.
The Agent Sandbox project [35], kagent [2], and agentgateway [3] bring agent-specific constructs to Kubernetes. Our contribution is the composition of these into a principled posture whose guarantees hold under full
agent compromise.

10

Conclusion

AI agents turn content into commands. On Kubernetes, where the cost of a wrong command is measured in
outages, the safe response is to treat the agent as an untrusted tenant and rebuild the data/control boundary
in infrastructure. We presented a threat model, nine principles, a seven-layer framework with concrete
Kubernetes artifacts, and a reference architecture in which every action is mediated, every guarantee survives
full agent compromise, and autonomy is earned per action class. The most important next step is empirical: a
Kubernetes-native injection benchmark that measures utility and attack success under layered ablations, so
that platform teams can choose their autonomy tiers on evidence.
