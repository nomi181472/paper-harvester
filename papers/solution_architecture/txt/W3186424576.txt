ABSTRACT With the popularity of container-based microservices and cloud-native architectures,
Kubernetes has established itself as the de facto standard for container orchestration. Kubernetes is known
for its advantage in easy deployment and operations for applications; however, it suffers from low resource
utilization, incurring high server provisioning and operational costs, due to following reasons. First, it is
common practice for latency-sensitive services to be over-provisioned for the peak load: Kubernetes might
consider such peak-load provisioning as constant, even though the actual resource utilization is low. Second,
the isolation between different containers is poor and cannot prevent performance degradation when besteffort jobs and latency-sensitive services run together. Users may have to run these two classes of workloads
on separate machines to avoid interference, resulting in higher provisioning costs. This paper presents a
highly scalable cluster scheduling system named Zeus, which is designed based on Kubernetes extension
mechanisms. Zeus achieves safe colocation of best-effort jobs and latency-sensitive services. Furthermore,
Zeus schedules best-effort jobs based on the real server utilization and can adaptively allocate resources
between the two classes of workloads. In addition, Zeus enhances container isolation by coordinating
software and hardware isolation features. As a result, Zeus can effectively improve the resource utilization of
Kubernetes clusters. We discuss the design and implementation of Zeus and evaluate its effectiveness using
latency-sensitive services and best-effort jobs in a massive production environment. The results show that
by colocating latency-sensitive services with best-effort jobs, Zeus can increase the average CPU utilization
from 15% to 60% without SLO violations.

• Static resource scheduling: Kubernetes does not consider the actual CPU and memory utilization of a node

on each server to report server resource usage to the scheduler

‘‘optimal’’ candidate scheduling node according to the historical load information of nodes and services. This approach

Pods can be categorized into three quality of service (QoS)

• Burstable: The rest of the Pods are burstable.
•

Kubernetes uses QoS classes to make decisions about
scheduling and evicting Pods. Guaranteed Pods are considered highest priority and have the highest resource guarantee. Burstable Pods have some resource guarantee that the
request manifest specifies and can use more resources when
available. Best-effort Pods are treated as lowest priority and
do not have any resource guarantee. The oom_score_adj
value of Best-effort Pods is the largest, which means that

memory. When the load of noncompressible resources such

of node, kubelet evicts the above Pods to ensure the stability
of the node. The order of eviction is Best-effort, Burstable,
Guaranteed.

B. KUBERNETES SCHEDULING

Kube-scheduler is a core component that affects resource
utilization and system performance. The newly created Pods
are added to a Pending Queue. Kube-scheduler continuously
fetches Pods from the queue one by one and schedules them
to the best node with sufficient resources based on the Pod’s
resource request and other conditions. For each pending Pod,
a two-phase operation is designed:
(1) Filter: Finds the set of nodes where it is feasible to
schedule the Pod.
(2) Priority: Ranks the filtered nodes to choose the most
suitable Pod placement. The scheduler assigns a score
to each node that survived filtering based on the active
scoring rules. Kube-scheduler then assigns the Pod to
the node with the highest ranking.
In the Filter phase, when Kube-scheduler judges whether
the idle resources on the node are sufficient, it does not
refer to the actual load of the node but considers the static
configuration resource request of Pods.
In the Priority phase, Kube-scheduler adopts the LeastRequested algorithm. It selects the node with the smallest
amount of resource requests first and tries to balance the load
between different nodes based on the following equations:

C. KUBERNETES CONTAINER ISOLATION

When multiple containers are running on the same node, they
compete for the shared resources on the machine, such as
CPU, memory, network, and IO. Kubernetes natively supports the scheduling of only CPU and memory resources, so it
isolates these two types of resources. The CGroups manager
in Kubelet configures the CGroups parameters according to
the Pods’ resource requests and resource limits to achieve a
certain degree of resource isolation.
For CPU resources, requests.cpu in the Pods corresponds to
the cpu.shares configuration in CPU CGroups, which defines
a relative weight of that container for the CPU time. limits.cpu maps to cpu.cfs_quota_us in CGroups, which limits
the CPU time of a container’s processes. CPU is a compressible resource. Pods can obtain at least the requested resources,
and if Pods use up all the time specified by the quota, they are
throttled for the remainder of the specified period and are not
allowed to run until the next period.
For memory resources, limits.memory in Pods maps to
memory.limit_in_bytes in CGroups, which means processes
in the container are killed by the kernel if they hit the specified
memory usage (OOMKilled).
However, the aforementioned isolation mechanism is more
limited than might be expected and cannot ensure that
latency-sensitive services are free from performance degradation. When services and jobs run on the same physical CPU
core or hyper-thread, Linux Completely Fair Scheduler (CFS)
cannot guarantee that batch jobs will not affect the SLOs
of latency-sensitive services [4], [16], [22]–[24]. CGroups
memory.limit_in_bytes limits the upper bound of only memory capacity usage, not the memory bandwidth. In addition, the physical machine resources shared between the
containers also include network bandwidth, IO bandwidth,
cache, etc. Container abstraction provides less isolation, and
sharing resources might lead to unpredictable performance
interference.
In this paper, we address the limitations of Kubernetes
native schedule and achieve multidimensional resource isolation on CPU, memory, cache, and network, effectively reducing the performance interference between services and jobs.

III. ZEUS SYSTEM DESIGN

The main design objectives of Zeus are summarized as
follows:
• Easy to deploy widely: The cost of data centers and
workload transformation is very large and not realistic
in the actual production environment, so Zeus must treat
the workloads as a black box and be able to be deployed
to any standard Kubernetes cluster.
• Maximize resource utilization through dynamic scheduling and dynamic resource allocation: Static allocation of
resources cannot take full advantage of idle resources
during off-peak times. Through dynamic scheduling
and dynamic resource allocation mechanisms, Zeus
enables batch jobs to use temporarily unused resources
of latency-sensitive services to maximize resource
utilization.
• Ensure batch jobs will not affect the SLOs of
latency-sensitive services and improve the execution
efficiency of batch jobs as much as possible to shorten
the completion time.
A. OVERVIEW AND ARCHITECTURE

We define a new API object, NodeProfile, based on the
Kubernetes Custom Resource Definition to describe the
resource profile of the node. We introduce two extended
resources, namely, colocation/cpu and colocation/memory,
which represent idle resources that batch jobs can use.
Fig. 4 describes the system architecture of Zeus; all components are developed based on the Kubernetes extension
mechanism.

Zeus-scheduler-extender: This component is developed
based on the Kubernetes scheduler http extender mechanism to implement dynamic scheduling of batch jobs.
• Zeus-exporter: The exporter collects the resource usage
metrics of the Kubernetes cluster.
Additionally, Zeus runs two agents on each node:
• Zeus-monitor-agent: The monitor agent collects
real-time metrics of resource usage and reports to NodeProfile objects.
• Zeus-isolation-agent: The isolation agent achieves multidimensional resource isolation on CPU, memory,
cache, and network. It regularly queries node resource
portraits from the Zeus-monitor-agent and applies isolation rules accordingly.
As shown in Fig. 5, when a user wants to create
batch jobs, he or she needs only to set the Pods label
colocation.netease.com/workload-type = batch-job, and containers still request native CPU and memory resources.
As shown in Fig. 6, the Zeus-webhook-server intercepts

Zeus-webhook-server converts native CPU/memory resource

D. RESOURCE ISOLATION MECHANISM

We realize multidimensional resource isolation to minimize interference and improve performance by means of
real-time resource monitoring and dynamic resource isolation
technology.
1) CPU ISOLATION

The main physical resource shared by services and jobs on
the server is the CPU. We should not statically allocate a fixed
number of CPUs to services and jobs. If insufficient CPUs are
allocated to latency-sensitive services, the SLOs of services
can easily be violated. If excessive CPUs are allocated to
services, underutilization may occur.
Zeus uses Linux’s cpuset CGroups to run services and jobs
on different CPUs and dynamically adjusts the configuration
of cpuset according to the resource requirements of latencysensitive services, which not only ensures the CPU resource
requirements of services but also allows jobs to fully utilize
idle resources of nodes.
When dividing the cpuset, we first sort the hyper-thread
according to the NUMA node topology and calculate the size
of the cpuset that could be allocated to jobs according to
equation (2). As shown in Fig. 7, hyper-threads are divided
into two cpusets: the head cpuset is allocated to latencysensitive services, and the tail cpuset is allocated to batch
jobs. When the cpuset of latency-sensitive services changes
from large to small, the adjustment step needs to be controlled. Each change can reduce at most 1 physical core.
In addition, we direct received network packets of services
and jobs to different Rx queues. Packets are sent to different Rx queues and bind to different cores for interrupt
processing.

use of disk IO bandwidth when services are idle; on the other
hand, it can prevent IO contention when services are busy.
5) NETWORK ISOLATION

We configure three VLANs to run control flow, services flow,
and batch jobs flow separately. As shown in Fig. 8, the tc
htb queue provided by the Linux kernel is used in the egress
direction of the server, and bandwidth guarantees and speed
limits are implemented for the three VLANs. In addition,
servers set different differentiated services code point (DSCP)
priorities for the three VLANs. Batch jobs network packets
use the lowest priority CS0, services network packets use
CS3, and control network packets use the higher priority
CS5. When the hardware switch forwards network packets,
it trusts the DSCP mark set by servers and preferentially
forwards control packets and services packets and discards
batch jobs packets first to ensure the network QoS when
network congestion occurs.
In the direction of server ingress, we use intermediate
functional block (ifb) technology to control the sending speed
of the sender through drop packets at the receiver and limit the
TCP traffic bandwidth of batch jobs.

V. RELATED WORK

Many papers propose various solutions to improve data center
resource utilization. However, most of the solutions have limitations: they rely on services to provide SLO and real-time
performance metrics API; they rely on specific hardware and
OS support; they do not consider the throughput of batch
jobs, which leads to lower job efficiency; or they are only
applicable to specific scenarios and are not universal. We propose a universal colocation solution for latency-sensitive
services and batch jobs, called Zeus, which has multiple
technical innovation advantages. We develop Zeus based on
the extension mechanism of Kubernetes, do not change any
Kubernetes in-tree code, treat services as a black box, and do
not rely on special hardware features. Therefore, Zeus can
easily be deployed to any standard Kubernetes cluster and
has good generalization ability. Moreover, Zeus considers not
only the performance of latency-sensitive services but also the
throughput of batch jobs. Zeus can increase the average CPU
utilization from 15% to 60% without SLO violations.
Bistro [28] is a scheduler for batch jobs that uses a hierarchical scheduling model, but it relies on static allocation of
reserved resources for latency-sensitive services, and batch
jobs use the remaining fixed-size resources. The static policy
is either too conservative (low resource utilization) or overly
optimistic (leading to SLO violations). Moreover, Bistro
emphasizes scheduling, and does not consider the problem of
resource contention between jobs and services on the node.
In contrast, Zeus dynamically adjusts the resource allocation, and batch jobs can make full use of the temporarily
unused resources of latency-sensitive services to maximize
the resource utilization.
PerfIso [4] is a performance isolation framework that runs
services/jobs on different CPU cores and dynamically adjusts
the CPU cores allocated to jobs according to the load of
services. However, PerfIso does not consider the isolation
of other physical resources shared by services and jobs,
such as caches and networks. Moreover, it is implemented
based on the Windows system and uses nonwork-conserving
VOLUME 9, 2021

X. Zhang et al.: Zeus: Improving Resource Efficiency via Workload Colocation for Massive Kubernetes Clusters

operating system scheduling algorithms, which limits the
wider adoption of this framework. Conversely, Zeus design a
multidimensional resource isolation framework by coordinating software and hardware mechanisms to achieve resource
isolation on CPU, memory, cache, and network, effectively
reducing the performance interference between services and
jobs. In addition, Zeus is implemented based on Kubernetes
and Linux, which is beneficial to its wide deployment.
Heracles [16] dynamically adjusts isolation parameters
based on the real-time latency of services and adjusts the
amounts of resources allocated to batch jobs. Heracles
requires knowledge of the services SLO and real-time latencies, which limits wide deployment in large-scale production
environments. Meanwhile, Zeus regards services as a black
box, and does not make assumptions about their implementation. Furthermore, Zeus needs to ensure only that there are
sufficient idle resources when services are at the peak load.
Elfen [3] achieves CPU-level isolation through simultaneous multithreading technology. However, Elfen needs services to provide latency and SLO query interfaces, which is
impossible or expensive in large-scale production environments. Moreover, Elfen is implemented at the OS kernel level,
which is impractical and imposes substantial overhead.
Bubble-Up [2] is concerned mainly with memory bandwidth interference in colocation scenario and does not
take other shared resources into consideration. Additionally, it must perform a colocation experiment for every
possible colocation scenario to obtain the degree of performance degradation for services under different memory
pressure from batch jobs. However, latency-sensitive services in the production environment are complex and diverse,
and frequent version upgrades are performed. Additionally,
the performance model may change, so this approach is not
practical.
Quasar [19] is a resource management system that
can improve resource utilization while meeting services
SLOs. The system uses collaborative filtering technology to
calculate resource requirements and adjusts resource allocations dynamically based on the real-time performance information of the service. In contrast, Zeus does not assume
that services provide explicit real-time latency and SLO
requirements.
Paragon [15] is an online scalable scheduler based on collaborative filtering technology that considers server heterogeneity and interference between shared resources, quickly
classifies and recognizes unknown services, and schedules
services to nodes with the best performance. At the same
time, Paragon can maximize server utilization. However,
it focuses on scheduling issues and does not consider the
isolation of shared resources.
ROSE [22] is a resource over-subscription framework.
Batch jobs can make full use of the redundant resources that
the services require but are currently not using to improve
resource utilization while meeting services SLOs. Zeus is
similar but does not oversell the resources of services and
does not change the QoS semantics of services in Kubernetes,

which can fully guarantee the SLO of latency-sensitive
services.
Townend et al. [29] propose a solution that coordinates
software and hardware isolation mechanisms to improve the
efficiency of data centers and implement their own scheduler
based on Kubernetes. However, its focus is on energy saving,
and it does not consider the services SLOs.
VI. CONCLUSION

The resource utilization of data centers is low, which results
in high operational costs and substantial resource wastage.
Colocating best-effort batch jobs with latency-sensitive services can effectively improve resource efficiency.
This paper presents the design and implementation of Zeus,
a cluster scheduling system based on Kubernetes. As an
operating system in the cloud computing era, Kubernetes
unifies the scheduling of latency-sensitive services and batch
jobs. We design a weighted dynamic scheduling algorithm
based on a time sliding window and realize multidimensional resource isolation mechanisms to coordinate software and hardware characteristics. Zeus treats services as
a black box, does not make any assumptions about services, and can be easily deployed to any standard Kubernetes
cluster.
We evaluate Zeus with three representative latencysensitive services (Redis, MySQL, and Nginx) on a single
machine and analyze the resource usage and application
performance of an over 5000-node production Kubernetes
cluster. The results demonstrate the effectiveness of Zeus for
scheduling and resource isolation: Zeus can minimize performance interference and maximize resource utilization. Colocating batch jobs with latency-sensitive services can increase
CPU utilization to 60% safely without SLO violations.
In the future, we will improve Zeus in the following aspects: quantifying the interference between
latency-sensitive services and batch jobs; reinforcing the
isolation of memory bandwidth and buffer IO; and considering the quality of idle resources and expected completion time of batch jobs. Such efforts will enhance the
versatility and effectiveness of Zeus in improving resource
efficiency.
