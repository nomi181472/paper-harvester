1

Connection Escrow: Holding AI-Agent Pod
Egress in the Kernel Until an Isolated Verifier
Rules

arXiv:2610.26501v1 [cs.CR] 19 Oct 2026

Ashok Subbabhatta Gopalakrishna
Abstract—AI agents running in containers act on the world by opening network connections, and the text that drives them can be
hostile. Controls placed between the agent and its tools, such as gateways, SDK hooks and proxy settings, can be bypassed by a child
process or a direct socket, and even when they are not bypassed, their approval is not tied to the connection the kernel later opens. We
present connection escrow: every outbound TCP connection from a supervised pod is parked inside the kernel’s connect() path,
before any packet exists, by a 98-instruction eBPF program attached to the pod’s cgroup. An interceptor on the node attributes the held
socket to its kernel socket cookie, process, executable digest, cgroup and pod identity, parks the first bytes the agent writes (HTTP
request line or TLS ClientHello), and asks a verifier that runs in a separate container with its own key. The connection is released only
on a signed verdict that names that one socket cookie and destination, is unexpired and unused; no verdict by the deadline resets the
connection, and a late approval is refused. The agent is unmodified. We implement the system (Python plus eBPF, with an iptables
fallback) and evaluate it two ways. A 36-check adversarial suite on Linux 6.18 with real cgroups and uid-separated agent processes
passes on both hold points (the three UDP-pinning checks need the kernel path): refused connections never reach the destination,
forged, rebound, replayed, expired and late verdicts are refused, the agent’s own attempt to reach the verifier is escrowed and refused,
child-process and renamed-binary bypasses fail, and UDP is pinned to the cluster resolver. On a single-node Kubernetes cluster, an
unmodified agent pod is held per connection and attributed to its SPIFFE identity; a raw socket that bypasses a comparison sidecar
proxy is held by escrow; and six pods opening 600 connections are all gated. The hold adds 4.3 ms median (6.8 ms p95) per released
connection on loopback, of which 24 µs is policy evaluation; the rest is attribution, one HTTP round trip and two signatures. Finally, we
extend escrow to gate on request content without terminating TLS: an eBPF uprobe reads every plaintext write at the agent’s
TLS-library boundary, a model scores it, and each TLS record is held until the write that produced it is scored, while the TLS session
stays end-to-end to the real server with the real certificate and the enforcer holds no key. The gate is demonstrated on three runtime
shapes with two kernel programs — shared OpenSSL, statically linked OpenSSL (the BoringSSL shape) and Go’s crypto/tls —
against the keep-alive exploit that defeats a first-record check: on one connection a benign request is allowed and an exfiltration
request that follows it is denied on its captured plaintext, so the server receives only the first. What decides a verdict is deliberately
pluggable and out of scope.
Index Terms—AI agents, eBPF, Kubernetes, egress control, workload identity, runtime enforcement, time-of-check to time-of-use.

a standing allow-list: once a destination is permitted, it is

2

P ROBLEM AND THREAT MODEL

2.1

Setting

A supervised workload is a Kubernetes pod (or, more generally, any control group) in which an agent and the tool
processes it starts run. The pod has a service account and,
through it, a platform identity such as a SPIFFE verifiable
identity document (SVID). The operator wishes to control
every outbound connection the pod makes, one connection
at a time, according to a policy that a verifier evaluates. The
verifier is trusted by the operator and is outside the agent’s
control; it runs elsewhere in the cluster, in its own pod with
its own key. The question is not what the policy should say
— that is the operator’s and is deliberately out of scope
— but where the decision can be enforced so that the agent
cannot route around it, and how the decision can be tied to
the exact connection it is about.

This matters because an agent’s outbound calls are the
point at which text it was given turns into action in the
world: fetching a URL named in a web page, posting to
an API named in a tool result, pushing to a host named
in a prompt. When that text is adversarial — a prompt
injection, a poisoned document, a compromised upstream
tool — the connection the agent opens is the thing that must
be checked, and checked somewhere the agent’s own code
cannot disable.
2.2

Assets and trust boundary

The assets to protect are (i) the confidentiality of data the
pod holds, which an unapproved outbound connection
could exfiltrate, and (ii) the integrity of external systems,
which an unapproved connection could act on (write, delete,
transfer). The trusted computing base is the operating-system
kernel, the node agent that loads the eBPF programs and
runs the interceptor, the verifier, and the cluster control
plane (API server, kubelet, CNI). The untrusted part is everything inside the supervised pod: the agent process, every
process it spawns, every library and interpreter it loads, and
any tool server it starts. The boundary between the two is
the pod’s cgroup: the kernel is on one side, the untrusted
workload on the other, and the eBPF hook sits exactly on
that line, inside the kernel, invoked by the untrusted code
but not modifiable by it.
2.3

Adversary capabilities

We grant the adversary full control of the code running inside the pod. Concretely, the adversary may: open a connection to any address, port and protocol; issue the connection
from the agent process, from a child process, from a thread,
or from a freshly exec’d binary; rename, copy or rebuild
its executables to defeat path-based rules; craft arbitrary
application-layer bytes (any HTTP request, any TLS ClientHello, any opaque stream); attempt to contact the verifier
directly to forge or solicit an approval; replay a verdict it
has observed; and open many connections concurrently to
race the control. The adversary may observe traffic on the
node network between the interceptor and the verifier. The
adversary may not escape the pod’s cgroup (that is container
escape, a separate problem assumed solved by the sandbox),
obtain root on the node, read the verifier’s signing key or the
interceptor’s record-authentication key, or forge the kernel’s
socket-cookie allocation. We assume the sandbox and the
kernel’s namespace isolation hold; escrow composes with
them rather than replacing them.
2.4

Goals

Against that adversary the system must meet six goals. Each
is stated as a property and the reason it is hard without a
kernel-resident, per-connection mechanism.
G1 — Pre-packet hold. A connection the policy refuses
must produce no packet to the destination, not merely a reset
after the SYN. A control that acts after the connection is
established (a proxy that reads the request, a filter that sees
the first packet) has already leaked the fact of the attempt,
and sometimes the first bytes, to the destination. Holding

3

inside connect(2), before a route is allocated, is what
makes the refusal invisible to the outside.
G2 — Attribution. Every held connection must be attributed to the kernel object that made it (the socket, identified by its cookie), to the process (pid, executable digest,
cgroup), and to the platform identity (pod, namespace,
service account, SPIFFE id). Without attribution the verifier
cannot apply a per-workload policy, and a receipt cannot
be trusted to name who did what. Attribution must survive
the adversary renaming its binary or acting from a child
process.
G3 — Isolated verifier. The verdict must come from a
component the agent can neither reach nor impersonate. If
the agent could open a connection to the verifier, it could
request its own approvals; if it could forge a record, it could
answer as the interceptor. Both paths must be closed.
G4 — Single-use, socket-bound release. An approval must
release exactly one socket, to exactly one destination, exactly
once. This is what closes the time-of-check-to-time-of-use
(TOCTOU) gap: an approval that authorises “connections to
host H ” can be spent by a later, different connection to H ;
an approval bound to one socket cookie and one destination
hash, consumed atomically, cannot. Replay of a captured
verdict, rebinding it to another socket or destination, and
forgery under the wrong key must all fail.
G5 — Fail closed. If no verdict arrives before a deadline, or
the verifier is unreachable, the connection must be reset, not
allowed. An approval that arrives after the deadline must
have no effect, so that a slow or replayed verdict cannot
open a connection the agent attempted earlier and the
system cannot be pushed into a fail-open state by delaying
the verifier.
G6 — No agent change. The control must require nothing
of the agent: no SDK, no proxy environment variable, no
modified library, no injected sidecar in the agent’s own
process. Anything the agent must opt into, it can opt out
of; and anything that lives in the agent’s address space, a
compromised agent can disable. The enforcement must hold
for an unmodified binary, in any language, including code
the agent writes and runs at run time.
2.5

Non-goals

Escrow does not decide whether a connection is acceptable;
that is the policy’s job, and the verifier’s policy engine
is replaceable (Section 3.5). It does not defend against an
adversary who has escaped the pod or holds root on the
node. Without the content gate it does not inspect or control
traffic on connections it has released — once a socket is
spliced to its destination, the bytes flow unexamined beyond
the first bytes checked at release; with the content gate every
write on the connection is scored (Section 3.7). It does not
provide confidentiality for the traffic itself (that is TLS’s job)
and does not terminate TLS. Finally, it is not a replacement
for network policy or a service mesh; it composes with
them, adding a per-connection, identity-bound, fail-closed
decision that those layers do not provide.

3.1

Why the connect() hook

Several places could host an egress control, and the choice
determines which goals are reachable. A sidecar or egress
proxy (Envoy ext_authz, a CONNECT proxy) sees only
traffic the workload chooses to send it, so it fails G6 and G1:
a child process or a raw socket bypasses it, and by the time
it sees a request a connection already exists. A netfilter queue
(NFQUEUE, as OpenSnitch uses) holds a packet in the kernel
pending a user-space verdict, which satisfies G1 and G5,
but it acts on the first packet after the socket is created and
attributes by scanning for the owning process after the fact,
which is racy under load and has no notion of workload
identity. An LSM hook (security_socket_connect via
BPF-LSM) is synchronous and pre-packet, but its verdict
is a local allow/deny: it cannot sleep to wait for an external verifier, so it cannot host a held, remotely-decided
connection (G3, G4). A transparent redirect (TPROXY, or NAT
REDIRECT) delivers the connection to a local userspace
process that can then take as long as it likes, which is what
we need, but plain redirect loses the original destination and
the identity unless they are recovered separately.
The cgroup/connect4 hook combines the properties
none of these has alone. It is synchronous and pre-packet
(G1): it runs inside connect(2) before a route is allocated.
It can rewrite the destination, so it redirects the socket to
a userspace interceptor that is free to wait for an external
verdict (G3, G4, G5). It runs in process context, so it reads
the cgroup id and pid directly from the kernel (G2). And it is
attached per cgroup, so it covers every process in the pod —
the agent, its children, its tool servers — without anything
in the agent’s address space (G6). The one thing it does not
give us for free is the original destination on the interceptor
side, because after the rewrite the kernel only knows the
interceptor’s address; we recover it from the socket cookie,
which is the hinge of the whole design and the subject of
Section 3.3.

3.3

Attribution

When the interceptor accept()s the redirected connection,
it must answer three questions about a socket it did not
create: which kernel socket is this, which process and cgroup
opened it, and which pod identity does that cgroup belong
to. The three answers are joined through the socket cookie.

Kernel object: The interceptor recovers the cookie of
the agent’s socket in one of two ways. In the common case
the sockops program has already written {local address, local port} → cookie into peer_map, and the interceptor looks
it up by the peer address of the accepted connection; this
works across network namespaces, which matters because
each pod has its own. As a fallback (and on the iptables
path) it issues a NETLINK_SOCK_DIAG (inet_diag) query
for the exact 4-tuple, which returns the socket’s cookie,
inode and uid. Either way the cookie it obtains is the same
value the connect4 program keyed its escrow_map entry
on, so the interceptor can read back the original destination,
cgroup id and pid the kernel recorded at connect() time.
No secret is shared between the agent and the interceptor
for this to work; the join is on a kernel-assigned identifier
the agent cannot forge.
Process: With the eBPF entry the pid and cgroup
id are known directly. Otherwise the owning process
is found by scanning /proc/*/fd for the symlink
socket:[inode]. From /proc/<pid> the interceptor
reads the cgroup path, the executable path, its SHA256, and comm. The digest is taken by reading through
/proc/<pid>/exe, which follows the kernel’s reference to
the actual inode, so an adversary that copies or renames its
interpreter gets a new inode and the real digest of whatever
it ran — the renamed-binary bypass (T11) changes the path
but not the digest or the cgroup.
Platform identity: A registry maps cgroup-path prefixes to pod identities. On Kubernetes the kubelet names
each pod’s cgroup after the pod uid, so the mapping is
a longest-prefix lookup, and the node agent fills it from
the API server for the pods it has labelled supervised,
refreshing on an interval so pods that start later are covered.
The identity carried forward is {pod uid, namespace, name,
service account, SPIFFE id}; the SPIFFE id is the key the
verifier’s policy is written against.

3.4

Parking the first bytes

The interceptor reads up to 4 KiB for at most 150 ms. An
HTTP/1.x request line and headers yield method, host
and path; a TLS ClientHello yields the SNI; anything else
is opaque. Nothing is forwarded: the bytes stay with the
connection and go to the destination only after release, byte
for byte. Their hash is part of what the verdict binds to, so an
approval for one request cannot be spent on another written
on the same socket.

3.5

The verifier

The verifier is a service with its own signing key, running
in its own pod. It accepts an escrow record authenticated
with a message-authentication key (HMAC-SHA256) that
is mounted only into the interceptor container, so a pod
that somehow reached the verifier’s port could not submit
a record it would accept. It evaluates a policy keyed on the
workload’s SPIFFE id and returns a signed verdict

v = Signverifier escrow_id, cookie, H(dst, first bytes),

ALLOW | DENY, tissued , texpires , nonce .
Policy: A policy is a set of per-workload rule lists
plus a default. Each rule matches on any of: destination
by name (SNI or HTTP Host, with glob), by Kubernetes
service (a cluster-IP→namespace/name map the verifier
keeps from the API server), or by address; destination
port; HTTP method and path prefix; and whether layer-7
metadata is required at all. The first matching rule decides
allow, deny or hold. A per-workload token-bucket budget
caps the rate of allowed connections, so a workload that
is compromised into a burst of approved-looking calls is
throttled even where each call matches a rule. A rule set is
deliberately small and declarative; the point of the paper is
the enforcement path, and the policy function is a single call

6

that any richer engine — an OPA/Rego evaluator, a learned
classifier, a human queue — can replace without touching
the kernel or the interceptor. Section 3.5 ships the rule engine
as a default, not as the contribution.
Service identity of destinations: Because pods
reach services by cluster IP, a rule written against
lab/internal-api must be matched against the cluster
IP the connection actually used. The verifier maintains the
reverse map from the API server and refreshes it, so a
destination’s service identity, not just its IP, is available to
the policy and recorded in the receipt.
Self-protection: A destination equal to the verifier’s
own address (or that of its service) is always denied with
reason destination_is_verifier. Combined with the
interceptor-only record key, this closes G3 from both sides:
the agent cannot reach the verifier (its connection to it is
escrowed and refused), and could not be understood by it if
it did.
3.6

UDP and DNS pinning

TCP connections are escrowed; UDP is pinned. An agent that
cannot exfiltrate over TCP could otherwise leak over DNS
— encoding data in query names to a resolver it controls
— or over any other UDP service. The connect4 and
sendmsg4 programs therefore apply a narrow rule to UDP:
a datagram to the configured cluster resolver (dns_ip:53)
is allowed; every other UDP destination is denied in-kernel
with EPERM. This is a pin rather than an escrow — the
datagram is not held for a verdict — because DNS is
latency-critical and the cluster resolver is a fixed, trusted
endpoint; holding every query would add a round trip
to every name lookup for no security gain. The effect is
that name resolution works normally through the cluster’s
own resolver, and a query aimed anywhere else, or a UDP
tunnel to an arbitrary host, never leaves the node. Per-rule
kernel counters record how many UDP datagrams were
allowed and denied, which the evaluation reports. The same
approach extends to other UDP services (NTP, QUIC) by
widening the pinned set; escrowing UDP for a verdict, and
the IPv6 hooks, are left to future work (Section 9).
3.7

Gating on content without terminating TLS

Everything so far decides on where the agent connects
— destination, port, and the SNI visible in a TLS ClientHello. That is the right control for the dominant agentegress threats (exfiltration to an unauthorized destination,
command-and-control, calling a forbidden service), and encryption hides none of it: the destination address is the one
field the kernel must have in the clear to route, and escrow
sits exactly where it is. What encryption does hide is the
request content — the body of a request to a destination
the policy permits. To gate on that, one normally terminates
TLS at a proxy with a trusted certificate authority in the
workload, which holds a key, sees all plaintext, and breaks
the end-to-end property. We avoid that.
Reading the plaintext: The plaintext is available at
the agent’s own endpoint, before encryption. An eBPF uprobe attached to the write function of the agent’s TLS library
is invoked with the plaintext buffer as an argument; it copies
up to one TLS record (16 KiB) of every write, in order, into

a kernel FIFO, each event carrying the writing task, the full
length of the write, and the TLS object it was made on (the
SSL* or *tls.Conn handle, the function’s first argument).
A second pair of probes records which socket each handle
writes to: exactly, by a probe on SSL_set_fd for OpenSSL,
or by the socket write that immediately follows a TLS write
on the same task (syscall.write for Go, write in libc
as a fallback). The interceptor resolves that handle to a
file descriptor and, through /proc, to the socket’s local
port, which is the port it accepted the connection from, so
each captured write is matched to its connection by socket
identity rather than by arrival order. Where that function
lives, and which registers carry the buffer, depend on the
runtime, and nothing else does. For OpenSSL the symbols
are SSL_write and SSL_write_ex with the buffer and
length in rsi and rdx (System V ABI); the probe is placed
at the symbol’s file offset in libssl.so when the library
is shared, or in the agent’s own executable when it is
statically linked, which is also the shape of a BoringSSL
build. For Go, crypto/tls is compiled into every binary;
the symbol is crypto/tls.(*Conn).Write and the Go
register ABI passes the slice pointer and length in rbx and
rcx, so a second 52-instruction program reads those two
registers and shares the capture path. The loader inspects
the agent’s ELF to choose the program and the symbol (Go
symbol present → Go; SSL_write present → static; otherwise shared libssl). The TLS session is untouched — the
handshake completes end-to-end to the real server, which
presents its real certificate, and the agent validates it against
the hostname as usual. The enforcer never possesses a key
and never decrypts the wire; it observes the plaintext inside
the agent’s address space, through the kernel. This capture
technique is itself known from observability systems [6]; the
contribution is to act on it.
Holding on the plaintext: The interceptor already
relays the agent’s encrypted bytes without a key. For a
TLS connection it forwards the handshake untouched and
then holds every outgoing application-data record until the
write that produced it has been scored. The simplest form
of the gate — hold only the first application-data record,
then splice — is the one we built first, and it is wrong in
a way worth stating: it is blind to everything written after
that record, so a benign first request on an HTTP keep-alive
connection opens the door for a second, hostile request on
the same socket, the tail of a body longer than one record is
never seen, and under HTTP/2 the first record is the connection preface, not a request at all. Section 6.5 demonstrates
that exploit before showing it closed. The stream gate drains
the FIFO, binds the connection to the TLS handle of its first
write and thereafter consumes only writes on that handle, so
concurrent TLS sessions in one process cannot cross; a write
of n plaintext bytes becomes one or more records, and the
relay calibrates the per-record ciphertext overhead from the
first record and releases records until n bytes are accounted
for, then treats the next record as the start of a new write
and fetches its plaintext. A content model scores each write;
on allow its records are released, on deny the connection
is reset and the held record never leaves the node. If no
plaintext arrives for a held record within the timeout the
gate denies, so an agent whose TLS the probe cannot see
loses egress rather than gaining an unobserved channel. The

7

verdict is bound to the connection as in Section 3.8; this is the
same single-use, identity-bound gate applied one layer up,
to each write instead of to the destination. The cost is that a
content-gated connection stays in the userspace relay for its
lifetime and pays one model call per write. Under TLS 1.2
application-data records (type 0x17) are distinguishable
from the handshake on the wire; under TLS 1.3 the outer
type is uniformly 0x17 after the ServerHello, so the gate
holds every post-ServerHello record and uses the uprobe
events, which exist only for application writes, to decide
what to score — the enforcer still decrypting nothing.

Scope: The uprobe is per-library. Shared OpenSSL,
statically linked OpenSSL (and by the same mechanism
BoringSSL, which keeps the SSL_write signature) and
Go’s crypto/tls are covered and evaluated (Section 6.5);
Rustls has a different write shape and needs its own probe,
and a stripped binary carries no symbol, so its offset must be
supplied out of band. The content model is a deterministic
logistic-regression placeholder over request features; like the
connection policy, it is replaceable and is not the contribution. Two limits remain in the prototype. Up to one TLS
record (16 KiB) of each write is captured, so a request whose
body spans several records is seen only up to its first record
and a model that scores whole multi-record bodies needs
the capture chunked across them. And under HTTP/2 every
frame is scored at the byte level, but HEADERS frames
are HPACK-compressed, so a content model needs a perconnection HPACK decoder to read them; DATA frames are
plain. The join from a captured write to its connection is by
the write’s socket, resolved through /proc, so concurrent
TLS sessions in one process are disambiguated whatever
their interleaving (Section 6.5 runs two interleaved sessions
and confirms an exfiltration write stays on its own connection); the resolution races the kernel’s fd binding by a
few microseconds, during which the gate falls back to the
handle of the connection’s first write. More fundamentally,
the content gate’s adversary is weaker than the connection
gate’s. Section 2 grants the adversary full code control;
against that adversary the connection gate holds, because
it is in the kernel and keyed on the cgroup, but the content
gate does not: an agent that ships its own TLS, strips its
symbols, or inlines encryption gives the probe nothing to
see. The gate then fails closed — the agent loses TLS egress
rather than gaining a channel — but a decoy write through
the probed function while the real payload goes another
way, or a race on the buffer between the probe’s copy
at function entry and the library’s encryption, is available
to such an adversary and is inherent to observing before
encryption inside an address space the adversary owns. The
content gate is therefore a control against hostile input to
an honest agent, the prompt-injection setting of the introduction, not against hostile code; the connection gate is the
control against hostile code. What is new is the combination
— see the plaintext via a uprobe, gate the connection on
it with a single-use identity-bound verdict, and keep the
connection end-to-end with no key at the enforcer — which
removes the usual “inspect or stay end-to-end, choose one”
tradeoff between a terminating proxy and a pure observer.

3.8

The release gate

The interceptor releases a held connection only if all of
the following hold: the escrow id is still live (not decided,
not retired by the deadline); the signature verifies under
the verifier’s key; the verdict names this escrow id, this
socket cookie and this destination hash; the verdict has
not expired; the escrow id has not been consumed; the
verdict is ALLOW. On success the escrow id is consumed
and the interceptor connects to the destination, forwards
the parked bytes and splices the two sockets. Any other
outcome, including a transport error toward the verifier,
sets SO_LINGER to zero and closes, so the agent sees a
reset. Because the interceptor only calls connect() after
the gate passes, a refused connection sends nothing to the
destination (G1).
3.9

Hold and release with a deadline

A hold rule parks the decision at the verifier until an
operator posts a release or the verifier’s hold timeout passes.
The interceptor’s deadline D is independent and shorter.
When D passes the connection is reset and the escrow id is
retired; a verdict released afterwards for that id fails the first
condition of the gate (“stale”) and opens nothing (Fig. 3).
An approval therefore cannot act on a connection the agent
attempted earlier, and the agent cannot keep a connection
pending indefinitely.
3.10

Receipts

Each decision becomes a receipt {escrow id, node, cookie,
inode, pid, cgroup, executable digest, workload, destination,
wire summary, outcome, reason, timings} appended to a
hash chain at the interceptor; the verifier keeps its own chain
of {escrow id, workload, decision, reason, decision time}. A
changed receipt breaks the chain at that entry.
3.11

Deployment on Kubernetes

A DaemonSet runs the node agent with host PID and
host network, the host cgroup tree mounted, and the
capabilities needed to load and attach the programs. It
watches the API server for pods on its node labelled
escrow.io/supervised=true, resolves each pod uid to
its cgroup directory under the node’s kubepods hierarchy,
attaches the three programs there, and writes the registry;
the watch interval picks up pods that start later. The interceptor listens on the node address reachable from pods (the
CNI bridge), so a redirected connection from any pod on
the node arrives at it; because it runs on the host network
it can in turn reach cluster-IP services (through kube-proxy)
and the verifier. The verifier is a Deployment in its own
namespace, fronted by a Service, with a NetworkPolicy
admitting only node addresses on its port. The supervised
pod needs nothing but the label and its service account (G6):
no sidecar, no init container, no changed image. For clusters
where eBPF cannot be loaded, a per-pod sidecar variant
uses an iptables init container and a shared process
namespace so a sidecar interceptor can attribute through
/proc. Section 6.4 reports a run of this deployment against
real pods on a single-node cluster.

I MPLEMENTATION

The prototype is Python 3 (standard library; pyelftools
to load the ELF object; cryptography optionally for native
Ed25519, with a pure-Python fallback) and about 250 lines
of restricted C compiled with clang -target bpf into
five programs: connect4 (98 instructions), sendmsg4 (50),
sockops (22) and the two TLS-write uprobes (52 each).
The loader uses bpf(2) directly: it creates the two maps,
patches the ld_imm64 map relocations, loads the program
as CGROUP_SOCK_ADDR/INET4_CONNECT and attaches it
to a cgroup directory with BPF_F_ALLOW_MULTI. The interceptor is an asyncio server; attribution runs in a thread.
The verifier is a threaded HTTP server with /v1/escrow,
/v1/release and /v1/pending. Records are canonical
JSON; verdicts and receipts are Ed25519 over a tagged
canonical encoding. The whole system, both hold points, the
harness, the suite and the benchmark are about 3 800 lines,
of which the system itself (package and eBPF programs) is
about 2 150.
The test harness creates one cgroup per pod under
cgroup v2, runs each agent as a separate process under
an unprivileged uid inside that cgroup, and uses loopback
echo servers that record every accepted connection and its
first bytes. Agents are ordinary programs: the suite uses
a small Python client, and the end-to-end script uses an
unmodified curl. The cross-engine primitives (canonical
JSON, Ed25519, the hash-chained audit log) are reused from
our earlier gateway [16], so the new code is the kernel
programs, the loader, the attribution join, the interceptor
state machine and the verifier.

5

S ECURITY ANALYSIS

We argue each goal against the adversary of Section 2,
and point to the adversarial check (Section 6, Table 2) that
exercises it.
G1, pre-packet hold: The interceptor calls
connect() toward the destination only after the release
gate returns true. On the eBPF path the agent’s own
connect() never carried the destination address past the
hook — the kernel rewrote it in place — so for a refused
connection no SYN is ever formed for the real destination.
The harness confirms the destination accepts nothing (T1,
T7); the code path is what makes the guarantee, not the
observation. The one caveat is that the destination’s address
appeared in the kernel’s escrow_map, never on the wire.
G2, attribution, under evasion: Attribution binds to
the cgroup and the executable digest, not the path or the
process name. A child process (T11) is in the same cgroup
and is attributed to the same pod; a renamed or copied
interpreter (T11) yields a new inode and the true digest
of what ran. The socket cookie that joins the kernel and
interceptor views is assigned by the kernel and cannot
be chosen by the agent, so the agent cannot present one
connection’s identity for another’s.
G3, isolated verifier: The verifier is a destination like
any other, so an agent’s attempt to reach it is itself escrowed
and refused by the destination_is_verifier rule (T6);
only the interceptor’s record reaches the verifier at all. And
the record carries an HMAC under a key mounted only in
the interceptor, so even a pod that reached the verifier’s
port could not submit a record it would accept. The agent
can thus neither request its own approval nor answer as the
interceptor.
G4, single-use socket-bound release: The gate accepts
a verdict only if it is signed by the verifier (forgery under
another key fails, T5), names this escrow id (a verdict for
another connection fails), names this socket cookie (rebinding to another socket fails, T5), names the hash of this
destination and these first bytes (rebinding to another destination or request fails, T5), has not expired (T5), and has
not been consumed (replay of an accepted verdict fails, T5).
Consumption is atomic: the escrow id moves to a consumed
set under the interceptor’s lock, so two concurrent deliveries
of the same verdict cannot both release. This is the property
that closes TOCTOU: an approval is spent on exactly the one

9

socket it names.
G5, fail closed: If no verdict arrives within the deadline D, or the verifier is unreachable or returns a transport
error, the gate’s first condition fails and the connection is
reset (T3, T12). The deadline is enforced at the interceptor
independently of the verifier’s own hold timeout, so a slow
verifier cannot hold a connection open past D. A verdict that
arrives after D finds the escrow id retired and is rejected as
stale (T4), so delaying or replaying a verdict cannot reach
a fail-open state; the system’s failure direction is always
closed.
G6, no agent change: Nothing in the enforcement
lives in the agent’s address space. The hook is in the kernel,
attached to the cgroup, and covers the agent, its children
and its tool servers regardless of language or runtime. The
bypass comparison (Section 6.4) makes this concrete: a control that lives in the agent’s environment (an HTTP_PROXY
setting) is defeated by a raw socket, while the kernel hook
holds it.
Residual risk: The analysis assumes the TCB of Section 2. An adversary with root on the node can detach the
programs or read the keys; escrow does not defend the node
against itself, and a production deployment would pair it
with attestation of the loaded program set (which our earlier
gateway [16] provides and which is left as integration).
Data-only attacks that reuse an already-released connection
are out of scope for the connection gate, which controls the
opening of a connection and the first bytes on it; the content
gate’s stream mode extends the check to every write on a
content-gated connection (Section 3.7). UDP other than to
the pinned resolver is denied, not escrowed, so a covert
channel inside allowed DNS traffic is not addressed.

record: deciding on request content while the tunnel stays
end-to-end, which a terminating proxy cannot do without a
key and a pure observer cannot enforce.

identity at the pod or mTLS-principal level. They do not see
the process, do not bind the verdict to a kernel socket, and
are bypassed by anything that does not traverse the sidecar.
Interactive host firewalls. OpenSnitch [3], [4] queues each
new connection in NFQUEUE, identifies the process, asks
the user, and applies a default after 15 s; a “once” duration
makes a verdict per connection. It is the closest non-agent
prior art for a held, process-attributed connection, but has
no workload identity, no separate verifier and no socketbound token. Quarantine until a later verdict is old [5].
Kernel enforcement for agents. AgentSight [6] observes
agents with eBPF (TLS uprobes correlated with syscalls)

12

but does not enforce. ActPlane [7] compiles informationflow rules into eBPF with block, kill and notify effects.
mcpguard-dynamic [8] derives allow-lists from MCP tool
schemas and enforces them with BPF LSM on open,
connect and execve. ProcRoute [9] authorizes routes per
process with cgroup/connect4, synchronously, from local
policy. Tetragon [10] enforces in-kernel with override or
kill. AgentKernel [11] argues for a mandatory enforcement
boundary below the agent. In all of these a policy entry
is standing: it authorizes any matching connection for as
long as it is loaded, and nothing waits for an external
verdict. AARM [12] specifies intercept-then-decide for agent
actions, listing eBPF among possible architectures, without
a socket-level mechanism. Agent sandboxes. Claude Code’s
sandbox [13] routes egress through a proxy outside the
sandbox and prompts the user for a new host, then allows
the host for the session; NVIDIA OpenShell [14] forces
egress through a CONNECT proxy under OPA, identifies
the calling binary via procfs, and blocks unknown endpoints until an operator widens the policy. Both approve a
destination, not a connection, and act on traffic that uses
the proxy. Tran et al. [15] argue for treating agent security
as a networking problem with a per-agent sidecar under a
separate control plane, which is the architectural position
this paper implements at the kernel rather than at a proxy.
Attribution building blocks. Socket cookies are kernelunique identifiers readable from eBPF [17] and, as we use
here, from inet_diag; cgroup-based container attribution
with connect hooks was described by Meta [18]. SPIFFE/SPIRE resolves a process to a pod identity through the
same cgroup path. We know of no prior system that keys an
external verifier’s single-use approval on the socket cookie.
Table 6 places the closest systems against the five properties that together define connection escrow: (a) holding a
connection pending an external verdict rather than deciding
locally; (b) attributing it to the process and workload identity; (c) enforcing before any packet leaves; (d) a deadline
after which the held connection is denied; (e) binding each
approval to a single socket, used once. Each property appears somewhere in the prior art; no prior system has all
five. What distinguishes connection escrow is exactly that
combination: hold at connect() inside the pod’s cgroup,
attribution that joins the kernel view to the pod identity,
a verifier the agent cannot reach, and a release bound to
one socket and one destination with a fail-closed deadline.
Together they close the gap between approving an action
and the connection that performs it — the gap a standing
allow-list or a bypassable proxy leaves open.

The deadline is the real knob: For a workload whose
connections are all policy-allowed, escrow adds a few milliseconds and is invisible against tool calls that take hundreds of milliseconds. The cost that bites is the hold rule:
a connection parked for a human or a slow external check
pays up to the full deadline when no answer comes, and
fails closed. Operators therefore reserve hold for genuinely
ambiguous destinations and let the common case be a fast
allow/deny; the calibrated-risk style of decision from our
earlier gateway [16] fits here, deciding at once for the bulk
and holding only the tail.
Composition: Escrow is not a network policy and
not a mesh; it is a per-connection, identity-bound, failclosed decision that sits underneath both. A cluster can run
NetworkPolicy for coarse L3/L4 segmentation, a mesh for
mTLS between services, and escrow for the agent-specific
question of whether this pod may open this connection right
now. Because it enforces below the application and below
the sidecar, it also catches the traffic those layers miss: the
child process, the raw socket, the static binary.
Toward a product: The natural next step is to pair the
verdict-bound release demonstrated here with an attested
record of the loaded program set, so a relying party can verify not only the decision but that the approved enforcement
was in force when it was made — the integrity half our
earlier gateway [16] already provides. Escrow supplies the
enforcement; that supplies the proof; together they are an
auditable egress-governance layer for agent workloads.

L IMITATIONS

The hold point covers IPv4 TCP, and pins IPv4 UDP (including DNS) to a configured resolver through the connect4
and sendmsg4 hooks; IPv6 needs the connect6 and
sendmsg6 hooks, which are not implemented. UDP is
pinned rather than escrowed: a datagram to the cluster
resolver is allowed and anything else denied, so DNS cannot
be exfiltrated to an outside resolver, but a covert channel
inside otherwise-allowed DNS traffic, and UDP payloads in
general, are not held for a verdict. Relatedly, the agent resolves a name before it calls connect(), and a lookup of an
attacker-controlled name reaches that name’s authoritative
server through the cluster resolver; escrow holds the connection, not the resolution, so G1 hides the connection attempt

13

from the destination, not the fact that its name was looked
up. The iptables fallback keys on uid and therefore assumes
an unprivileged agent (Section 3.2); the eBPF path does not.
A connection whose first bytes carry no SNI or recognisable request gives the verifier only the destination tuple.
Attribution through /proc needs CAP_SYS_PTRACE on the
node; the eBPF path avoids the scan for pid and cgroup but
still reads /proc/<pid> for the executable digest. After the
in-kernel rewrite the agent’s getpeername() returns the
interceptor’s address; a cgroup/getpeername4 program
can present the original, and we have not written it. The
prototype’s interceptor is a single Python process and the
verifier a threaded Python server; the concurrency figures
reflect that, not the kernel program, and the paths to scale
out are in Section 8. The evaluation is single-node; a multinode run would exercise the DaemonSet and cross-node
verifier traffic, which the manifests support but we have
not measured. The content gate’s uprobe covers shared and
static OpenSSL and Go’s crypto/tls; Rustls needs its own
probe target, a stripped binary needs its offset supplied, the
content model is a placeholder, each write is scored on up
to one 16 KiB record, and HTTP/2 headers need an HPACK
decoder in the model; the gate is demonstrated on TLS 1.2
on loopback, not yet at cluster scale, and its adversary is hostile input to an honest agent, not hostile code (Section 3.7).
The threat model trusts the node; an attacker with root on
the node can detach the programs, which is why the product
direction pairs escrow with attestation of the loaded set.

10

C ONCLUSION

A connection can be held where it is born. Doing so in
the kernel, attributing it to the socket and the pod, asking
a verifier the agent cannot reach, and releasing exactly
that socket once, gives an agent runtime a control that no
library or proxy setting can route around, at a cost of a
few milliseconds per connection. The decision logic that sits
behind the verifier is a separate problem; this paper gives it
a place to stand.
