Abstract—The User Plane Function (UPF) of a 5G Standalone
core terminates every GPRS Tunnelling Protocol user-plane
(GTP-U) packet arriving from the radio access network, which
makes its N3 interface both the busiest and the most exposed
point of the mobile data path. As operators migrate the core
onto Kubernetes and public cloud, the UPF increasingly shares a
general-purpose Linux kernel with other workloads, and kernelbypass frameworks such as DPDK become harder to operate.
This paper presents GTP-Guard, a design for line-rate GTPU admission control built on the eXpress Data Path (XDP)
hook of the Linux kernel. GTP-Guard drops illegitimate tunnel
traffic in the network driver, before socket-buffer allocation, using
six ordered stages: peer allow-listing, GTP-U header validation,
Tunnel Endpoint Identifier (TEID) admission against session
state derived from the Packet Forwarding Control Protocol
(PFCP), bounded extension-header parsing, inner-packet antispoofing with GTP-in-GTP detection, and per-session policing.
We formalize stage ordering as a cost-minimization problem
and show that sorting stages by the ratio of per-packet cost to
rejection probability minimizes expected per-packet work, which
motivates run-time reordering through tail-call program arrays
when traffic mix shifts under attack. We further describe a
Kubernetes deployment model based on a node-level DaemonSet
with pinned eBPF maps that survive agent upgrades, discuss
constraints specific to public-cloud virtual NICs, and define a
reproducible evaluation methodology, with explicit hypotheses,
for throughput, latency, CPU efficiency and attack resilience.
This paper presents the design and methodology; experimental
results will be reported in a subsequent version.
Index Terms—eBPF, XDP, 5G core, UPF, GTP-U, packet
filtering, Kubernetes, DDoS mitigation, cloud-native network
functions

I. I NTRODUCTION
In a 5G Standalone (SA) system, the UPF anchors user
sessions and forwards traffic between the radio access network
(RAN) and external data networks [1]. Uplink traffic arrives
on the N3 reference point encapsulated in GTP-U over UDP
port 2152 [2], and the UPF is programmed by the Session
Management Function (SMF) over the N4 interface using
PFCP [3]. Because the UPF must accept tunnelled packets
from a large population of gNBs and, in roaming and multiUPF topologies, from peer UPFs on N9, its ingress is a natural
target for volumetric floods, TEID scanning, spoofed inner
sources and GTP-in-GTP injection [4].
Historically, high-capacity UPFs have relied on kernelbypass frameworks such as DPDK [5], which dedicate polling

cores and take the NIC away from the kernel. That model fits
poorly with cloud-native operations: Kubernetes schedulers,
container network interfaces, observability agents and publiccloud virtual NICs all assume the kernel owns the device. The
eXpress Data Path (XDP) [6] offers a middle ground. An XDP
program is an eBPF program that runs in the driver’s receive
path before the kernel allocates a socket buffer, can return
a verdict for each frame (drop, pass, transmit, or redirect),
and co-exists with the regular networking stack. XDP has
been used for in-kernel UPFs [7]–[9] and for GTP-U-aware
receive-side scaling [10], [11], but considerably less attention
has been paid to XDP as a dedicated admission-control layer
placed in front of an existing UPF, regardless of how that UPF
implements forwarding.
This paper addresses that gap. Our contributions are:
1) A six-stage XDP pipeline, GTP-Guard, that validates
GTP-U traffic against PFCP-derived session state and
drops illegitimate packets in the driver (Section V).
2) A cost model for ordering filter stages, with a closedform optimal order and a mechanism for re-ordering at
run time without detaching the program (Section V-D).
3) A Kubernetes deployment model, including state persistence across upgrades, privilege scoping, and publiccloud NIC considerations (Section VI).
4) A reproducible evaluation methodology for XDP-based
user-plane protection, stated as testable hypotheses (Section VII). Measured results are deferred to a later version
of this paper.
II. BACKGROUND
A. eBPF and the XDP Hook
eBPF lets user space load verified bytecode into the kernel
and attach it to hooks. Before a program is accepted, the
in-kernel verifier proves memory safety and termination by
symbolically executing every path, rejecting out-of-bounds
packet access, unbounded loops and unchecked pointer dereferences [12]. Programs share state with user space through
maps: hash tables, arrays, longest-prefix-match (LPM) tries,
per-CPU variants, ring buffers and program arrays used for
tail calls [13].

itself stays in XDP.
C. The 5G User Plane and GTP-U
The GTPv1-U header [2] is eight bytes: a flags octet (3-bit
version, protocol-type bit, and the E, S and PN bits), a message
type, a 16-bit length and a 32-bit TEID. If any of E, S or PN
is set, four optional bytes follow (sequence number, N-PDU
number and next-extension-header type). On N3, the E bit is
normally set because the PDU Session Container extension
header carries the QoS Flow Identifier (QFI) [15]. User data
uses message type 255 (G-PDU); signalling messages include
Echo Request/Response, Error Indication and End Marker. The
UPF learns valid TEIDs, UE addresses and QoS Enforcement
Rules (QERs) from PFCP Session Establishment and Modification messages carrying Packet Detection Rules (PDRs) and
Forwarding Action Rules (FARs) [3].

XDP underpins L4 load balancing such as Katran [17] and
Kubernetes service acceleration in Cilium [18].

Scheich et al. extended a UPF with XDP GTP-U handling

Positioning. Prior work uses XDP to be the UPF. GTPGuard instead treats XDP as a UPF-agnostic front door: it
protects any UPF, kernel-based, AF XDP-based or DPDKadjacent, by admitting only traffic consistent with current
PFCP state, and it focuses on stage ordering, run-time adaptation and cloud-native lifecycle concerns not addressed in
earlier designs.

V. GTP-G UARD D ESIGN
A. Design Goals
GTP-Guard is guided by four goals: (G1) drop early, so that
every rejected packet costs as little as possible; (G2) stay UPFagnostic, so the guard can front any UPF implementation;
(G3) never be the source of truth, so that session state is

always derived from PFCP and a guard failure can degrade
to pass-through; and (G4) be operable on Kubernetes, with
declarative configuration, rolling upgrades and Prometheusnative telemetry.
B. Pipeline
Fig. 1 shows the pipeline, and Fig. 2 gives a condensed
implementation of the IPv4 path.
Pre-classification. Frames that are not IPv4/UDP to port
2152 receive XDP_PASS immediately, so the guard is transparent to management, PFCP and N6 traffic sharing the
interface.
S1 – Peer allow-list. The outer source address is looked
up in an LPM trie holding gNB and N9 peer prefixes. The
trie is populated from operator inventory (for example, via a
Kubernetes custom resource) rather than from PFCP, because
gNB addressing changes far less frequently than sessions.
S2 – Header validation. The guard enforces version 1 and
the protocol-type bit, and passes non-G-PDU messages (Echo,
End Marker, Error Indication) to the UPF unmodified, since
their volume is low and their semantics belong to the UPF.
S3 – TEID admission. The TEID indexes a hash map
whose entries mirror the uplink PDRs currently installed by
the SMF. A miss means the tunnel does not exist on this UPF
and the packet is dropped. This single lookup removes TEID
scanning and traffic for torn-down sessions.
S4 – Extension-header walk. The optional fields and
extension-header chain are traversed in a loop bounded by
a compile-time constant, satisfying the verifier while accommodating the PDU Session Container that is ubiquitous on
N3 [15]. Chains that exceed the bound or overrun the frame
are rejected.
S5 – Inner checks. The inner source address must equal
the UE address bound to the TEID, which defeats spoofing
of other subscribers’ addresses. An inner UDP datagram
addressed to port 2152 indicates GTP-in-GTP injection and
is dropped.
S6 – Policing. A token bucket keyed by QER index enforces
a per-session ceiling. Admitted packets are redirected to an
AF XDP socket bound to the receive queue when the UPF is
an AF XDP application; otherwise the XDP_PASS fallback
of bpf_redirect_map delivers them to the kernel stack.
C. State Model and Control-Plane Synchronization
GTP-Guard holds three kinds of state: the peer allow-list
(operator-managed), session state (PFCP-derived) and policing state (data-plane-owned). Session entries map a TEID
to a compact record containing the UE IPv4 address, an
IPv6 prefix, and a QER index. To satisfy G3, a user-space
agent subscribes to session lifecycle events exported by the
UPF, translating PFCP Session Establishment, Modification
and Deletion into map updates. Where the UPF exposes no
such interface, the agent can derive the same state from the
N4 exchange it terminates; we prefer the event-export path
because it avoids re-implementing PFCP parsing and remains
correct if N4 is protected by IPsec.

Two consistency properties matter. First, insert-before-use:
a TEID must be present before the gNB sends traffic on
it. Because PFCP establishment precedes the N2 signalling
that hands the TEID to the gNB, an agent that applies
updates within the PFCP round trip satisfies this naturally.
Second, delete-after-drain: entries are removed only after
session deletion is acknowledged, so in-flight uplink packets
are not penalized. A watchdog compares map cardinality
with the UPF’s session count and flips the guard into a
pass-through mode through a single control-map flag if drift
exceeds a threshold, preferring availability over filtering when
state cannot be trusted.

Proposition 1. E[Cπ ] is minimized by ordering stages in

Proof. Consider two adjacent stages a followed by b, preceded
by stages with joint forwarding probability P . Their contribution is P (ca + pa cb ), and swapping gives P (cb + pb ca ).
Placing a first is no worse iff ca + pa cb ≤ cb + pb ca , i.e.
ca (1 − pb ) ≤ cb (1 − pa ), i.e. ra ≤ rb . Stages outside the
pair are unaffected, so any order containing an inversion can
be improved by an adjacent swap, and the sorted order is
optimal.
Under benign load almost every packet passes every stage
(pi ≈ 1), so ordering barely matters. Under attack it matters
a great deal: in a TEID-scanning flood, S3 rejects most traffic
while S1 rejects almost none, so r3 ≪ r1 even though the
LPM lookup is cheaper. Dependencies constrain the order (S3–
S6 need the parsed GTP-U header), but S1, S3 and S6 can
be permuted. GTP-Guard implements each permutable stage
as a separate program in a BPF_MAP_TYPE_PROG_ARRAY
and chains them with tail calls. The agent estimates pi from
per-stage counters, recomputes ri , and atomically rewrites
program-array slots, re-ordering the pipeline without detaching
XDP from the interface. The tail-call indirection adds a small
fixed cost per stage, so the agent uses a single fused program
in steady state and switches to the re-orderable chain only
when drop rates cross a configured threshold.

VI. C LOUD -NATIVE D EPLOYMENT ON K UBERNETES
A. Packaging and Lifecycle
GTP-Guard ships as a DaemonSet scheduled onto UPF
nodes by node affinity (Fig. 3). The agent loads a CO-RE
(compile once, run everywhere) object built against BTF, so
a single image runs across kernel versions in a mixed fleet.
Maps and links are pinned under /sys/fs/bpf; on restart,
the agent re-opens pinned objects rather than re-creating them,
so a rolling upgrade of the agent never interrupts filtering or
loses session state, the same persistence property eUPF relies
on for datapath continuity [9]. Program upgrades use atomic
replacement of the attached link, so the interface is never left
without a program. Where other XDP programs must share
the interface, the libxdp multi-program dispatcher [20] chains
them with defined priorities.
B. Interface Attachment
On bare-metal or private-cloud clusters, N3 is typically an
SR-IOV virtual function plumbed into the UPF pod through
Multus. Native XDP must then attach to the VF in the host
namespace before it is moved, or inside the pod namespace
by an init container; the latter couples guard lifecycle to the
UPF and is therefore avoided. On public cloud, N3 is usually a
dedicated elastic network interface on the node, and the guard
attaches in the host namespace.
C. Privilege Scoping
Loading XDP requires CAP_BPF and CAP_NET_ADMIN
on modern kernels; older kernels require CAP_SYS_ADMIN.
Deshpande and Bera note that eBPF-enabled 5G pods commonly run with broad capabilities and that the shared kernel
then becomes an attack path [19]. GTP-Guard confines all
privileged operations to the agent, keeps the UPF container
unprivileged when it uses the kernel path, restricts map access

by pinning under a directory readable only by the agent, and
exposes telemetry through an unprivileged sidecar.
D. Public-Cloud NIC Considerations
Virtual NICs impose constraints absent on bare metal. Native XDP support in cloud NIC drivers may require a reduced
MTU, a limited number of queues, or specific buffer sizes,
and loaders that do not meet these requirements can silently
fall back to generic mode. A practitioner report on AWS
describes AF XDP on the ENA driver falling back to generic
mode with about a quarter of packets lost unnoticed, and
reaching lossless operation only after adjusting buffer sizing,
at which point the instance’s packets-per-second allowance
became the bottleneck [21]. GTP-Guard’s agent therefore (i)
requests native mode explicitly and fails closed to an alert
rather than silently accepting generic mode, (ii) exports the
effective attach mode and per-queue counters as metrics, and
(iii) treats the provider’s per-instance packet-rate allowance as
a first-class capacity limit in planning.
VII. E VALUATION M ETHODOLOGY
A. Per-Packet Budget
For minimum-size Ethernet frames, line rate is 14.88 Mpps
at 10 Gb/s, 37.2 Mpps at 25 Gb/s and 148.8 Mpps at 100 Gb/s.
At a 3 GHz clock, one core sustaining 14.88 Mpps has a budget
of about 200 cycles per packet. Real N3 frames are larger,
because GTP-U, the PDU Session Container and inner headers
add at least 50 bytes, so the packet rate per link is lower;
however, attack traffic need not respect realistic sizes. We
therefore report both packet rate and bit rate, and treat cycles
per packet as the primary efficiency metric.

State divergence. A guard that drops on TEID miss can
black-hole legitimate traffic if session state lags PFCP. The
watchdog and pass-through flag bound the impact, but operators should monitor insert-to-first-packet latency (W5) before
enabling strict mode.
Shared-kernel risk. XDP improves isolation of the UPF
from hostile traffic, but it enlarges the trusted computing base
on the node. Loading must remain limited to a single audited
agent, and program signing should be adopted where the
platform supports it [19].
Scope of filtering. GTP-Guard does not inspect payloads,
enforce full PDR precedence, or apply downlink policy on N6;
the latter can reuse the same framework with a UE-addresskeyed map.
IX. C ONCLUSION AND F UTURE W ORK
GTP-Guard places a PFCP-aware, line-rate admission layer
in the driver receive path of a Kubernetes-hosted UPF, removing illegitimate GTP-U traffic before it consumes socket
buffers or UPF cycles while remaining agnostic to the UPF’s

own forwarding technology. The stage-ordering result gives
a principled basis for reconfiguring the pipeline when traffic
shifts under attack, and the deployment model addresses
lifecycle, privilege and public-cloud NIC constraints that determine whether XDP is practical in production. The immediate
next step is to execute the evaluation of Section VII and test
hypotheses H1–H5; further work will extend the pipeline to
IPv6 and N6, evaluate hardware offload on SmartNICs, and
close the loop between per-stage telemetry and an automated
controller that adjusts allow-lists, ordering and policing thresholds as part of a self-healing operations framework.
