Designing Collaborative AI-Driven Workflows for Scientific Software Engineering⋆
Akash Dhruva , Max Knobbeb , Pedro Machadob , Anshu Dubeyc
a Argonne National Laboratory, United States
b Fermi National Accelerator Laboratory, United States
c RIKEN Center for Computational Science, Japan

Abstract

arXiv:2610.09995v2 [cs.SE] 13 Oct 2026

Agentic artificial intelligence systems can carry out a broad range of tasks in software engineering and scientific research, from
writing and translating code to running workflows for data analysis and visualization. In scientific computing, the difficulty is
verifying that agent-generated code is both correct and understandable to teams whose members bring different areas of expertise. We
therefore argue that these systems are best used within collaborative team structures rather than as full automation. In the workflows
we propose, domain experts write the specification and plan, and agents operate under a deterministic orchestration pattern to write
the target code. Each stage ends with a numerical comparison against the reference code and requires human review and approval
before the next begins. We evaluate these workflows on the translation of a large high-energy physics application from Fortran
to C++, running the same task under different orchestrators, design patterns, and models. Across fourteen experiments, a simple
author–reviewer loop with enforced limits completed a comparable number of files to a multi-agent workflow at about one-third of
the cost per file.
Keywords: Scientific software engineering, Large language models, Agentic workflows, Human-AI collaboration, Code translation,
Research software, Loop engineering, Graph engineering

1. Introduction

Scientific software is a research instrument whose development is chronically under-resourced. A numerical code can
usually only be modified safely by someone who understands
the science it encodes, and such expertise is scarce. The codes
are long-lived and carry decades of modifications and domain
knowledge that is rarely documented in the published literature.
Previous work in research software engineering has argued that
investment in software practice is an investment in science, and
that long-lived applications need continuous maintenance to remain correct and usable (Heroux et al., 2023; Godoy et al., 2025).
Any substantial change to a scientific codebase, such as adding
features, refactoring, porting to new hardware, or translating it to
another language, is therefore necessary but limited by available
developer time. Modernizing legacy code is a common example,
where the aim is to preserve the encoded domain knowledge and
keep the code usable (Shipman and Randles, 2023).
Large language models (LLMs) are now widely used as coding
assistants (Chen et al., 2021; Jimenez et al., 2024), and agentic
tools place them inside loops in which they read files, run commands, and revise their work based on feedback (Yang et al.,
2024; Liu et al., 2024b). This can lower the cost of software
development and maintenance, but an agent’s output is not guaranteed to be correct and its behavior over long tasks is difficult
to control (Lahlou et al., 2026). Because agentic systems require human supervision, unconstrained agent behavior directly

increases supervisor workload. Moreover, an agent overseen
by a single person can pass an existing regression suite while
introducing errors the suite misses. Such errors accumulate and
make the code harder to maintain, which poses a risk to the
quality and numerical correctness of scientific software.
We argue that agents are better used within a collaborative
structure than in full automation, with work divided into stages
that humans can easily review and verify. In the workflows we
propose, domain experts write the specification and plan for
each stage of the work, and agents carry out the mechanical
work in bounded orchestration patterns. Each stage ends with
a numerical comparison against the reference code, and only a
human can record the approval that lets the next stage proceed.
Building on empirical studies of the effect of AI coding assistants on developer productivity and code quality (Ziegler et al.,
2024; Dakhel et al., 2023), we explicitly separate the roles of
supervision, implementation, and acceptance. This keeps the
human developer engaged and preserves their understanding of
the code.
To test this approach, we use a computational Lab Notebook
built on the practices we developed in our earlier work on reproducible computational research (Dhruv and Dubey, 2023),
which provides a controlled environment in which the same task
can be repeated under equivalent conditions.
The Lab Notebook is a versioned directory tree that holds the
code, configuration, and the agentic layer (specification, plan,
tools, and logs) for each stage. Keeping this state in shared
files rather than in a user’s private orchestrator configuration is
what lets the same task be rerun under a different orchestrator

P2. Humans design and accept the objectives, agents do
the repetitive work. Agents are used for tasks that are broad
and repetitive, such as applying a known translation rule across
many files, updating build files, and checking test coverage.
Humans make the decisions that require judgment, such as what
counts as correct for a given routine, how to resolve a numerical
disagreement, and whether to accept a result.
P3. Reproducibility and provenance. The orchestration of
the agents is deterministic, but their output is not. The workflow
therefore records what was done, including which files were produced, which test exercised them, and what numerical agreement
was observed. This record is kept in plain text files, tool-call
logs, and reasoning summaries, so that a run can be inspected,
resumed, or repeated.
P4. Collaboration between roles. The work involves domain experts, who know what the code computes, and research
software engineers, who know how it is built and run. Domain
experts write the specification and review the results, while software engineers write and maintain the tools and workflow code
that the agents use.
P5. Open and user-controlled agent execution policy. The
scientists doing the work should have full access to the orchestrator’s agentic stack: system prompts, inter-agent interactions,
tool definitions and protocols, model calls, shell environment
behavior, and ReAct-based execution policies (Yao et al., 2023).
With this control, workflows can be specified explicitly and reproduced reliably.

The test case we examine here is the translation of Monte
Carlo for FeMtobarn processes (MCFM) (Campbell and Ellis,
1999; Campbell et al., 2011; Campbell and Neumann, 2019;
Campbell et al., 2021), a widely used parton-level Monte Carlo
program for precision collider phenomenology, written in Fortran. Modern high-performance computing (HPC) requirements
make translation to C++ and a more modular software architecture desirable, with the eventual goal of integrating it into
device-portable codes such as Pepper (Bothmann et al., 2024).
Code translation is a suitable test case because the existing code
provides a numerical reference for each translated routine, so
correctness can be measured directly. Translation is also already
one of the main applications of LLMs in scientific computing
and an active research area (Assunção et al., 2025; Pietrini et al.,
2024; Valero-Lara et al., 2025; Dearing et al., 2024; Davis et al.,
2025). In our earlier work, we used CodeScribe1 , an LLM-driven
tool, to generate Fortran–C++ interface layers for MCFM, allowing existing and translated code to run together during an
incremental migration (Dhruv and Dubey, 2025). In this paper, we extend CodeScribe’s architecture to design autonomous
agentic workflows and evaluate their performance and efficiency.
We run the same translation task, starting from the same commit and the same agentic layer, under different strategies and
models. The strategies range from a simple author–reviewer
loop to a multi-agent workflow running concurrent agents. In
our experiments, the control needed to use agents on scientific
software came from deliberate design of the workflow architecture and the agent execution policy. Adding concurrency without
careful design did not improve the outcome and increased the
cost.
The paper is organized as follows. Section 2 states five design
principles and describes the workflow architectures we examine.
Section 3 presents the case study and the experimental design.
Section 4 reports the evaluation and results, and Section 5 concludes with the implications and limitations.

Because the inputs are kept separate from the orchestrator,
the orchestration can be changed while the task and the correctness criterion stay fixed. We compare two patterns: an author–
reviewer loop, and a phased workflow that distributes the work
over many subagents and integrates their results serially (Figure 3).
Single-agent loops are a common choice for such translation
tasks. One agent runs repeatedly in short sessions and keeps all
of its state on disk, a pattern known as the Ralph Loop (Huntley,
2025) and used by Lahlou et al. (2026) for Fortran to JAX code
translation. Each iteration starts a new session and passes it a
file, prompt.md, that points the agent to the shared inputs. The
session reads the current state, advances the work, and exits, so
state passes between iterations only through the files on disk.
Knuth (2026) describes a similar practice, in which the agent
records its progress in a plan file after every step. The purpose is
to avoid the degradation of output quality due to growing context
length (Liu et al., 2024a; Modarressi et al., 2025; Hong et al.,
2025).
CodeScribe author–reviewer loop. CodeScribe (Dhruv et al.,
2026b) implements a fixed author–reviewer loop that extends
the single-agent loop. Two agents work on the shared inputs,
an author that advances the plan and a reviewer that checks
the result and passes its findings to the next cycle. The loop is
implemented in _loop.py in the CodeScribe repository and is
configured by loop.toml. This file lists the shell commands
that the author may run in addition to CodeScribe’s internal tools
(read, write, edit, glob). It also contains a first user message,
under the key [[chat.user]], that CodeScribe places in the
chat history before the loop starts. The message points the
agent to the specification and plan files, tells it to read the plan
first, and states that the constraints it should operate under. The
file serves the same role as prompt.md in a single-agent loop,
while the instruction for each cycle is built by CodeScribe. The
configuration used in the experiments is as follows.

The CodeScribe loop repeats at two levels. A cycle is one
author pass followed by one review pass. Within a pass, the agent
makes a sequence of model API calls, built on ReAct policies,
which we refer to as iterations (Figure 4). Each iteration sends
the message list to the model and receives its reasoning, tool-call
requests, and output text. Between calls, CodeScribe validates
each requested tool call, runs it only if it passes, and appends the
result to the message list. A pass ends when the model returns
completion text without tool calls.
The CodeScribe loop, which runs at most five cycles by default, is shown in Figure 5. It contains only the agents and the
orchestrator, and acceptance lies outside the loop. At the end of
each cycle, CodeScribe adds a summary of the cycle and the list
of pending items to the prompt of the next cycle. The loop ends
earlier in two cases: when the author agent reports the work complete, which skips the review, or when the reviewer reports no
pending items or blockers (pending items that require a human
review). CodeScribe also writes log files in .codescribe/loop
for inspection, crash-resume, and audit.
Enforced limits. CodeScribe enforces the limits on each agent
at the validation step between iterations. It caps the number of
iterations and tool calls, and it rejects a tool call after repeated
failures. After several consecutive failed iterations, it instructs
the agent to report a blocker instead of continuing. When a
tool call is rejected, CodeScribe returns an error message to the
agent so it can diagnose the problem in the next iteration. Unlike
limits stated in the specification or the prompt, which the model
may not follow, these cannot be exceeded by the agent. This
implements principle P5 and allows the loop to run unsupervised

For the multi-agent workflow, authoring is parallel and integration is serial. Many subagents translate individual files at the
same time, each writing only its own output, while a single integrator subagent owns the shared build, adds the new files, and
runs the verification. Authoring is routed by file complexity: the
workflow inspects each file and sends ordinary files to a lighter
model and large or deeply nested files to a stronger one. To
profile the full transformation end to end, we run the workflow
as an open-ended process across these agents, so it terminates
only at the approval gate rather than after a fixed number of steps.
As a result, the multi-agent workflow itself runs as a loop, with
additional control flow around the agents.

3. Case Study: MCFM
With the inputs fixed, the workflow configurations differ only
in how the orchestrator is started and in how much control flow
surrounds the agents. We investigate three consequences of that
difference: whether the additional structure of a multi-agent
workflow justifies its cost relative to the loop, whether enforcing
limits in the orchestrator rather than stating them in the prompt
changes what the agent does, and how far either result depends
on the model.
We evaluate these effects on the modernization of MCFM,
a parton-level Monte Carlo program for hadron-collider phenomenology. MCFM provides a large library of Standard Model
processes. It computes cross sections and differential distributions at next-to-leading order (NLO) in QCD and, for a subset
of processes, at next-to-next-to-leading order (NNLO). To do
5

so, it also supplies the necessary phase-space integration, partondistribution handling, and analysis routines (Campbell and Neumann, 2019). The task is representative of a broader scientific
software engineering problem: development and improvement
of a Fortran codebase with hundreds of source files and deep call
trees.

Under both orchestrators, the agents run these tools through
dev/workflow.py, which takes a transformation name and runs
the corresponding script using Python. CodeScribe agents use
the python3 executable from their allowlist, and Claude Code
agents follow the directions in their prompts. The gate and the
oracle are therefore the same code in every run, so the orchestrator and the pattern can be varied while everything else stays
fixed.

times. All runs start from the same commit of the MCFM submodule and therefore from the same set of 445 candidate files.

3.1. Task, target and verification criteria
Translation is done in two steps. The first step translates
each Fortran unit into C++, emitting three files per unit: a C++
implementation with an extern "C" wrapper, a C++ header,
and an iso_c_binding Fortran interface. These bindings let
existing Fortran callers continue to link and run while the code
is translated one unit at a time. A second step ports the resulting
C++ code to device-portable kernels, so the full pipeline is
Fortran → C++ → kernels.
Correctness is defined by the code’s own benchmarks. A
translated file is verified when two checks pass. First, a coverage
probe perturbs the translated file and confirms that the benchmark
result changes, showing that the benchmark exercises it. Second,
the unperturbed file reproduces the reference benchmark value
within a fixed tolerance. Together these two checks form the
oracle used in the rest of the paper. A file that no benchmark
exercises, such as pure infrastructure code, is tagged as translated
but not verified.

3.2. The Lab Notebook and the Design of Experiments
The Lab Notebook’s structure (Figure 2) is a template other
teams can adopt for their own AI-driven workflows. The inheritance structure, the shared agentic layer design, and the
staged transformation format are all generic. Only the tools under dev/tools are specific to MCFM. A different project can
keep the same layout, change the project-specific parts, and add
its own implementation of a concrete agentic layer with tools
accessible via model context protocal (MCP).
The transformation transformations/mcfm-translate is
designed to batch-translate a group of Fortran files. Each file
carries three attributes. A file is ready when every file it depends
on has been translated, and it is not marked as untestable infrastructure. File-level dependencies are obtained from a Doxygen
cross-reference build of the Fortran source. Its oracle status is
verified, translated, or failed, as determined by the checks above.
Its recorded outcome is the status the agent itself reports, which
may contain hallucinations.
The agent groups ready files, typically about five that share
a folder or a test, and lists each group in agent_log.md as a
Markdown heading followed by a checklist of its files. Before
opening a new group, an agent runs a gate script that reads these
groups and the approvals in approvals.toml. The gate limits
how far the agents can work ahead of human review: a new group
cannot be opened while three completed groups are waiting for
approval, or while a group waiting for approval contains a failed
file. Work in a group that is already open may finish. Only a
human writes approvals to approvals.toml (Section 2.2).
The deterministic steps, namely building the dependency
map, ranking the ready files, checking a file against the oracle, and enforcing the gate, are scripts under dev/tools.

ccloop (runs R12–R14) the same author–reviewer loop, with at
most five cycles, run by Claude Code. The execution policy
is stated in the prompt, the agent has an unrestricted shell,
and the author reports its own actions to the reviewer.
The configurations ccworkflow and csloop differ in both orchestration pattern and base agent, so comparing them directly
cannot isolate the effect of either factor on cost and performance.
The third configuration, ccloop, shares its agent with ccworkflow
and its pattern with csloop, so each pairwise comparison varies
only one factor.
Comparing ccloop against ccworkflow holds the agent and
the model fixed (Claude Code, Opus 5) and varies only the
orchestration pattern. Comparing ccloop against csloop holds
the pattern fixed, and varies only the base tool-calling agent and
its execution policy. Together, these two comparisons let us
attribute performance differences to specific layers of the agentic
stack. Within csloop the orchestrator stays the same while the
model changes across different families, so differences there can
be attributed to the model and its API format.

4.3. A specialized against a general-purpose agent
This comparison holds the agentic approach constant and
varies only how the behavioral rules are enforced. csloop (R4–

and the context size per author–reviewer loop, checking for
repeated tool calls, and protecting files the agent is not allowed
to edit. The Claude Code loop gave its agents unrestricted access
and stated its rules only through prompted constraints.

4.4. Comparison across models
This comparison keeps the orchestrator the same and changes
only the model. The models differed in their tool-calling behavior, and these differences drove cost. The cheapest and most
expensive runs in Table 2 do not line up with which model tier
is nominally cheaper. The tier billed as cheapest produced two
very expensive runs per file settled (Sonnet 5, R7 and R8). The
pattern is clearer in tool calls. The two Sonnet 5 runs used several times as many tool calls per file as every other csloop run
(Table 2 and Figure 7(d)), and finished fewer files. This suggests
that Sonnet 5 needed many more passes on a file to make the
same progress, some of them from rejections and constraints
imposed by the bounded shell. The cheapest-billed model was
therefore the least efficient per file settled.
The runs from a different family (csloop GPT 5.6-Sol, R9–
R11) show that the results carry over to a different provider.
R10–R11 performed similarly per file to the Opus 5 runs at a
similar token cost, though GPT 5.6-Sol used more tool calls to
get there. They also picked work that closely matched what the
Opus 5 runs picked (Section 4.5).
A major difference between the runs originates in a Fortran
idiom in the MCFM codebase that has no direct C++ equivalent. On one file, the runs split on a design decision the agent
specification never addressed. The Fortran original declared four
named precision kinds.

5. Conclusion
Scientific software is expensive to maintain and sensitive to error, and AI agents can already carry out substantial autonomous
work on it. Using that capability without eroding domain understanding and correctness guarantees requires structure around
the agent. We designed such a collaborative orchestration structure and compared its variants on a single task, the translation of
MCFM.
In our approach, humans retain ownership of intent and acceptance, and numerical correctness is specified and enforced
at an explicit verification boundary. Hallucinated progress is
contained by checks that the workflow must confirm before a
file counts as verified. Five design principles connect the orchestration architecture with the agentic layer to run a multi-agent
workflow or a two-agent loop.
We ran fourteen versions of the same translation task, changing the orchestrator (CodeScribe vs Claude Code) and the models
(Opus 5, Sonnet 5, GPT 5.6-Sol), to identify which parts of the
design determined the outcome. A single author–reviewer loop
matched the output of the multi-agent workflow at roughly one
third of the cost per file settled. Multiple parallel agents pay off
only when the work and its context are independent (Section 4.2).
The models we tested chose similar files, largely because the
ranking tool used by the orchestrator determined which files
were ready to translate. Tool usage was enforced through the
agent execution policy (CodeScribe) or through prompt-based
instructions (Claude Code), which influenced the outcome. One
result was driven by an orchestrator memory note that influenced
agent decision-making in three later runs without leaving a trace
in our records. The oversight was ours, but a mechanism that
can introduce a correct assumption across runs can introduce an
incorrect one the same way.

Shared agentic layers can help teams organize their science
campaigns and promote systematic use of AI to improve productivity. The author-reviewer loop can be applied to deploy
simulation campaigns, run analyses, and perform work in manageable portion, which lets humans supervise AI work effectively. Several aspects of agentic layers remain open and may
continue to shape their design. One is the format of the model
API. The model API exposes controls for prompt caching and
tool use, which account for the cache efficiency of CodeScribe
(Section 4.4). Reasoning summaries, also available through the
API, allow direct inspection of model reasoning and support
human-AI collaboration. Exposing reasoning through an API
introduces security risks, and recent work has proposed mitigations (Panfilov et al., 2026). Such work will likely influence how
open-source LLMs are used and may lead to a common model
API for scientific applications.
Agent execution policy is a further open problem. A recent
report found that multi-agent systems operating at scale circumvented well-enforced guardrails to complete the work their specifications prescribed (METR, 2026). Specification and policy
design therefore require care. Treating this design as a collaborative process allows agentic systems to be evaluated as scientific
instruments prior to autonomous deployment.

Appendix A. Dataset Archive
The evaluations in Section 4 were carried out using the Lab
Notebook archived on Zenodo (Dhruv et al., 2026a). The archive
contains transformations and datasets for agent trajectories described in Section 3.2. These trajectories are organized by date,
with separate agent logs for the CodeScribe and Claude Code
runs.
The two orchestrators record their agent logs in different formats. Claude Code supplies jsonl logs, which can be parsed
with Python scripts to extract token usage and tool calls for each
assistant message; each such message is treated as one agent
iteration. CodeScribe’s loop agents store their logs in toml files
containing detailed records of tool-call events, token usage, and
run information. These logs are collected by a metadata agent,
which is triggered after a run is complete. The metadata agent
copies the run logs to the evals/experiments directory and
creates a corresponding GitHub branch that records the MCFM
code changes in its repository. For all agents, the reasoning
summaries and hashes returned by Anthropic’s Messages API
have been scrubbed from the logs.
The metadata agent uses evals/archive.toml, which provides simple instructions on how to discover, archive, and label
the run logs. It is supplied as a task file to a CodeScribe agent:
