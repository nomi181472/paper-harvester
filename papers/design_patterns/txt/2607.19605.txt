A BSTRACT
Almost every piece of recorded music you have ever heard was modified before
it reached you; commercial releases rarely spring fully formed from a musician’s
mind. Despite the promise of music generation models for one-shot output, such
fine-grained iterative refinement workflows are a complementary problem, and
largely out of their reach. There is also a gap for musicians: while they can
express what they want to hear, not all have the facility with studio production
tools to implement the complex set of actions needed to realize these intuitions. We
formalize this task as agentic post-production, wherein individual aspects of a track
are targeted, refined, and combined into a final version. We argue the bottleneck
is data: existing corpora do not reflect how realistic post-production chains map
onto the vocabulary musicians and engineers actually use. We observe that there is
a language for modifying recorded music that is dense, consistent, and learnable.
To leverage this, we introduce the Rule-based Instructions for Music Editing
(RIME) framework, which generates realistic paired edit-instruction data from
any baseline music dataset grounded in canonical methods, design patterns, and
constraints derived from real production workflows. RIME leverages POEMS, a
new toolkit that combines stem separation, mixing, and common studio effects
for use by multimodal agents. We use POEMS and RIME to generate 15,000
pairs of edit instructions and ground-truth audio, and use this data to evaluate
existing multimodal LLMs as agents on this task, showing persistent challenges
in current models’ post-production capabilities. We also demonstrate RIME’s
ability to improve post-production agent performance via supervised fine-tuning
using synthetic data generation. We see RIME as an early step towards iterative
musical agents, collaborative systems that could transform music production much
as interactive coding agents have reshaped software engineering.1

I NTRODUCTION

There is a pervasive loop in the studio. When a producer listens to a recording they’re working
on, they will often hear something wrong, or something that could be better. They may isolate the

offending stem, apply a chain of effects, blend it back in, and listen again. The musician being
recorded may hear something else and make a request. The producer implements a fix, then listens
again. Then again. Then again.
This loop has its own peculiar language. When a musician asks for something “warmer” or “bigger,”
a seasoned engineer can translate it into a specific recipe (e.g. a high-shelf cut at 8 kHz, parallel
compression on the drum bus, and a tempo-synced reverb send on the vocal) and run it. The translation
between what music feels like and the sequence of operations that produces that feeling is not, in fact,
magic. It is a dense and surprisingly consistent vocabulary, built up over decades of studio practice.
Today’s AI music systems are typically not part of this loop. Yet, we have good reason to desire
them to be: it admits an iterative, interactive workflow that is musician-centered at its core. It is
now reasonable to ask whether a software agent could join it, because these agents live in loops of
their own: perception, action, reasoning, and tool use. Indeed, this would also be a strong testbed for
such agents. Each iteration in this loop couples a perceptual judgment, an instruction context, a large
assortment of potential tools, planning, and reasoning. What would it take, then, to bring an agent’s
loop into dialog with this post-production loop?
We argue that what is needed is a general framework for modifying music, beyond the capabilities
of one-shot generators. To this end, we introduce the Rule-based Instructions for Music Editing
(RIME) framework, which aims to generate large-scale music editing data that follows a process
closer to what you would see in studio music production. RIME starts from individual mixes, creates
edit “recipes” using a large vocabulary of common studio engineering rules, constraints, and design
patterns, and executes a series of tool calls to isolate sources, apply edits, and create a final mix.
This then creates supervision for agents to do the same. Additionally, RIME creates instructions at
varying levels of abstraction to describe the edit chain for a given recipe, mimicking the variation in
how precisely these intents are described in the real world. To create editing data, RIME leverages a
newly built suite of tools that allow for pitch, ornamentation (various effects), equalization, mixing,
and source separation (POEMS) edits, which we call POEMS.
RIME is also unique in that it can be extended to any dataset containing musical tracks, and especially
designed for mixed tracks (or even generated ones, potentially, which normally come without
individual instrument stems). We demonstrate using RIME in conjunction with state-of-the-art music
understanding models to generate triplet edit data from untagged musical mixes.
Overall, our contributions are:
1. We formalize agentic post-production as an iterative task: starting from a mixed track and
a production intent (an arbitrarily clear instruction), an agent targets individual elements,
refines them, and recombines them into a finished mix
2. We introduce RIME, a scalable, reusable data generation framework for transforming
virtually any corpus of (contemporary Western) musical audio into a structured set of (input,
output, instruction) triples. RIME encodes recipes, motifs, ordering constraints, and pattern
policies of studio post-production, in part calibrated from datasets of real production chains,
and produces instructions at multiple levels of abstraction.
3. To support this framework, we introduce POEMS, an audio post-production toolkit
spanning 20+ operators exposed via Model Context Protocol for use by tool-calling agents.
4. We run a paired triplet benchmark with ≈15,000 (input, output, instruction) triples
generated with RIME on MusicCaps (Agostinelli et al., 2023), enabling evaluation across
instrument families, edit categories, and abstraction levels.
5. We conduct a listener study to validate that musically experienced users can reliably match
edits and their corresponding instructions across abstraction levels.
6. We develop the POEMS Agent Framework to design and evaluate zero-shot agent baseline
multi-step tool-calling audio-language model agents, surfacing major limitations in currentgeneration models’ abilities on this task, such as their ability to assemble the correct chain
of operators vs. parameterize those operators correctly.
7. We fine-tune an open-weight LLM orchestrator with RIME-synthesized data and demonstrate improvements over the zero-shot agent baselines.

R ELATED W ORK

Many previous text-prompted generative editing tasks have relied solely on paired instruction/audio
data and audio-language embedding improvements to perform edits (Liang et al.; Tsai et al., 2024;
Chu et al., 2025; Zhang et al., 2024; Manor & Michaeli, 2024; Yang et al., 2026; Lan et al., 2026).
While this allows for certain edits without the need for supervised (input, output, text) data, the
lack of ground-truth data makes these methods difficult to evaluate systematically. Several general
audio editing frameworks leverage triplet data (input audio, edited audio, instruction); however, their
datasets largely focus on more general edits such as addition, deletion, replacement (via text-to-audio
synthesis), inpainting, and superresolution (Wang et al., 2023; Liang et al., 2025; Jia et al., 2025; Ellis
et al., 2025). InstructME (Han et al., 2024) creates paired triplet edit data from musical variations,
focusing on only a small subset of production edits such as remixing, adding, replacing, extracting,
and removing.
Agentic editing is a relatively unexplored area. SonicMaster (Melechovsky et al., 2025) uses an agent
to repair five categories of degradations (EQ, Dynamics, Reverb, Amplitude, and Stereo) from audio,
but does so using DDIM inversion and noise injection. LLM2Fx-Tools (Doh et al., 2026) creates a
benchmark from MedleyDB (Bittner et al., 2014; 2016), randomly sampling musically realistic FX
chains on single sources and uses a language model to create specific natural language instructions. It
then fine-tunes a (text-only) LLM tool-calling agent to derive FX chains from instructions. Although
this is the closest work to a post-production agent, it operates only on single stems, does not rely on
an iterative listening workflow, and does not differentiate the multiple levels at which an edit may be
described in natural language.
Several existing frameworks have analyzed the mapping between abstract natural language and studio
effects. SoxialFX (Zheng et al., 2016) analyzed common abstract descriptors of three individual
effects. Further work analyzed effect chain recommendation from natural language descriptors (Stasis
et al., 2017). Recently, MixAssist (Clemens & Marasovic, 2025) introduced a dataset capturing
conversations between amateur and professional music producers during a mixing session. There is
no existing work that has leveraged these findings to motivate actions taken by a tool-calling agent,
nor have these language/FX mappings been extended to the full context of music post-production.
In all, no existing benchmarks match the characteristics of real-world post-production loops described
earlier. For this, such a benchmark would need to (i) apply edits to individual stems and introduce
them back into a mix, (ii) be able to handle instructions at varying abstraction levels, and (iii) support
an iterative, listen-and-tweak workflow. Here, we introduce exactly this suite of components.

3.1

T HE POEMS T OOLKIT

First, we need a suite of tools to enact a given edit workflow. Modern LLM agents can sometimes write
code to create such tools, but we see no need to reinvent the wheel at runtime. Producers often have
favored audio plug-ins, and integrating with these similarly requires the agent to use existing tools. At
the same time, we need a stable, canonical, and agent-oriented set of tools for a robust evaluation. For
this purpose, we introduce the Pitch, Ornamentation, Equalization, Mixing, and Separation (POEMS)
toolkit, which defines an operator catalog O for end-to-end music post-production. Each operator
o ∈ O has an associated parameter space Θo .
To edit an individual source within a mixed track, we must first isolate it using source separation.
We use the 6-stem variant of Demucs (Rouard et al., 2023) to separate x = xs + rs , where xs is the
target stem and rs = x − xs is the residual. This restricts editable stems to vocals, drums, bass, piano,
and guitar (we attempted to use SAM Audio (Shi et al., 2025), but found it produced poor results in
this setting). After processing, we mix the edited stem back with its residual x̃ = x̃s + rs .
We provide two pitch edits for vocal stems: pitch correction (autotuning) and harmony generation. For both edits, we use estimated f0 contour from CREPE (Kim et al., 2018), S-KEY key
detection (Kong et al., 2025), quantization, and resynthesis with PSOLA (Valbret et al., 1992) to
preserve formant structure. We implement four ornamentation and equalization effect families
with Pedalboard (Sobot, 2021): time-based (delay, algorithmic reverb), modulation (chorus, phaser),
dynamics (compressor, peak limiter, waveshaping distortion, noise gate, split-band de-esser), and
equalization (high-pass, low-pass, high-shelf, low-shelf, and parametric peaking filters). In all, this
gives us a substantial toolkit capable of enacting a wide variety of desired edits (list in Appendix A).
3.2

RIME C OMPONENTS

Recipes, Graphs, and Motifs The central abstraction RIME relies on is an edit graph G = (V, E),
a directed acyclic graph whose nodes v ∈ V = (ov , θv , sv ) each apply an audio operator ov ∈ O
with parameters θv ∈ Θov to audio. This is similar to an FX chain in common audio production
parlance, except that it allows parallel branches (via audio sends which copy audio off from the
stream, and audio returns which re-mix modified versions of those copies into the original stream).
Hand-specifying enough graphs (e.g. thousands) to form a robust dataset would be infeasible. Rather,
we need a way to generate such graphs at scale. Fortunately, audio production follows many recipes,
defined here as symbolic templates for edit graphs with particular aesthetic goals (see example in
Figure 2). Each recipe r ∈ R is specified using a schema r = (Br , φr , λr , Hr ):
• bindings Br : (references to clip metadata resolved at plan-generation time, e.g. key)
• when φr (eligibility predicate, e.g. vocal harmony support requires vocal stem and key)
• weight rules λr (multipliers to indicate how common certain recipes should be)
• graph Hr (outline for applying the recipe, normally SEPARATE → PROCESS → MIX)
PROCESS contains the recipe’s actual processing sub-graph. SEPARATE and MIX scaffold it with stem
isolation and residual recombination steps, so every recipe operates in a stem-aware fashion.
To share structure across recipes, we factor commonly co-occurring sub-chains into reusable units
we call motifs. A motif is a named, typed sub-graph that can be expanded inline within any recipe
that references it. For example, the retro tilt eq motif expands to high shelf() → lowpass(),
capturing the joint high-frequency roll-off characteristic of a vintage sound.
Parameter Priors To generate plausible-sounding audio effects, we need to sample their parameters
in such a way that we favor commonly used settings while allowing naturalistic variation across
edits. We take an empirical approach to this by estimating prior sampling distributions from observed
processor settings, which we call generation priors. Each prior πo is a distribution over operator o’s
argument space Θo . Recipes specify which prior πo to use, so the same operator can use different
priors in different recipes (e.g. to account for stylistic variation).
We collect processor settings from MixParams (Clemens & Marasovic, 2025) and SocialFX (Zheng
et al., 2016), using MixParams for equalization and compression, including separate vocalcompression priors, and SocialFX to supplement general compression thresholds and ratios. To

3.3

I NSTRUCTION G ENERATION

We combine the recipes, motifs, priors, and constraints above to construct a candidate pool P
(Algorithm 1). For each clip x, we resolve recipe bindings against m(x) and generate J parameter
draws per eligible assignment. We retain each graph with weight ω for subsequent subsampling.
In post-production, there are varying degrees of granularity with which you can describe the same set
of edits. A sound engineer may be able to describe an edit with extreme specificity (e.g. “apply a
chorus with 20 ms delay and 0.65 depth”), while a musician desiring a similar result may say e.g.
“apply a delicate shimmer.” We account for this by generating instructions at three abstraction levels:
AL0 Describes the edit graph directly. All effect names, exact parameter values, and operator
order are preserved in the generated instruction (e.g. language of professional mix engineers).

3.4

DATA VALIDATION

As a final check, we seek to ensure instructions and recipes are audible, stylistically appropriate,
and accurate at every abstraction level. We therefore screen examples for four types of errors: (1)
abstraction-level violations: instructions fail to follow the requirements for their abstraction level;
(2) inconsistencies: instructions misinterpret the preceding level’s text; (3) stylistic inconsistencies:
instructions describe edits that conflict with the source material, using MusicCaps (Agostinelli et al.,
2023) captions as context, and (4) parameter incongruity: edits combine parameter values in ways
that produce implausible processing. We use Qwen3 235B (Yang et al., 2025) as an LLM judge
and discard examples it flags under any criterion. We then rank the remaining examples by cosine
similarity between source and edited audio using MERT (Yizhi et al., 2023) embeddings; we remove
the lowest-scoring 5% to screen out extremely atypical edits, then keep the next 5,000 by audibility
as our primary set. In Appendix D, we provide full validation procedure details.

E XPERIMENTS

POEMS-AF: the Agent Framework We introduce a multi-turn tool-calling framework for an
agent to use POEMS to isolate a target stem, process it, and mix it back into the original track. The
agent first listens to the input and proposes a tool-use plan based on the user’s instruction. At each
step, it listens to the current audio and may revise its plan before selecting the next tool or returning
the result. For malformed tool calls, we allow n recovery attempts before invoking the tool with
default arguments (Appendix A); we set n = 1. We allow at most 20 tool-call steps (excluding
recovery attempts). If the agent does not return edited audio within this limit, we declare agent
failure and use the unedited audio as evaluation outputs.

Generating Synthetic Data with RIME We use RIME to synthesize evaluation triplets
(input audio, edited audio, instruction) starting from a corpus of full mixes with no available stem-level annotations. We use Music Flamingo (Ghosh et al., 2026) to identify instruments in
MusicCaps (Agostinelli et al., 2023) tracks, and keep only tracks that contain at least 2 stems and have
at least one stem in [vocals, bass, drums, guitar], resulting in 2899 tracks. From these, we generate
79, 905 plans and subsample 25, 000 as described in Algorithm 1. Before filtering, 1, 757 plans were
excluded because Demucs failed to isolate the target stem. Using the LLM filtering described in
Section 3.4, we obtain 15,335 valid clips and then further subsample the top 5,000 using the MERT
ranking described in the same section.
For SFT training data, we sample 3,000 random instrument combinations, with priors derived from
Nunes & Ordanini (2014); Pereira et al. (2023), generate 105,741 plans, subsample to 25,000, and
then filter using the LLM judge, resulting in 20,098 plans. We then use coverage-constrained stratified
random sampling, where we select 1,000 of these plans such that all recipes used in creating groundtruth edit data are represented in the training set. For each chosen plan, we generate instructions
at all three abstraction levels, resulting in 15,000 unique evaluation and 3,000 unique SFT training
(source audio, output audio, editing instruction) triples.
Supervised Fine-tuning We perform supervised fine-tuning on an agent using G EMMA 3 N (Team
et al., 2024) orchestration. We fine-tune only the reasoning step and do not enforce any specific tool
calls. We use low-rank adaptation (Hu et al., 2022) with a rank of 16, α of 16 and learning rate of
2 × 10−4 . We train for one epoch on the 3,000 data triplets from the training dataset. We keep the
multi-turn tool-calling framework identical to the zero-shot agent for comparison.
Evaluation Metrics We use two primary modes of evaluation: audio similarity and edit-graph
similarity. We use Fréchet Audio Distance (Roblek et al., 2019; Gui et al., 2024) and Kernel Audio
Distance (Chung et al., 2025) in the MERT (Yizhi et al., 2023) embedding space. We also introduce
edit similarity (∆sima ), which measures the similarity between the direction of change (in the MERT
embedding space) of the agent’s output vs. input and the direction of change of the ground-truth
edited audio from RIME. For graphs, our primary metric is Graph F1, which is the arithmetic mean
of four F1 scores on graph kind, operator, stem, and edge. In Appendix G.1, we provide several
additional evaluations to corroborate the primary metric results.
Human Evaluation To test whether instructions adequately describe audible edits across abstraction
levels, we conduct a listener study using 30 original–edited audio pairs, rating three instructions per
pair: the matching instruction, a hard negative targeting the same instrument and often similar effects,
and another distractor, rating the correspondence of each with the audible edit on a 1–5 scale.

Figure 13 shows recipe coverage across generation, subsampling, and final benchmark selection. The

A BSTRACTION LEVEL SYSTEM PROMPTS

AL0: You are a professional mixing engineer writing up a chain for an assistant
to patch. You know the signal path and you specify it exactly: every processor
named, every setting given with its units, in the order it is patched. You speak
economically, the way one engineer talks to another. Write one to three spoken
sentences.
AL1:
You are a musician who records and mixes your own material. You know
what the common effects are called and you use their names, but you do not work
in numbers: you say how something should sound and how much of it there should
be. Your vocabulary is a player’s, not a spec sheet’s. Write one or two spoken
sentences.
AL2: You are a musician describing the sound you want rather than how to get
it. You talk about the overall character of the result and how far it is pushed,
in the words you would use about a record you like. Naming an effect is fine
where that is the natural way to say it, but you are asking for an outcome, not
dictating a recipe. Write a single short sentence.

D.1

P ROMPTS

System Prompt
You are auditing one instruction written for a music-editing dataset.
You are given the symbolic edit graph it describes, the instruction one
level of abstraction below it, the rules that instruction was written
under, and what this level is licensed to discard. You decide two things
and nothing else. First, whether the instruction obeys its own rules.
Second, and separately, whether it correctly describes the instruction
it was derived from -- the same edit, at less precision, still
truthfully. You are indifferent to style. You do not rewrite anything.

Rules
1. Judge the instruction only against the rules and contract supplied.
Do not import preferences of your own about how it should read.
2. The contract says what this level MAY discard. Discarding something
the contract permits is never an inconsistency, however much detail
is lost. Adding processing the source does not describe always is.
3. For a banded level, a descriptor is correct when it lands in the
band the graph specifies. The suggested wording is a suggestion:
different words in the right band are correct, and the suggested
words in the wrong band are not.
4. For consistency, judge fidelity to the source, not conformance to a
contract. Ask only whether a reader of the rewrite would come away
with a true picture of the edit the source describes. Classify each
way it fails:

26

Preprint. Under Review.

• wrong interpretation { the element IS in the source but the
rewrite describes it incorrectly: a cut described as a boost, a
large space described as subtle, the wrong stem, one processor
mistaken for another. The information is present and wrong.
Calling a reverb a delay is this, not hallucination.
• hallucination { the rewrite describes processing, a parameter or
a target that is not in the source at all. Something is ADDED
while the rest stays intact.
• omission { something the level was obliged to keep is missing.
Being less detailed than the source is NOT omission where the
licence above permits it; that is the abstraction working as
intended.
5. A rewrite can fail in more than one way, so list every kind that
applies. An empty list means it describes the source correctly.
6. Do not report the same defect under both verdicts. al rules grades
the text against its own level’s rubric; consistency grades it
against the source. A missing operator can be either or both, but
say so once under each only if it genuinely fails both tests.
7. Cite rule failures by the index of the rubric item. An
unattributable failure is not a failure.
8. Mechanical checks have already run separately. Judge only what they
cannot settle.
9. Give each failing verdict exactly one sentence of justification,
naming the rubric item or contract term it breaks. The two verdicts
get their own sentence each: they answer different questions and can
disagree, so one sentence covering both explains neither. A passing
verdict needs none.

1. Working Audio State - The agent keeps track of the working audio, the active isolated source,

and if the audio is ready to return
4. Failure/Repair State - Tracks the failed tool name, failed tool assignment, and failed arguments to the tool call.
E.2

E NFORCING AGENT B EHAVIOR

We introduce a few mechanisms to steer the behavior of the agent:
• Separation and Mixing “Branches” - When a stem is isolated, a branch is opened and kept
track of in the execution state and closed when the source is mixed back in with the residual.
This branch keeps track of which source is isolated and the location of the corresponding
residual track. The system will not allow another separation tool call or operation on another
source until the source has been mixed in with the residual.
• Forced Separation - The system can force separation if the agent tries to operate on a source
before isolating that source
• Branch Recombination Gate - If a branch is open and there is no pending assignment, the
system can force a mix tool call so the agent does not stray
• Forced Pending Assignment Processing - If the agent tries to return or mix sources before it
has completed all of its assignments, the system will force it to perform another tool call.
• Forced return - If there are no more assignments and no branch is open, the system will
force the agent to return the audio
