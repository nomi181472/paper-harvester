Large Language Models (LLMs) have significantly improved programming efficiency by parsing natural language into code snippets. However, their performance degrades significantly as requirements scale; when
faced with multi-modal documents containing hundreds of scenarios, LLMs often produce incorrect implementations or omit crucial constraints. Observing LLMs’ ever-evolving capability and their persistent stochastic hallucination, we raise a question, i.e., whether it is possible to make LLM-based agentic programming go
beyond code generation to requirement compilation, i.e., whether programmers can produce a runnable system
by only accomplishing (non-trivial) requirement documents?
In this work, we take a first step by proposing the ARC (Agentic Requirement Compilation) technique to
parse a multi-modal requirement document, describing hundreds of scenarios in a DSL format, into a runnable
software system. In addition to the source code, ARC also generates software engineering artifacts including
(1) a modular design that spans the user interface, API interface, and database, (2) enriched test cases for
each interface (including unit tests, modular tests, and integration tests), and (3) detailed traceability across
all artifacts for software maintenance. Our approach employs a bidirectional test-driven agentic loop: (1) a
top-down architecture phase that decomposes requirements into UI, API, and database interfaces, each of
which is equipped with verifiable test suites, and (2) a bottom-up implementation phase where agents
generate code that must satisfy the generated tests. Throughout this process, ARC maintains strict traceability across requirements, design, and code to facilitate intelligent asset reuse and follow-up maintenance. We
evaluate ARC on two complementary benchmarks, i.e., a depth-oriented benchmark of 6 runnable web systems spanning 50–200 requirement scenarios, and the breadth-oriented AppForge benchmark comprising 101
Android app generation tasks. Across 3 independent trials, ARC outperforms all state-of-the-art LLM-based
baselines, with the generated web systems passing on average 50.6% more GUI tests, and achieving 100%
compile success and 68.3% test case pass rate on AppForge. In addition, a user study with 21 participants

1 Introduction
The software engineering landscape has entered a transformative era where Large Language Models (LLMs) have evolved from simple autocompletion assistants into proactive coding partners capable of planning and executing complex development workflows [59, 71]. The integration of these
models into the software development life cycle has broadened access to code creation, shifting the
developer’s role from a low-level code producer to a high-level curator and architect [46, 65]. However, while LLMs excel at generating localized code snippets, their performance faces a “complexity wall” when tasked with large-scale projects. As requirement documents transition from simple
text to multi-modal specifications spanning hundreds of scenarios, traditional agentic generative
approaches frequently suffer from requirement drift and omission and persistent hallucinations
[30, 33, 42]. This widening gap between intent and implementation raises a fundamental question
in the age of agentic programming, i.e., how far are we from shifting the paradigm from mere code
generation to a more rigorous process of requirement compilation?
The research community has primarily explored the following paradigms to address large-scale
code generation from textual descriptions [33]:
• Role-Based Orchestration: These frameworks [29, 56] such as MetaGPT simulate a traditional
software company by assigning specialized roles (e.g., Product Manager, Architect, Programmer)
to different agents. By following Standard Operating Procedures (SOPs), they decompose highlevel requirements into intermediate artifacts like PRDs and system designs before implementation. While their waterfall approaches [29] can output a complete repository structure, they
remain procedural rather than verifiable, i.e., a misinterpretation in the initial PRD generates a
structurally sound but functionally broken repository.
• Reactive Action-Loops (OpenHands [68] / SWE-agent [73]): These frameworks focus on
tight environment interaction. OpenHands, in particular, utilizes an event-driven architecture
where a centralized “EventStream” coordinates interactions between the user, the agent, and
a secure docker-based runtime. By this means, these tools enable the agents to autonomously
search complex directory structures, execute shell commands, and iteratively refine code based
on real-time feedback from compilers or test execution results.
Despite these sophisticated structures, generating a runnable system from a multi-modal document remains difficult for the following reasons. First, most existing tools treat requirements as
natural language prompts. However, natural language is inherently ambiguous and lacks the explicit hierarchy needed for repository-scale dependency tracking. MetaGPT’s waterfall approach
[29] is procedural but less trustworthy in practice. For example, if a ”Product Manager” agent misinterprets a requirement node, that error propagates into the architecture and code without an
early-stage gate to stop the cascade. Second, reactive agents (e.g., OpenHands [68]) are excellent

To bridge this gap, we propose ARC (Agentic Requirement Compilation), a framework that shifts
the paradigm from stochastic code generation to a rigorous process of requirement compilation.
Unlike existing “role-play” or “reactive” systems, ARC treats multi-modal requirement documents
as a high-level source language, structured via a light-weight, graph-based Domain Specific Language (DSL). By transforming dense specifications into a formal graph of requirement scenarios,
we provide a deterministic blueprint which reduces requirement drift and implementation omission typical of natural language prompts. This structured foundation enables a novel bidirectional,
test-driven agentic loop, i.e.,

• Testable Architecture Construction: A top-down phase that first decomposes the graph into
verifiable UI, API, and database interfaces, accompanied by reliable tests for each interface. As
a result, the architecture is modularized as a set of interactable interfaces, each of which is
equipped with a set of tests in the form of unit tests, component tests, and integration tests.
• Constrained Code Generation: A bottom-up implementation phase where agents generate
code that must satisfy these predefined test suites as constraints. Specifically, ARC implements
the architecture by satisfying low-level unit tests first, then moves to satisfy component tests
and integration tests in the higher level.
Generally, this dual-phase approach simulates the workflow of the classical V-model [22] in a
test-driven manner, which solves the “complexity wall” by enforcing a continuous feedback loop
between design and code. By prioritizing the generation of interface tests before application logic,
ARC creates a grounding mechanism that “gates” agent creative output, ensuring every generated module is strictly verified against its functional requirement. Furthermore, ARC maintains
an explicit traceability record across the requirements, designs, and tests, allowing the system to
intelligently reuse existing assets and maintain global consistency even as project scale increases.
This systematic alignment ensures that the final output is not just a collection of code snippets,
but a cohesive web system that is consistent with the original multi-modal document. The maintained traceability record can also facilitate software maintainability such as incremental requirement compilation. Moreover, we track the agentic requirement compiling process with the version
control system (e.g., Git), allowing us to intervene the process by checking out their designated
revisions.
We evaluated ARC by compiling 6 complex web systems from multi-modal requirement documents containing 50 to 200 distinct scenarios. To further assess generalizability beyond web systems, we additionally evaluated ARC on the AppForge benchmark [57], which comprises 101 Android app generation tasks. results demonstrate that by replacing the stochastic one-shot generation of vanilla LLMs and the
rigid waterfall roles of frameworks like MetaGPT with our bidirectional compilation loop, we enhance system reliability. Specifically, ARC outperforms state-of-the-art baselines by generating
repositories that pass on average 50.6% in GUI tests and successfully eliminating the fragmented
implementation errors common in existing agentic workflows. Furthermore, to assess the accessibility of our lightweight DSL, we conducted a user study involving 21 participants, including
novice users with limited programming experience. The study demonstrates that the structured,
graph-based DSL serves as an effective medium for human-AI collaboration. Participants successfully specify an average of 107 scenarios per project within 5.6 hours, and existing requirement

2.1

Formal Definition and Meta-Model of Requirement

We define a requirement document as a directed acyclic graph (DAG) of Requirement Nodes. As
illustrated in our meta-model (see Figure 1), each node acts as a container for full-stack specifications, spanning from high-level context at the root to specific UI, API, and DB constraints at the
leaves. The core structure of our DSL is built upon three primary entities:
• Requirement Node: Each node represents a unique feature. It explicitly defines multi-modal
description, Dependencies (prerequisite requirement) and Children (hierarchical sub-features), ensuring the framework can track repository-scale impacts.
• Scenario: Each requirement node contains one or more workflows that represent end-to-end
user journeys. One scenario can specify a set of prerequisite scenarios, indicating its dependency.

• Step: A scenario is decomposed into an ordered sequence of atomic steps expressed in a Gherkinlike manner. Each step captures the test context (Given), the action under test (When), and the
expected, verifiable outcome (Then), which are used to generate test cases.
For the full formal grammar of our DSL, readers may refer to the BNF specification on our
project website [54]. The design of this DSL is not merely for organization. It is the fundamental
grounding mechanism that allows ARC to overcome the complexity wall of large-scale systems.
• Deterministic Blueprinting: By converting ambiguous natural language into a dependencyaware graph, we provide the agentic loop with a deterministic path for top-down Architecture
Construction (see Section 4).
• Test-Driven Grounding: Every step requires a paired action and expectation; the DSL serves
as a direct source for generating GUI and API test suites. These expectations act as the “gates”
that prevent the requirement drift and hallucinations common in existing models.
• Traceability: The unique identifiers (IDs) within the DSL allow ARC to maintain a Traceability
Record. This ensures that every line of generated code in the Bottom-Up phase (see Section 4.3)
is provably linked back to a specific requirement expectation.
While formal, our DSL is designed to be lightweight and accessible to both human architects
and AI agents. In addition, we design a visualization tool to enable users to design the requirement
graph in a more intuitive way. Interested readers can check our project website [54] for how the
tool is used to draft requirement documents.

• The second phase operates in a bottom-up implementation direction, where agentic creative

the lowest level, the DB Access layer, and move upward through the API implementation to
the frontend implementation. Crucially, each generated code module is immediately executed
against its predefined test suite. If a module fails its test, the agent enters a reactive loop to fix
the code until it satisfies the interface contract.
Throughout both phases, ARC maintains a traceability record. This captures the link between
a specific scenario in the original document and its corresponding test and code implementation.
This record allows ARC to decide whether to reuse, modify, or create a new interface. In addition,
such a record serves as a blueprint for the generated system, allowing developers to understand
exactly why a piece of code exists and how it relates to the original multi-modal intent.

• UI: Defined as both a producer and a consumer of events, 𝑖UI = (𝐸out , 𝐸in ), where 𝐸out is the set
of events generated by user actions and 𝐸in is the set of events received from APIs.
• API: Defined as mapping events to operations and emits events, 𝑖API ∶= (𝑒in , 𝒪, 𝑒out ), where
𝑒in is the incoming event, 𝒪 is a data operation, and 𝑒out is the event emitted to the UI or other
APIs.
• DB: Defined as a set of data entities, 𝑖DB ∶= {𝐷𝑖 }, where each entity 𝐷𝑖 = (name, {𝑎1 , 𝑎2 , … , 𝑎𝑛 })
consists of a name and a set of attributes.
To determine the interfaces required by a node 𝑟 , ARC parses both textual descriptions and
images (via an image captioning vision-language model). Based on the formal definitions of interface types, it generates a set of interfaces 𝑖 ∈ ℐ𝑟 that collectively capture all requirements. Each
interface signature specifies the type (UI, API, or DB), the name, and the expected location in the
system 𝒮. For UI interfaces, the signature includes layout information inferred from images, as
well as the events produced and consumed. For API interfaces, it includes the incoming events,
the data operations performed (expressed as function headers with parameters), and the outgoing
events emitted to other interfaces. For DB interfaces, it includes the data entity name and its attributes. When two interfaces reference the same event (i.e., one produces it and another consumes
it), a data flow is established between them, which serves as a reference for the bottom-up phase.
Using the login feature in Figure 2 as an example, the agent generates a UI interface that produces a LoginClicked(username, password) event and consumes a LoginResponse(success,
message) event, with layout information inferred from the screenshot. It also generates an API
interface that maps the incoming LoginClicked event to the authService.login(username,
password) data operation (function header) and emits the corresponding LoginResponse event.
Finally, the DB interface defines a User entity with attributes username and passwordHash. The
detailed agent prompt and more detailed animated demonstrations are available at [54].

4.3

Bottom-up: Constrained Code Generation

The second phase of the ARC framework operates in a bottom-up direction, transforming the
testable architecture into a realized software system. As described in Algorithm 3, this phase ensures that agentic creative output is strictly gated by the predefined interfaces and test suites,
preventing architectural drift. The implementation process follows the recursive unwinding of the
DFS traversal, distinguishing between leaf and non-leaf nodes.
Implementation of Leaf Nodes. For a leaf node 𝑟 ∈ 𝑉𝑟 (where Children(𝑟) = ∅), the implementation focus is localized. The input to the agent consists of the set of interfaces 𝐼𝑟 generated during
the top-down phase. The objective is to synthesize a code implementation 𝑐𝑟 that fulfills the contract defined by 𝐼𝑟 and satisfies its local test suite 𝒯𝑟 . In this case, the dependency set is empty, i.e.,
𝒟𝑟 = ∅. The agent is prompted to generate code 𝑐𝑟 such that 𝑐𝑟 ⊧ 𝒯𝑟 .
Implementation of Non-Leaf Nodes. For a non-leaf node 𝑟 , the implementation begins only after
all its children 𝑣 ∈ Children(𝑟) have been processed. At this stage, ARC must not only implement
the interfaces 𝐼𝑟 directly associated with the current node but also correctly invoke the realized interfaces generated by its children. The dependency interfaces are defined as 𝒟𝑟 = ⋃𝑣∈Children(𝑟) 𝐼𝑣 .
The implementation 𝑐𝑟 is thus conditioned on both the target interfaces 𝐼𝑟 and the implemented
child interfaces in 𝒟𝑟 . This ensures structural alignment between the requirement hierarchy and
the software’s internal call structure.

5 Evaluation
We design our experiments to answer the following research questions:
• RQ1: Effectiveness. Can ARC correctly implement web systems of different scales from complex multi-modal requirements, in comparison to state-of-the-art approaches?
• RQ2: Overhead Analysis. What is the overhead introduced by ARC, measured in token consumption and development time?
• RQ3: Ablation Study. How much does each individual component (DFS search strategy, test
suite 𝒯, traceability record ℳ) contribute to the overall performance of ARC?

Baselines

We selected four state-of-the-art baselines. The baselines are described below, along with details

(1) MetaGPT [29]: a multi-agent repository-level CLI framework that generates code from highlevel requirements via role-based agent coordination.

Why can ARC outperform the baselines? First, we observe that baselines often compress requirements into unstructured summaries, the resultant context is usually long and noisy, potentially
leading to hallucination by missing or mistaking the crucial implementation. In contrast, ARC interprets each feature (i.e., requirement node) into a set of verifiable tests, providing a more reliable
signal for LLM to produce code. Second, existing frameworks and AI IDEs (e.g., Cursor and Copilot) are likely to repetitively modify implemented code, even if their features are independent in
the requirement documents. In contrast, ARC avoids these issues by parsing the requirements with
the designed DSL where agents can strictly process one feature after another, isolating their implementation with minimal interference. As a result, ARC enforces orthogonality and non-regression
in the process of code generation.
When can ARC fail to pass the GUI tests? By investigating the GUI tests that ARC failed to pass,
we identify two main causes. First, implicit requirement scenarios may be missing from the documents. Since ARC treats the requirement graph as the source of truth, it may miss implicit constraints; for example, our 12306 document did not explicitly specify that user IDs cannot be duplicated during registration, causing failures in related test cases. Second, test feedback may provide
insufficient guidance within the given budget. For instance, in PrestaShop’s “Recently Viewed”
product feature, the test only reports that “viewed product A is not shown,” which gives limited
information for the LLM to infer where and how to fix the problem.

RQ3: Ablation Study

5.7.1 Experiment Design. In this experiment, we adopted the settings described in Section 5.1 and
5.4. On the web benchmark, we compared three ablated variants of ARC: (1) w.o. DFS strategy,
where ARC designs and implements requirement nodes in an arbitrary order; (2) w.o. Test, where
no test suites 𝒯 are generated for interfaces during the top-down phase; and (3) w.o. Traceability,
where code provenance ℳ is not recorded during the bottom-up phase. On the Android app benchmark, AppForge, we compared the performance on fully and partially described requirements (see
Section 5.1). We used the same performance metrics as in RQ1 (Section 5.5).
5.7.2 Results. Table 6 shows our results. Without traceability, ARC spends more time gathering
contextual information from the repository. Although the DFS strategy and testing contribute to
increased time and cost, this is a necessary trade-off to support reliable development in large-scale
systems, as evidenced by the higher pass rate. These results validate our claims in RQ1 and RQ2.
On AppForge, ARC has better performance on the fully described documents. Test suite pass rate
increases from 18.3% (partially described) to 31.7% (fully described). The improvement also applies
in the test case pass rate and the final pass rate. Note that, the performance on partially described
documents still outperforms the state-of-the-art baselines.

against our ground-truth test cases. Finally, participants completed a post-study survey.

DSL easy to learn, requiring an average of 5 rounds of requirement updates to complete their tasks.

5.9

Discussion

Beyond the conventional software generation, ARC also shows promise for supporting software
evolution [61]. Its core advantage lies in the explicit traceability it maintains across requirements,
interfaces, tests, and implementations, which helps agents reason about how local changes may
affect interacting components in an existing system. Our experimental results further suggest that
this design is effective in practice. Compared with state-of-the-art baselines, ARC consistently
achieves higher pass rates and exhibits stronger stability on complex, repository-scale systems,
indicating that requirement grounding and test-driven decomposition are beneficial.
At the same time, the experiments also reveal important limitations of the current framework.
First, ARC is primarily optimized for functional correctness, and therefore may overlook nonfunctional requirements such as security, performance, scalability, and reliability, which are equally
important in practice. Second, ARC remains fundamentally bounded by the completeness of the
requirement document and the quality of the generated tests. When key scenarios are missing or
the feedback signal from tests is weak, the system may still produce partially incorrect implementations. These observations point to several directions for future work. One direction is to extend
ARC from pure functional compilation to multi-objective requirement compilation, where functional requirements are treated as hard constraints and non-functional properties are optimized
as soft objectives. Another is to improve the strength of the testing and feedback loop, for example by generating more complete tests, richer debugging signals, and more informative failure
localization.

concerns reliance on proprietary LLMs, which may be updated at any time without disclosure, making precise versioning and full replication of results difficult. We acknowledge this as an inherent

last threat is LLM non-determinism, which we mitigated by running each approach for 3 independent trials and reporting mean and standard deviation on all results. We will extend the study with

External Validity. There are two main factors that may limit the generalizability of our results.
First, we selected six web systems for our benchmark. While these systems capture standard enterprise and transactional web applications, they do not fully represent the diversity of web system
behaviors. For example, media-heavy streaming applications (e.g., YouTube, Discord), real-time
collaboration tools (e.g., Google Docs), and single-page applications (e.g., Google Maps) exhibit
complex behaviors that are difficult to automatically test and therefore challenging to systematically benchmark. Furthermore, such systems often involve ambiguity in implementation choices,
such as whether to use WebSockets for real-time communication, or other architectural decisions.
Addressing these complexities could be an avenue for future work. Second, ARC was evaluated
using Gemini 3 Pro as the underlying model, which raises questions about transferability to other
models. However, as long as the underlying model is trained on coding data, the framework remains applicable. Our approach is a general organizational and instructional framework that is
similar to multi-agent or other system frameworks, which do not rely on any model-specific advantages. It is designed to leverage already capable models in a structured way.
6 Related Work
Code Generation. Early automatic-programming systems such as PROW generated executable
code from formal logical specifications [9, 67]. Later heuristic and probabilistic methods include
grammar-based generation [4, 72] and specialized statistical models [19, 32], but are often rigid
and hard to scale. Transformer-based models support longer-context reasoning and more complex
program generation, including Codex [13], MBPP [7], APPS [28], and competitive-programming
systems such as AlphaCode [39]. Stronger foundation models such as ChatGPT and Deepseek [2,
27] enable semantic code understanding for IDE suggestions such as Cursor and Copilot [14, 16, 40],
and real-world repair on SWE-bench [34, 74], with Trae Agent reaching near 80% [64]. These works
motivate the shift from function-level code generation to repository-level generation [31, 43, 63].
Repository Generation. Repository-level generation is difficult because long-context business
logic spans many files. Existing work follows three axes: (1) Interactive feedback: multi-round planning with external feedback, such as SDE-I [77], which uses static analysis and unit tests for library generation but requires reliable pre-existing tests, and CodePlan [8], Cursor [16], and Copilot [14] Plan Mode, which derive repository-aware plans before code generation; (2) Memory augmentation: RepoCoder [76] and CodeChain [37] retrieve code through dependency graphs, codesearch methods align natural-language queries with code fragments [44], and RepoGraph [49]
models code-line-level repository structure; and (3) Task delegation: multi-agent systems such as
OpenHands [68] and HyperAgent [51] distribute planning, navigation, and editing across agents,
with communication and context-management overhead [70]. Effective for incremental generation
over existing repositories, these approaches lack explicit system-level requirement modeling; newfeature changes can therefore affect unrelated components or invalidate passing tests. In contrast,
ARC tracks requirement-implementation alignment throughout the development lifecycle.

End-to-end SE Agents. Extending repository generation, waterfall frameworks model development as a linear pipeline, including Self-Collaboration [21], ChatDev [56], and MetaGPT [29],
whereas agile frameworks such as AgileCoder [45] use iterative sprints. Existing agents still lack
enforced requirement alignment. ARC treats such alignment as a first-class objective, keeping new
implementations consistent with system requirements without regressing prior behavior.
Test Generation. Test generation is central to software reliability and spans three complementary
classes: (1) Program-analysis-based approaches: symbolic execution [12, 25, 58], including Klee [12]
and DART [25], and search-based techniques [6, 23, 50], including EvoSuite [23] and Randoop [50],
systematically explore program behaviors but often require precise models or extensive search;
(2) Hybrid approaches: program analysis with learning-based guidance improves exploration and
prioritizes semantically relevant executions [11, 38], yet remains implementation-centric; and (3)
LLM-based approaches: recent work frames test generation as code synthesis from focal methods
or natural language descriptions [3, 20, 35, 47, 60, 66, 69, 75]. Requirement-intention-driven testing generates project-specific tests from explicit validation objectives, preconditions, and expected
results [55]. Recent issue-localization work also treats test suites as executable proxies for requirements [41]. Although these methods capture semantics, they typically operate at the unit level and
generate tests independently of system-wide specifications. Test generation is complementary to
ARC: rather than proposing a new test generator, ARC treats tests as first-class artifacts derived
from structured requirements and uses them as correctness gates in repository-level compilation.
7 Conclusion
Repository-scale development is challenging because maintaining correctness and managing dependencies in large, evolving systems is difficult. We frame this as a requirements compilation
problem, translating multi-modal specifications into runnable web systems. We propose ARC,
which operates in two phases. The top-down phase designs formalized UI, API, and DB interfaces,
with dependencies enforced by initially failing tests. The bottom-up phase implements and validates these interfaces. On a depth-oriented benchmark of six web systems, ARC outperforms
state-of-the-art approaches by up to 108.1% in test pass rates; on the breadth-oriented AppForge
benchmark of 101 Android apps, ARC achieves a 68.3% test case pass rate on average, outperforming all baselines. A user study further confirms its effectiveness and usability.
